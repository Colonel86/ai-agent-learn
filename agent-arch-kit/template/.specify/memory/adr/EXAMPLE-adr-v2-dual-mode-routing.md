# EXAMPLE-ADR: 量化研究 Agent V2 采用双模式路由 + Skill 配置驱动，替代多 SubAgent 层级路由

> 这是一份 **worked example**（参照 nfr-standard 的 EXAMPLE-plan.md 惯例），
> 展示一份合格 ADR 的成品形态。真实项目中请从 `_TEMPLATE.md` 起步并按 `README.md` 编号。

## 元信息

- **状态**: 已采纳
- **决策日期**: 2025-Q4
- **决策人**: 耿明
- **触发条款**: constitution §2.3 **A1**（影响全部核心模块，替换成本远超 1 人周）+

- **相关 ADR**: 无前置

## 1. 背景与问题陈述（Context）

- 触发因素：V1 采用多 SubAgent 硬编码层级路由，**新增一个能力需改 4+ 文件（含 2 个核心文件）**，
  每次上新能力都带回归风险；能力需求进入快速增长期（规划翻倍），架构成为吞吐瓶颈
- 关键约束：金融研究场景，输出正确性容错率低；团队小，无法承受每能力多文件回归测试的成本；
  已有评估体系（组件/轨迹/任务三层）必须继续可用
- 不在范围内：模型选型、评测栈选型（另行决策）

## 2. 决策（Decision）

**决策**：重构为 **双模式路由（Fast / Deep）+ Data-First 流水线 + Skill 配置驱动系统**，
放弃 **修补 V1 层级路由** 和 **迁移 harness 式单循环**。

**核心理由**（≤ 3 条）：

1. 新增能力的边际成本必须降到"加 1 个配置文件、零核心改动"，否则能力翻倍计划不成立
2. Fast/Deep 双模式让 80% 的简单查询走低成本快路径，复杂分析才进重流程——成本与延迟按需分层
3. 配置驱动使评估可以按 Skill 粒度做回归，与既有三层评估体系天然对齐

## 3. 备选方案对比（Alternatives Considered）

### 方案 A：双模式路由 + Skill 配置驱动（✅ 最终选用）

| 维度 | 描述 |
| --- | --- |
| 简介 | 意图先分流 Fast/Deep 两模式；能力以 Skill 配置文件描述（when_to_use / 参数 schema / 数据依赖），SkillRunner 统一执行 |
| 优点 | • 新增能力 = 1 配置文件，零核心改动、零回归风险 • System Prompt 按需装配，token 显著下降 |
| 缺点 | • 需要一次性重构（约 6 周） • Skill 描述质量成为新的关键依赖（when_to_use 写差则路由错） |
| 隐藏成本 | Skill 配置规范需要文档与评审习惯养成；SkillRunner 的参数自动修正逻辑需专门测试 |

### 方案 B：保留 V1 层级路由，局部修补（❌ 放弃）

| 维度 | 描述 |
| --- | --- |
| 简介 | 不动架构，把最痛的两个核心文件做抽象收敛 |
| 优点 / 缺点 | 短期成本最低 / 边际成本不变：每能力仍改多文件，能力翻倍后维护成本线性上升 |
| **放弃理由** | 修补解决不了"新增能力必须动核心"这个结构性问题；且 V1 的 SubAgent 层级使跨域查询（如"资金费率 + RSI 关联"）在架构上就难以支持（实测 0% 成功率）——这不是 bug 是结构 |

### 方案 C：迁移 harness 式单循环（Claude Agent SDK 范式）（❌ 放弃）

| 维度 | 描述 |
| --- | --- |
| 简介 | 弃显式编排，单循环 + 工具集 + 模型自主规划 |
| 优点 / 缺点 | 新能力=新工具，扩展性也好；开放任务上限高 / 执行路径不确定，难做步级审计 |
| **放弃理由** | 金融研究场景要求查询路径可解释、可审计、可逐步评估（轨迹级评估是质量底座）；且典型查询模式高度结构化（数据获取→计算→解读），确定性流水线的成本与延迟都更优。留观察点：模型能力提升后此路线可能翻盘（见 Revisit Triggers） |

## 4. AI Agent 视角

| 维度 | 评估 |
| --- | --- |
| Token 成本 | System Prompt token **↓43.8%**（Skill 按需装配替代全量描述）；典型查询 LLM 调用次数 **↓50%** |
| 延迟（TTFT / E2E） | Fast 模式跳过规划步骤，简单查询 E2E 显著下降（数据获取为主要耗时） |
| Eval 友好度 | Skill 粒度回归成为可能；从 0 建 **246/246** 全通过测试体系 |
| Observability | 路由决策与 Skill 执行均为显式 span，轨迹评估直接可用 |
| 注入风险 | Skill 配置收敛了工具面（每 Skill 声明数据依赖），比 V1 全局工具池的攻击面更小 |
| 数据出域 | 无变化（自托管栈，符合 R1） |

## 5. 后果（Consequences）

- **正面**：能力数量翻倍（+10 项，总 30+）零回归事故；核心代码 ↓70%；
  歧义消解 72.2%→100%（Hard 33.3%→100%）；跨域查询 0%→100%；工具调用命中率 80%+→99%+
- **负面 / 代价**：when_to_use 描述质量成为单点依赖——写差直接导致路由错误
  （靠"精确化 when_to_use + 评审 checklist"缓解，但本质是把复杂度从代码移到了配置）；
  一次性重构占用 6 周，期间新能力冻结
- **中性 / 副作用**：团队工作方式改变——"写能力"从写代码变成写配置 + 写评估用例

## 6. 重新评估触发条件（Revisit Triggers）

- 当 Skill 数量 > 80，检查 when_to_use 冲突率与路由准确率是否劣化（配置驱动的规模上限）
- 当模型换代后，harness 式方案在本场景的轨迹评估指标追平流水线（方案 C 翻盘条件）
- 当 Fast/Deep 边界的误判率 > 5%（双模式分流本身失效）
