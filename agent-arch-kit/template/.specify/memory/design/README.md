# Design Doc · 架构描述

ADR 管"**为什么**这么选"（一个决策一份），design doc 管"**系统现在长什么样**"
（一个系统/子系统一份，持续更新）。目标读者：新人与新会话的 AI——五分钟建立系统图景。

## 规则

- **轻量为纲**：C4 前两层（系统上下文 + 容器）+ 关键数据流 + 信任边界，**不做 arc42 全套**；
  组件级细节留给代码和模块 README
- **图一律 mermaid**：可 diff、可评审，禁止贴图片
- **更新时机**：plan 阶段涉及新增容器、改变数据流或信任边界的变更，必须同步更新本目录对应文档
  （不同步 = 计划不完整）；纯内部实现变更不用动
- **与 ADR 互链**：图中每个"有故事"的选择标注对应 ADR 编号；design doc 说现状，ADR 说来路
- 命名：`<system-or-subsystem>.md`，从 `_TEMPLATE.md` 复制起步

## 腐化防线

design doc 最大的风险是过时后误导读者。两条防线：

1. 文档头部必填「最后校对日期」；收尾 retrospective（constitution §4）检查其是否晚于本次变更
2. 发现图与现实不符：以现实为准立即修图，并检查是否有未落档的决策（漏写的 ADR）
