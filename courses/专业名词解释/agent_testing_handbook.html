00 — 起点

为什么 Agent 要分四层来测

Agent 不是「一问一答」。它是一连串决策:调哪个工具、传什么参数、拿到结果怎么处理、失败怎么恢复、整体计划是否连贯、任务最终有没有完成。

核心认知

Agent 评估的单位是 「轨迹 trajectory」,不是「最终答案」。

轨迹 = 系统提示 + 推理步骤 + 带参数和返回值的工具调用 + 每一步的中间状态,这一整条有序序列。

为什么必须看整条轨迹?因为误差会累积:每步 95% × 8 步 ≈ 66% 的端到端完成率。只看最终答案,你永远不知道失败发生在哪一步。所以 Agent 的失败会聚成几类互相独立的维度——某一维好,不能弥补另一维的崩。这就是为什么要分层、逐层兜住。

越往上 = 越接近用户、闸口越关键;越往下 = 覆盖越全、频率越高。

①
LAYER 1 — 地基

可观测 / 追踪

离线 + 在线

没有 trace,后面所有评估都是盲的。这一层全量记录每一步,是整个金字塔的地基。

测什么:调用链可视化、延迟、成本、token 用量、错误追溯、工具选择路径。把多 Agent 的调用渲染成图,让你看到「这一次运行到底发生了什么」。

对应工具
Phoenix(开源/本地最强) LangSmith(LangGraph 原生最顺) Langfuse(开源全栈) W&B Weave Helicone(代理式,最快接入) Datadog LLM Obs
标准底座:OpenTelemetry + OpenInference / OpenLLMetry 语义约定
②
LAYER 2 — 核心

离线质量评估

离线 · CI 门禁

每次提交代码时跑,达不到阈值就拦住。这层最杂,内部分三块。

2A · Agent 执行质量(Agent 专属,最核心)

普通 LLM 评估的「相关性 / 毒性」抓不到 Agent 的失败模式。需要单独打分的维度:

工具选择 / 正确性
调对工具了吗?不需要工具时能正确地不调用吗?(常见错误:工具描述语义相近时按关键词瞎匹配)
参数正确性
传给工具的参数对不对。
轨迹 / 计划遵循度
走的推理路径对不对,计划质量如何。答对了但路径混乱 = 生产隐患。
任务完成 / 目标达成
最终目标到底实现了没有。
错误恢复
工具失败时 Agent 是否优雅地处理、重试。
推理连贯性
中间步骤在回答层和轨迹层是否逻辑一致。
任务放弃的诚实度
无法完成时是否如实报告,而不是硬编一个答案(拒答校准)。
对应工具
DeepEval(6 个 agent 指标 + DAG 决策树确定性打分) TruLens(专门的 agentic 评估器) LangSmith(多轮轨迹评分) Phoenix evals
2B · 输出 / RAG / 对话质量

如果 Agent 有检索或多轮对话,这层单独测:RAG 三元组(context relevance / groundedness / answer relevance)、输出 faithfulness、多轮对话的 role adherence、记忆保持、对话完整度。

对应工具
RAGAS(最轻,只测 RAG) TruLens(RAG Triad 首创) DeepEval(多轮 ConversationalTestCase + G-Eval 自定义)
2C · 内容安全

幻觉、毒性、偏见、PII 泄露。这是「内容层」的安全,区别于下一层的「对抗层」安全。

对应工具
DeepEval(开箱即用) Giskard Phoenix evals
③
LAYER 3 — 对抗

安全 / 红队

离线 · 定期

常被忽略,但对金融 / DeFi Agent 是必做项。Agent 特别容易中间接 prompt 注入——攻击者把恶意指令藏在 Agent 会读取的外部数据里(行情、链上数据、网页)。

🔥

真实教训:2025 年 3 月,某金融科技公司的 AI Agent 在对账时陷入失控循环,跑了 11 天、烧掉 $47,000 才被发现。这正是缺少红队 + 护栏的代价。

测什么:jailbreak(越狱)、prompt 注入(尤其间接注入)、多轮渐进式越狱(crescendo)、内容安全绕过。

对应工具
Garak(NVIDIA,37+ 漏洞探针) Promptfoo(50+ 漏洞类型,带 CI/CD) PyRIT(Microsoft,多轮 / 多模态,crescendo·TAP) DeepTeam(DeepEval 红队套件)

推荐节奏:上线前必做一次 + 模型升级 / prompt 改动后重跑 + 按月或季定期跑(捕捉新出现的攻击技术)。把注入成功率从 15%→3% 是可量化的进步;模型更新让越狱率从 1%→8% 是必须立刻处理的回归。

④
LAYER 4 — 闸口

运行时护栏

在线 · 实时

前三层都是「事后 / 离线」,这一层是「实时挡在用户前面」。每个生产请求都要过。

原则

护栏必须活在 LLM 之外。

评估是事后兜底,护栏是实时拦截。靠模型自己「克制」不算护栏。

测什么 / 拦什么:实时校验输出格式与内容、注入检测、把危险动作挡下来。

对应工具
Guardrails AI(RAIL 校验) NeMo Guardrails(NVIDIA) Llama Guard / LlamaFirewall(Meta,带对齐检查防注入) Galileo Luna
🛑

对 DeFi Agent 最关键的一条:不可逆动作(下单、转账、调仓)绝不能让 Agent 自动执行——卡在人工审批或 kill switch 之后。这呼应「文件型防火墙 + 人工批准 + 急停开关」的护栏三件套。

跨切面 — 支撑设施

贯穿四层的测试基础设施

这些不属于某一层,而是「怎么把评估跑起来、跑得久」。

落地 — 你的场景

给多 Agent DeFi 平台的推荐配方

LangGraph + 四个分析域(链上数据 / 交易策略 / 风险评估 / 投资研究)。不是四选一,而是「1 个追踪 + 1–2 个评估库 + 红队 + 护栏」。

Recommended Stack

从金字塔底两层先落地,再往上补

  1. 追踪 — Phoenix(本地、数据不出环境)或 LangSmith(你那四个 Agent 调用链最直观)。
  2. Agent 执行评估 — DeepEval 的 6 个 agent 指标(工具 / 轨迹 / 任务完成)+ DAG 做确定性门禁。
  3. RAG / 研究质量 — TruLens RAG Triad(契合重严谨可审计)或 RAGAS(更快)。
  4. 红队 — Promptfoo 或 DeepTeam。金融 Agent 必须测间接注入(它要读链上数据 / 外部行情这类外部源)。
  5. 运行时护栏 — Guardrails AI 之类;关键是把「下单 / 转账」卡在人工审批 / kill switch 后面——对应你关注的「自动化动作边界」。
