## 一、Spec-Driven Development 是什么

> "Give your coding agent a markdown file or a long prompt, explaining exactly what to build, and it implements that spec."

**核心做法**：不再亲手写代码，而是把"Agent 不知道的 context"写成规范（spec）交给它。

---

## 二、SDD 的三大收益

1. **小改 spec 控制大改 code**
   一句"用 SQLite + Prisma"可能影响几百行代码；改成"换 MongoDB"也是同样的放大效应。改 spec 比改 code 高效得多。

2. **消除会话间的 context decay**
   Agent 是无状态的——每次启动加载高质量 context 极其重要。Spec 是跨会话、跨 Agent 的持久锚点。

3. **提高 intent fidelity（意图保真度）**
   写 spec 强迫你定义问题、成功标准、约束、用户流，Agent 才不会瞎填。

---

## 三、SDD 的两层结构

```
项目 Constitution（不可变标准）
   ↓
Feature 开发循环（每个 feature 一个分支）
   plan → implement → verify
```

- **Greenfield**（全新项目）：和 Agent 对话产出 Constitution
- **Brownfield**（遗留代码）：让 Agent 反推现有代码生成 Constitution

---

## 四、什么时候不必写 spec

Andrew 说：**lazy prompting 在简单场景下完全 OK**。但当：
- 项目有显著复杂度
- 你有独特的业务/架构 context、有明确 trade-off 倾向
- Agent 要跑 20–30 分钟（≈传统几小时工作量）

**花 3–4 分钟写清楚 spec，比让它"赌运气"高效得多**。

---

## 五、本课程会教什么

- 写 Constitution（mission / tech stack / roadmap）
- Feature 循环（plan → implement → verify）
- 把工作流封装成可复用的 Agent Skill
- 在遗留项目上引入 SDD
