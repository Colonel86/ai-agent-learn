# L07 验证：人在回路（Verify）

> 原始字幕：`subtitles/L7-eng.vtt`

---

## 一、验证的两个层次

1. **代码 review**：看 diff（git commit view）
2. **运行验证**：跑应用 + 跑测试

> Code review 是程序员几十年的老手艺——只是现在 review 对象从同事变成了 Agent。

---

## 二、Review 的视角：**高层而非低层**

✅ 看：
- 功能是否真按 spec 实现？
- 结构是否合理（如组件划分）？
- 关键决策是否记在 spec 里？

❌ 不看：
- 用了哪个 CSS class
- 变量名好不好

> 高密度的视觉细节让人疲劳；抓"功能是否符合 spec"是 ROI 最高的 review 角度。

---

## 三、发现问题：**改 spec，不直接改 code**

例子：发现 `Home.tsx` 太极简，缺 layout 组件（header / main / footer），还没有 CSS 文件。

**直接改代码？** ❌ 这是 vibe coding 的回头路。

**正确做法**：
```text
Update the spec to require a layout component with header/main/footer
as sub-components in their own files, plus a CSS file.
Then fix the code accordingly.
```

→ Agent 同步更新 spec + code，两者保持一致。

---

## 四、关键概念：Cognitive Debt（认知债）

> "The mental load of tracking what your code is doing and how it has evolved."

Agent 写得飞快，人 review 跟不上 → 认知债积累。
**对策**：
- 每次变更尽量小、可控
- 频繁 commit（小步快跑）
- 用测试做"独立验证轨道"

---

## 五、IDE 操作也要让 Agent 知道

例：用 IDE 的 move tool 把三个子组件拆到独立文件——**手起刀落**很爽。

> 但是！这种"agent 不知道你做了"的改动 → spec 和 readme 可能 drift。

**正确做法**：
```text
I moved the sub-components into separate files using the IDE.
Please scan the project, fix any references in specs/readmes that mention them.
```

> 心法：**任何对仓库的改动，都要让 Agent "知道"**。否则 spec 和 code 就开始漂移。

---

## 六、关于 spec 版本化的开放问题

社区还在演化的话题：
- spec 改动和 code 改动**该不该同分支**？
- 怎么追溯"哪版 spec 产出了哪段 code"？

本课的实用约定：
- **小改 Constitution / Roadmap**（如勾掉一个 checkbox）→ 跟 feature 同分支
- **大改 Constitution** → 单独 replanning 分支

---

## 七、关上 Feature 循环

完成 review + 修复后：
```bash
git commit ...
# 切回 main
git merge feature/hello-hono
```

🎉 第一个 feature 完整跑过了 plan → implement → verify 三段式。
