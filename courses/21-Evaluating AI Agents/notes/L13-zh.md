# L13：把评估带进生产——监控、CI/CD、自我改进

智能体上线后，Trace、评估和 Experiment 这一整套要继续运行——本节讲怎么把开发期的工具自然延伸到生产。

## 回顾：四步从原型到生产

1. **选合适的架构（Architecture）**——匹配用例的 Agent 框架
2. **选关键评估指标（Metrics）**——准确率、延迟、收敛度等
3. **搭评估结构（Evaluation Structure）**——Prompt、工具、数据集
4. **基于数据持续迭代**——分析结果、调 Prompt/逻辑、回到测试

这个循环**横跨开发与生产**：捕捉问题、用真实反馈微调。

## 生产环境会引入哪些新复杂度

进入生产后，简单的单智能体设计往往会扩张：

- **多智能体系统（Multi-agent System）**：智能体之间互相调用
- **多模态系统**：处理文本、图像、音频
- **持续学习系统**：从用户互动中实时学习——手动或自动更新

**新的失败模式**也会冒出来：

- 用户问到开发期从未见过的问题
- 提到系统不认识的新产品/概念
- 调用外部 API 或其他智能体时的级联错误
- A/B 测试和模型切换引入意外回归

> 好消息是，开发期那一整套工具——埋点、评估、Experiment——在生产里**同样有效**，只是被**真实用户数据**喂得更丰满。

## 在生产里收集人工反馈

把每一次用户交互转成可以打标的素材：

- 用户的 **👍/👎** 反馈
- 标注员对问题输出的人工评注

**当评估指标与真实用户反馈不一致**，就是个明显信号：要么你测错了指标，要么逻辑有更深的问题。

## 持续追踪的指标

- **收敛度（Convergence）**：调整后步数变多 = 可能有回归
- **LLM 调用成本与延迟**：直接影响用户体验
- **模型选择的下游效果**：用大模型还是小模型？复杂任务的精度 vs 简单任务的速度

## "黄金数据集（Golden Datasets）"

精选最关键用例 + 已知失败模式，固化为一个**Golden Dataset**：

- 每次 Prompt/逻辑变更前都先在它上面回归
- 把 Experiment 当作**发布闸门（Gate）**——分数不达标就 roll back

## 自我改进闭环

设想一个自我改进的智能体：

1. 自动采集每一次用户交互（成功 + 失败）
2. 把它们持续追加到数据集
3. CI/CD 流水线在新数据集上跑实验，检验新版表现
4. 把新采集的失败案例**作为 Few-shot 示例**塞回 Prompt，让系统**逐步收敛**到真实任务上

这就是**在生产中实践 EDD**：监测新失败模式 → 量化 → 把生产反馈自动回灌评估。

## 小结

本节核心要点：

- **同一套工具贯穿开发与生产**——Trace、人工标注、评估、实验
- 生产里多关注延迟、成本、收敛度和真实反馈
- **Golden Dataset + CI/CD Experiment** 守住质量底线
- 自我改进的飞轮：生产数据 → 数据集 → Few-shot → Prompt → 评估 → 上线

至此你已具备**把智能体从原型推到生产并持续改进**的完整方法论。
