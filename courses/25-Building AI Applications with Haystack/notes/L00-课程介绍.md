## 一、为什么用框架（架构师视角）

Andrew 反复被问的问题：要不要用 AI 框架，还是从零搭？

| 维度 | 从零搭 | 用框架（Haystack） |
|---|---|---|
| 控制粒度 | 完全控制每一步 | 通过抽象牺牲细节控制 |
| 学习价值 | 高 | 中（更偏工程） |
| 维护性 | 随集成数量恶化 | 抽象层挡住底层变化 |
| 迭代速度 | 慢 | 快（branching、looping、可视化等开箱即用） |
| 替换底层 | 大改 | 换一个 Component 即可（如换向量库、换 LLM） |

**架构师判断要点**：当应用要集成多家 LLM / 向量库 / 检索器 / Web 搜索，且预期会换组件时，框架的「公共接口」抽象就是高价值；当应用只用一两个固定 API，框架反而是负担。

## 二、Haystack 的核心理念

只有两个根抽象：

- **Component（组件）**：原子能力单元。Embedder / Retriever / Generator / Converter / Fetcher / Router / Validator …
- **Pipeline（管道）**：把多个 Component 连接成一张图（DAG，必要时含环），数据沿边流动。

> **Tuana 强调**：Haystack 不打算"提供你需要的一切"，而是给一个**统一接口 + 简洁抽象**，让你能**用自定义 Component 扩展框架**。例如对接某个特定 API → 自己写一个 Component 包起来即可。

## 三、本课程的六节学习路径

| 节 | 主题 | 解决什么问题 |
|---|---|---|
| L1 | Building Blocks | 理解 Component / Pipeline / DocumentStore 三件套 |
| L2 | Customized RAG | 用 PromptBuilder + Jinja 模板，把 RAG 写"活"（参数化语言、引用 URL 等） |
| L3 | Custom Components | 用 `@component` 装饰器把任意逻辑封装成 Haystack 组件（Hacker News Summarizer） |
| L4 | Branching Pipelines | 用 `ConditionalRouter` 做分支：检索不到 → fallback 到 Web Search |
| L5 | Self-Reflecting Agents | 用 Pipeline 的循环（`max_loops_allowed`）让 Agent 自我反思 / 迭代修正 |
| L6 | Chat Agent with Function Calling | 用 OpenAI function calling + `BranchJoiner` 把 RAG / 天气查询当工具暴露给 Chat Agent |

## 四、架构脉络速记

从「线性 Pipeline → 分支 Pipeline → 带环 Pipeline → 工具调用循环」是一条逐步走向 Agent 的演化路径。Haystack 的设计意图：**Agent 不是新东西，而是 Pipeline 的一种形态**（带条件、带循环、带工具）。这与 LangGraph 的 "Agent = Graph" 思路同源。
