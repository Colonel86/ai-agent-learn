**尚未覆盖的特性**

**身份验证（OAuth 2.1）**

2025年3月的规范更新中，OAuth 2.1 被加入作为远程服务端的身份验证标准。流程是：客户端请求服务端 → 服务端要求用户认证 → 认证成功后交换令牌 → 客户端发起已认证请求。这是可选特性，但强烈推荐用于远程服务端。本地 Stdio 模式使用环境变量，无需此认证机制。

**根目录（Roots）——客户端暴露的原语**

客户端可以向服务端声明应该操作的 URI 范围（文件路径或 HTTP URL），限制服务端只在特定目录或位置工作，兼顾安全性和聚焦性。

**采样（Sampling）——反向通信**

这是一个特别强大的特性：服务端向客户端请求 LLM 推理，而不是常规的客户端调用服务端。例如，服务端收集服务器日志和性能指标后，直接请求 LLM 分析诊断，再将结果返回——数据无需经过客户端上下文，更安全，也避免上下文窗口污染。这对智能体架构尤为重要。

---

**MCP 的智能体未来**

MCP 的**可组合性**是其最大亮点：客户端可以是服务端，服务端也可以是客户端。这天然支持多智能体架构：

- 应用层 LLM 与一个"协调智能体"通信
- 这个智能体同时是 MCP 客户端和服务端
- 它可以连接更多专业智能体（分析、编程、研究等）
- 所有智能体使用相同协议通信

---

**路线图：统一注册中心**

类似 NPM 或 PyPI，MCP 正在建设统一注册中心，用于发现、验证和版本管理 MCP 服务端，防止恶意代码，并支持**动态发现**——智能体可以在运行时自动查找并连接所需服务端，而无需预先配置。

结合 OAuth 2.1，未来的场景是：用户说"帮我管理 Shopify 店铺" → 智能体查询 Shopify 的 MCP 配置文件 → 发现端点和认证要求 → 用户授权 → 智能体完成任务。

---

**其他待解决问题**

Streamable HTTP 的全面支持、工具命名冲突（多服务端时同名工具的歧义处理）、Sampling 的更广泛采用，以及大规模身份验证与授权机制。
