# Claude 提示工程最佳实践（官方文档中文翻译）

## 一、通用原则

### 1.1 清晰直接

Claude 对清晰、明确的指令响应良好。越精确地说明你的期望，结果越好。如果你想要"超出预期"的行为，**必须明确提出**，而不是依赖模型自行推断。

把 Claude 想象成一位**才华横溢但刚刚入职的员工**——他不了解你的工作规范和流程。

**黄金法则**：把你的提示给一位对任务几乎没有背景知识的同事看，问他能否照着做。如果他会感到困惑，Claude 也会。

实践要点：
- 明确说明期望的输出格式和约束条件
- 当步骤的顺序或完整性很重要时，用编号列表或项目符号提供指令

**示例对比：创建数据分析仪表盘**

```
❌ 效果较差：
"创建一个数据分析仪表盘"

✅ 效果更好：
"创建一个数据分析仪表盘。尽可能包含所有相关功能和交互。
不要局限于基础功能，实现一个完整的版本。"
```

---

### 1.2 提供背景和动机

向 Claude 解释指令背后的**原因**，可以帮助它更好地理解你的目标，给出更有针对性的回答。Claude 足够聪明，可以从解释中举一反三。

**示例对比：格式偏好**

```
❌ 效果较差：
"永远不要使用省略号"

✅ 效果更好：
"你的回复将由文字转语音引擎朗读，所以永远不要使用省略号，
因为引擎不知道如何发音。"
```

---

### 1.3 有效使用示例

示例是引导 Claude 输出格式、语气和结构最可靠的方式之一。几个精心设计的示例（即 few-shot / multishot 提示）能显著提升准确性和一致性。

添加示例时，确保它们：
- **相关性强**：尽量贴近你的实际使用场景
- **多样性足**：覆盖边缘情况，变化足够丰富，避免 Claude 学到非预期的模式
- **结构清晰**：用 `<example>` 标签包裹示例（多个示例用 `<examples>` 标签），让 Claude 能将其与指令区分开

> 💡 3–5 个示例效果最佳。你也可以让 Claude 评估你的示例的相关性和多样性，或基于你的初始集生成更多示例。

---

### 1.4 用 XML 标签结构化提示

XML 标签帮助 Claude 无歧义地解析复杂提示，尤其当提示中混合了指令、上下文、示例和变量输入时。将每类内容包裹在对应标签中（如 `<instructions>`、`<context>`、`<input>`）可减少误解。

最佳实践：
- 在所有提示中使用一致、描述性强的标签名
- 当内容有自然层级时嵌套标签（如文档放在 `<documents>` 中，每份文档用 `<document index="n">` 包裹）

---

### 1.5 给 Claude 指定角色

在 system prompt 中设定角色可以让 Claude 的行为和语气更聚焦。哪怕一句话也能产生明显差异：

```python
import anthropic

client = anthropic.Anthropic()

message = client.messages.create(
    model="claude-opus-4-6",
    max_tokens=1024,
    system="你是一位专注于 Python 的编程助手。",
    messages=[
        {"role": "user", "content": "如何按键对字典列表排序？"}
    ],
)
print(message.content)
```

### 1.6 长上下文提示技巧

处理大型文档或数据密集型输入（20k+ tokens）时，需要仔细构建提示：

**① 将长篇数据放在最前面**

将长文档和输入放在提示顶部，位于查询、指令和示例之上。这在所有模型上都能显著提升性能。

> 📝 测试显示，将查询放在末尾可将响应质量提升高达 30%，在复杂的多文档输入场景中尤为明显。

**② 用 XML 标签组织文档内容和元数据**

使用多个文档时，用 `<document>` 标签包裹每个文档，并附上 `<document_content>` 和 `<source>` 子标签：

```xml
<documents>
  <document index="1">
    <source>annual_report_2023.pdf</source>
    <document_content>
      {{ANNUAL_REPORT}}
    </document_content>
  </document>
  <document index="2">
    <source>competitor_analysis_q2.xlsx</source>
    <document_content>
      {{COMPETITOR_ANALYSIS}}
    </document_content>
  </document>
</documents>

分析年报和竞争对手分析报告，找出战略优势并推荐 Q3 重点方向。
```

**③ 用引用锚定回答**

对于长文档任务，先让 Claude 引用文档中的相关部分，再执行任务。这有助于 Claude 过滤噪音，聚焦关键内容：

```xml
你是一位 AI 医生助理，帮助医生诊断可能的患者疾病。

<documents>
  <document index="1">
    <source>patient_symptoms.txt</source>
    <document_content>{{PATIENT_SYMPTOMS}}</document_content>
  </document>
  <document index="2">
    <source>patient_records.txt</source>
    <document_content>{{PATIENT_RECORDS}}</document_content>
  </document>
</documents>

从患者记录中找出与诊断报告症状相关的引用，放在 <quotes> 标签中。
然后基于这些引用，列出所有有助于医生诊断的信息，放在 <info> 标签中。
```

## 二、输出与格式控制

### 2.1 沟通风格与详细程度

与前代模型相比，Claude 最新模型的沟通风格**更简洁自然**：

- **更直接、更务实**：提供基于事实的进度汇报，而非自我表扬式的更新
- **更对话化**：更流畅、更口语化，减少机械感
- **更简洁**：除非另有提示，可能跳过详细摘要以提高效率

这意味着 Claude 可能在工具调用后直接跳到下一步，而不提供语言总结。如果你希望更清晰地了解其推理过程：

```
完成涉及工具使用的任务后，简要总结你完成的工作。
```

---

### 2.2 格式控制的四种方法

**① 告诉 Claude 做什么，而不是不做什么**

```
❌ "不要在回复中使用 Markdown"
✅ "你的回复应由流畅的散文段落组成"
```

**② 使用 XML 格式标记**

```
"将回复的散文部分写在 <smoothly_flowing_prose_paragraphs> 标签中。"
```

**③ 提示风格与期望输出风格保持一致**

你在提示中使用的格式风格，可能影响 Claude 的回复风格。如果仍遇到格式问题，尝试让提示风格尽量接近期望的输出风格。例如，从提示中去掉 Markdown 可以减少输出中的 Markdown 用量。

**④ 使用详细提示控制具体格式偏好**

如需更精细地控制 Markdown 和格式使用，提供明确的指导：

```xml
<avoid_excessive_markdown_and_bullet_points>
在撰写报告、文档、技术解释、分析或任何长篇内容时，
请用完整段落和句子组成清晰流畅的散文。
使用标准段落换行进行组织，仅对 `内联代码`、代码块（```...```）
和简单标题（### 及 ###）使用 Markdown。
避免使用 **粗体** 和 *斜体*。

不要使用有序列表（1. ...）或无序列表（*），除非：
a) 你要呈现的是真正离散的条目，列表格式是最佳选择；
b) 用户明确要求列表或排名。

不要用项目符号或编号列出条目，而是自然地将它们融入句子中。
此指导尤其适用于技术写作。
使用散文而非过度格式化将改善用户体验。
永远不要输出一系列过短的项目符号。

你的目标是可读、流畅的文本，自然地引导读者理解想法，
而不是将信息碎片化成孤立的要点。
</avoid_excessive_markdown_and_bullet_points>
```

---

### 2.3 LaTeX 输出

Claude Opus 4.6 默认对数学表达式、方程式和技术解释使用 LaTeX。如果你希望纯文本输出：

```
请仅用纯文本格式回复。不要使用 LaTeX、MathJax 或任何标记符号，
如 \( \)、$ 或 \frac{}{}。
所有数学表达式请使用标准文本字符（如用"/"表示除法，"*"表示乘法，"^"表示指数）。
```

---

### 2.4 文档创建

Claude 最新模型在创建演示文稿、动效和视觉文档方面表现出色，具有出色的创意和强大的指令跟随能力，大多数情况下首次尝试即可产出精良、可用的结果。

最佳提示：

```
为 [主题] 创建一个专业演示文稿。在适当的地方加入精心设计的元素、视觉层次和吸引人的动效。
```

---

### 2.5 从预填充响应迁移

从 Claude 4.6 模型开始，**不再支持**在最后一个 assistant turn 进行预填充响应。以下是常见预填充场景的迁移方案：

**① 控制输出格式（如强制 JSON/YAML）**
迁移方案：使用[结构化输出](https://docs.anthropic.com/en/docs/build-with-claude/structured-outputs)功能，或直接告诉模型遵循你的输出格式。

**② 消除前言（如"以下是请求的摘要："）**
迁移方案：在 system prompt 中添加直接指令："直接回答，不要前言。不要以'以下是……'、'基于……'等短语开头。"

**③ 避免不当拒绝**
迁移方案：Claude 现在对拒绝的处理更加准确，清晰的提示应已足够。

**④ 续写被中断的回复**
迁移方案：将续写请求放入 user 消息中："你之前的回复被中断，结束于 `[previous_response]`。请从中断处继续。"

**⑤ 上下文注水和角色一致性**
迁移方案：对于非常长的对话，将之前作为预填充的提醒注入 user turn 中。

## 三、工具使用

### 3.1 明确指定工具使用

Claude 最新模型专为精确指令跟随训练，**需要明确指示才能使用特定工具**。如果你说"能不能建议一些改动"，Claude 有时只会提供建议，而不会实际实现。

```
❌ 效果较差（Claude 只会建议）：
"能帮我建议一些改进这个函数的修改吗？"

✅ 效果更好（Claude 会实际修改）：
"修改这个函数以提升其性能。"
或："对认证流程进行这些修改。"
```

**让 Claude 默认主动采取行动**（加入 system prompt）：

```xml
<default_to_action>
默认情况下，请直接实现改动，而不仅仅是提出建议。
如果用户意图不明确，推断最可能有用的行动并继续执行，
用工具来发现缺失的细节，而不是靠猜测。
尽量推断用户关于是否需要工具调用（如文件编辑或读取）的意图，并据此行动。
</default_to_action>
```

**让 Claude 默认保守，不急于行动**（加入 system prompt）：

```xml
<do_not_act_before_instructions>
除非明确被指示进行修改，否则不要直接实现或修改文件。
当用户意图不明确时，默认提供信息、进行研究并给出建议，而非采取行动。
只有在用户明确要求时，才进行编辑、修改或实现。
</do_not_act_before_instructions>
```

> ⚠️ **注意**：Claude Opus 4.5 和 4.6 对 system prompt 的响应比以前的模型更敏感。如果你之前的提示用了激进的措辞（如"CRITICAL: You MUST use this tool when..."），这些模型可能会过度触发。改用更普通的表述（如"Use this tool when..."）即可解决。

---

### 3.2 优化并行工具调用

Claude 最新模型擅长并行工具执行，会主动：
- 研究过程中同时发起多个搜索
- 一次性读取多个文件以更快地构建上下文
- 并行执行 bash 命令

这种行为易于引导。你可以通过提示将并行调用率提升至约 100%，或降低其激进程度：

```xml
<use_parallel_tool_calls>
如果你打算调用多个工具，且这些工具调用之间没有依赖关系，
请同时并行发起所有独立的工具调用。
优先同时调用工具，而非顺序执行。
例如，读取 3 个文件时，同时发起 3 个工具调用，
将 3 个文件同时读入上下文。
尽可能最大化并行工具调用以提高速度和效率。
但如果某些工具调用依赖于前面调用的结果（如参数值），
则不要并行调用这些工具，而应顺序调用。
永远不要在工具调用中使用占位符或猜测缺失的参数。
</use_parallel_tool_calls>
```

减少并行执行（如需要稳定性）：

```
请在每个步骤之间短暂暂停，顺序执行操作以确保稳定性。
```

## 四、思考与推理

### 4.1 过度思考与过度详尽

Claude Opus 4.6 在较高 `effort` 设置下，会比以前的模型进行**显著更多的前期探索**。如果你的提示之前鼓励模型更彻底地思考，需要针对 Claude Opus 4.6 调整该指导：

- **将笼统的默认指令替换为更有针对性的指令**：不要说"默认使用[工具]"，改为"当[工具]能增强对问题的理解时使用它"
- **删除过度提示**：在以前模型中触发不足的工具，现在可能会正确触发。类似"如有疑问，使用[工具]"的指令会导致过度触发
- **将 effort 作为兜底手段**：如果 Claude 仍然过于激进，降低 `effort` 设置

如果需要抑制过度思考：

```
在决定如何处理问题时，选择一种方法并坚持下去。
除非遇到与你推理直接矛盾的新信息，否则不要反复重新考虑决定。
如果你在两种方案之间权衡，选一个执行到底——如果所选方案失败，之后还可以纠正。
```

---

### 4.2 思考与交错思考能力

Claude 最新模型提供思考能力，对于工具使用后的反思或复杂的多步推理特别有帮助。

**自适应思考（Adaptive Thinking）**

Claude Opus 4.6 和 Sonnet 4.6 使用**自适应思考**（`thinking: {type: "adaptive"}`），Claude 会动态决定何时以及思考多少。它根据 `effort` 参数和查询复杂度来校准思考：高 effort 引发更多思考，复杂查询同样如此。对于不需要思考的简单查询，模型直接响应。

**何时使用自适应思考**：适用于需要智能体行为的工作负载，如多步骤工具使用、复杂编码任务和长周期智能体循环。

引导 Claude 的思考行为：

```
收到工具结果后，在继续之前仔细反思其质量并确定最优的下一步。
用你的思考来根据这些新信息进行规划和迭代，然后采取最佳的下一步行动。
```

控制思考触发频率：

```
扩展思考会增加延迟，只有在确实能显著提升回答质量时才应使用——
通常是需要多步推理的问题。如有疑问，直接回答。
```

**从 extended thinking 迁移到 adaptive thinking**：

```python
# 之前（旧模型的 extended thinking）
client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=64000,
    thinking={"type": "enabled", "budget_tokens": 32000},
    messages=[{"role": "user", "content": "..."}],
)

# 之后（adaptive thinking）
client.messages.create(
    model="claude-opus-4-6",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},  # 可选: max, high, medium, low
    messages=[{"role": "user", "content": "..."}],
)
```

**其他思考技巧：**
- **优先使用通用指令而非规定性步骤**："认真思考"通常比手写的分步计划产生更好的推理
- **Multishot 示例适用于思考**：在 few-shot 示例中使用 `<thinking>` 标签，展示推理模式
- **不开启 thinking 时的手动 CoT**：使用 `<thinking>` 和 `<answer>` 标签将推理与最终输出分离
- **让 Claude 自我检查**：追加"在完成之前，请根据[测试标准]验证你的答案"——对编码和数学任务特别有效

> ⚠️ 禁用 extended thinking 时，Claude Opus 4.5 对"think"及其变体特别敏感。可以改用"consider"、"evaluate"或"reason through"等替代词。

## 五、智能体系统

### 5.1 长周期推理与状态追踪

Claude 最新模型在长周期推理任务中表现出色，具有卓越的状态追踪能力——专注于增量进展，每次稳步推进少量任务，而非一次性尝试所有任务。这种能力在跨多个上下文窗口或任务迭代时尤为突出。

**上下文感知与多窗口工作流**

Claude 4.6 和 4.5 具有上下文感知能力，能够追踪剩余的上下文窗口大小（即"token 预算"），从而更有效地管理上下文。

管理上下文限制的提示：

```
你的上下文窗口在接近上限时会被自动压缩，
允许你从中断处无限继续工作。
因此，不要因为 token 预算顾虑而提前停止任务。
当你接近 token 预算上限时，在上下文窗口刷新之前，
将当前进度和状态保存到记忆中。
始终尽可能持久和自主地完成任务，即使预算即将耗尽也不要提前停止。
```

**多上下文窗口工作流最佳实践：**

1. **第一个上下文窗口使用不同的提示**：用第一个窗口建立框架（编写测试、创建初始化脚本），后续窗口迭代 todo 列表

2. **让模型以结构化格式编写测试**：在开始工作前创建测试，并以结构化格式（如 `tests.json`）追踪。提醒 Claude："删除或编辑测试是不可接受的，这可能导致功能缺失或出现 bug"

3. **设置便捷工具**：鼓励 Claude 创建初始化脚本（如 `init.sh`），优雅地启动服务器、运行测试套件和代码检查器

4. **全新开始 vs 压缩**：清除上下文窗口时，考虑从全新窗口开始。Claude 最新模型非常善于从本地文件系统中发现状态：
   - "执行 pwd；你只能在这个目录中读写文件"
   - "查看 progress.txt、tests.json 和 git 日志"
   - "在继续实现新功能之前，先手动运行一个基础集成测试"

5. **提供验证工具**：随着自主任务时长增加，Claude 需要在没有持续人工反馈的情况下验证正确性

6. **鼓励充分利用上下文**：

```
这是一个很长的任务，清晰规划工作可能很有帮助。
建议你花费完整的输出上下文来完成任务——
只需确保不要在大量未提交的工作时耗尽上下文。
系统性地持续工作，直到任务完成。
```

**状态管理最佳实践：**
- **结构化数据用结构化格式**：测试结果、任务状态等用 JSON 或其他结构化格式
- **进度笔记用非结构化文本**：自由格式的进度笔记适合追踪一般进展
- **用 git 追踪状态**：git 提供了已完成工作的日志和可以恢复的检查点
- **强调增量进展**：明确要求 Claude 追踪进度并专注于增量工作

状态文件示例：

```json
// 结构化状态文件 (tests.json)
{
  "tests": [
    { "id": 1, "name": "authentication_flow", "status": "passing" },
    { "id": 2, "name": "user_management", "status": "failing" },
    { "id": 3, "name": "api_endpoints", "status": "not_started" }
  ],
  "total": 200,
  "passing": 150,
  "failing": 25,
  "not_started": 25
}
```

```
// 进度笔记 (progress.txt)
第 3 次会话进度：
- 修复了认证 token 验证
- 更新了用户模型以处理边缘情况
- 下一步：调查 user_management 测试失败（测试 #2）
- 注意：不要删除测试，这可能导致功能缺失
```

### 5.2 平衡自主性与安全性

没有指导时，Claude Opus 4.6 可能会采取难以撤销或影响共享系统的行动（如删除文件、强制推送、向外部服务发送内容）。如果你希望 Claude 在采取可能有风险的行动前先确认：

```
请考虑你的行动的可逆性和潜在影响。
鼓励你采取本地、可逆的行动（如编辑文件或运行测试），
但对于难以撤销、影响共享系统或具有破坏性的行动，在继续之前请先询问用户。

需要确认的行动示例：
- 破坏性操作：删除文件或分支、删除数据库表、rm -rf
- 难以撤销的操作：git push --force、git reset --hard、修改已发布的提交
- 对他人可见的操作：推送代码、在 PR/issue 上评论、发送消息、修改共享基础设施

遇到障碍时，不要把破坏性行动作为捷径。
例如，不要绕过安全检查（如 --no-verify）或丢弃可能正在进行中的不熟悉文件。
```

### 5.3 研究与信息收集

Claude 最新模型展示出卓越的智能体搜索能力，能够有效地从多个来源查找和整合信息。

复杂研究任务的结构化提示：

```
以结构化的方式搜索这些信息。
在收集数据时，形成几个相互竞争的假设。
在进度笔记中追踪你的置信水平以提高校准性。
定期自我批评你的方法并规划下一步。
更新假设树或研究笔记文件以持久化信息并提供透明度。
系统性地分解这个复杂的研究任务。
```

---

### 5.4 子智能体编排

Claude 最新模型展示出显著改善的原生子智能体编排能力，能够主动识别哪些任务可以委托给专业子智能体，无需显式指令。

如果看到过多的子智能体使用，添加明确指导：

```
当任务可以并行运行、需要隔离上下文或涉及不需要共享状态的独立工作流时，
使用子智能体。
对于简单任务、顺序操作、单文件编辑或需要跨步骤保持上下文的任务，
直接工作而不是委托。
```

---

### 5.5 链式提示（Prompt Chaining）

借助自适应思考和子智能体编排，Claude 已能在内部处理大多数多步骤推理。显式提示链（将任务拆分为顺序 API 调用）在需要检查中间输出或强制特定流水线结构时仍然有用。

最常见的链式模式是**自我修正**：生成草稿 → 让 Claude 根据标准审查 → 让 Claude 基于审查结果改进。每一步都是独立的 API 调用，可以在任意节点记录、评估或分支。

---

### 5.6 减少智能体编码中的文件创建

Claude 最新模型在编码时可能会创建新文件用于测试和迭代（用文件作为"临时草稿"），这对智能体编码场景有好处，但如果你希望减少新文件：

```
如果你为迭代创建了任何临时文件、脚本或辅助文件，
请在任务结束时通过删除这些文件来清理。
```

---

### 5.7 过度设计（Overeagerness）

Claude Opus 4.5 和 4.6 有**过度设计的倾向**——创建多余文件、添加不必要的抽象层、构建未被要求的灵活性。

解决方案：

```xml
避免过度设计。只做被明确要求或明显必要的改动。保持解决方案简单且专注：

- 范围：不要添加未被要求的功能、重构代码或做"改进"。Bug 修复不需要清理周围代码，
  简单功能不需要额外的可配置性。

- 文档：不要给你没有修改过的代码添加文档字符串、注释或类型注解。
  只在逻辑不自明的地方添加注释。

- 防御性编码：不要为不可能发生的场景添加错误处理、回退或验证。
  信任内部代码和框架保证。只在系统边界（用户输入、外部 API）处验证。

- 抽象：不要为一次性操作创建辅助函数、工具或抽象。
  不要为假设的未来需求设计。正确的复杂度是当前任务所需的最小复杂度。
```

---

### 5.8 避免只关注通过测试和硬编码

为防止 Claude 只顾通过测试而牺牲通用性：

```
请使用可用的标准工具编写高质量、通用的解决方案。
不要创建辅助脚本或变通方案。
实现一个对所有有效输入都能正确工作的解决方案，而不仅仅是测试用例。
不要硬编码值或创建只适用于特定测试输入的解决方案。

专注于理解问题需求并实现正确的算法。
测试是用来验证正确性的，而不是定义解决方案的。
提供遵循最佳实践和软件设计原则的、原则性的实现。

如果任务不合理或不可行，或者某些测试有误，请告知我，而不是绕过它们。
解决方案应该健壮、可维护、可扩展。
```

---

### 5.9 减少智能体编码中的幻觉

```xml
<investigate_before_answering>
永远不要对你没有打开过的代码进行推测。
如果用户提到了某个特定文件，你必须先读取该文件再回答。
在回答关于代码库的问题之前，确保先调查并读取相关文件。
除非你确信答案正确，否则在调查之前永远不要对代码做任何断言——
给出有根据、无幻觉的回答。
</investigate_before_answering>
```

## 六、特定能力技巧

### 6.1 改进的视觉能力

Claude Opus 4.5 和 4.6 具有改进的视觉能力，在图像处理和数据提取任务中表现更好，尤其在上下文中有多张图片时。这些改进也延伸到计算机使用场景。

**提升图像理解的技巧**：给 Claude 一个裁剪工具，让其能"放大"图像的相关区域。测试显示，当 Claude 能够缩放图像时，在图像评估中有稳定的性能提升。

---

### 6.2 前端设计

Claude Opus 4.5 和 4.6 擅长构建复杂的真实世界 Web 应用，具有强大的前端设计能力。但没有指导时，模型可能会默认使用通用模式，产生用户所说的"AI 糊弄美学"。

以下 system prompt 片段可鼓励更好的前端设计：

```xml
<frontend_aesthetics>
你倾向于生成通用的、"符合分布"的输出。
在前端设计中，这会产生用户所说的"AI 糊弄美学"。
避免这种情况：创建令人惊喜和愉悦的、有创意的、与众不同的前端。

关注：
- 字体排版：选择美丽、独特、有趣的字体。避免 Arial 和 Inter 等通用字体，
  选择能提升前端美感的独特字体。
- 色彩与主题：坚持统一的美学风格。使用 CSS 变量保持一致性。
  主色调配合鲜明强调色，优于平淡分散的配色方案。
  从 IDE 主题和文化美学中获取灵感。
- 动效：使用动画制作效果和微交互。优先使用纯 CSS 解决方案。
  专注于高影响时刻：一个精心编排的页面加载（配合交错的 animation-delay）
  能比分散的微交互带来更多愉悦感。
- 背景：创造氛围和深度，而非默认使用纯色。
  叠加 CSS 渐变、使用几何图案，或添加与整体美学匹配的上下文效果。

避免通用的 AI 生成美学：
- 过度使用的字体系列（Inter、Roboto、Arial、系统字体）
- 俗气的配色方案（尤其是白色背景上的紫色渐变）
- 可预见的布局和组件模式
- 缺乏特定场景个性的千篇一律的设计

进行创意诠释，做出针对特定场景真正设计过的出人意料的选择。
</frontend_aesthetics>
```

## 七、迁移注意事项

从早期版本迁移到 Claude 4.6 时：

1. **明确说明期望的行为**：具体描述你希望在输出中看到的内容

2. **使用修饰词增强输出质量**：加入鼓励 Claude 提高质量和详细程度的修饰词。例如，将"创建一个分析仪表盘"改为"创建一个分析仪表盘，尽可能包含所有相关功能和交互，超越基础功能，实现完整版本"

3. **明确请求特定功能**：动效和交互元素需要明确请求

4. **更新思考配置**：Claude 4.6 使用自适应思考（`thinking: {type: "adaptive"}`），而非带 `budget_tokens` 的手动思考。使用 effort 参数控制思考深度

5. **从预填充响应迁移**：从 Claude 4.6 模型开始不再支持预填充。参见上文"从预填充响应迁移"章节

6. **调整反懒惰提示**：如果你之前的提示鼓励模型更彻底或更激进地使用工具，请降低该指导力度。Claude 4.6 模型更加主动，可能对旧模型所需的指令过度触发

### Sonnet 4.5 → Sonnet 4.6 迁移

Claude Sonnet 4.6 默认 effort 级别为 `high`，而 Sonnet 4.5 没有 effort 参数。

**推荐设置：**
- **medium**：适用于大多数应用
- **low**：适用于高吞吐量或对延迟敏感的工作负载
- 在 medium 或 high effort 时设置较大的最大输出 token 预算（推荐 64k tokens）

**何时使用 Opus 4.6 而非 Sonnet 4.6**：对于最难、最长周期的问题（大规模代码迁移、深度研究、扩展的自主工作），Opus 4.6 是正确选择。Sonnet 4.6 针对快速交付和成本效益进行了优化。

**不使用 extended thinking 时**：

```python
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=8192,
    thinking={"type": "disabled"},
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": "..."}],
)
```

**使用 extended thinking 时（迁移到 adaptive thinking）**：

```python
# 迁移后（adaptive thinking）
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "..."}],
)
```

自适应思考特别适合：
- **自主多步骤智能体**：编码智能体、数据分析流水线
- **计算机使用智能体**：Claude Sonnet 4.6 在计算机使用评估中使用自适应模式达到了业界最佳准确率
- **双峰工作负载**：简单查询跳过思考，复杂查询深度推理
