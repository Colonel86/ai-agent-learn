# L4 评测反思工作流（Evaluating the Impact of Reflection）

## 为什么要评测

反思通常能改善输出，但它也带来代价：

- 多一次 LLM 调用 → 延迟变长、成本上升。

所以在把"加反思"作为最终方案前，要**量化**它带来的提升到底有多少。

## 客观评测案例：数据库查询（SQL 生成）

场景：零售店问答系统。

- 用户问"哪种颜色的商品总销售额最高？"
- LLM 生成一段 SQL → 跑在数据库上 → 拿到结果 → LLM 回答用户问题。

**加反思版本**：第一版 SQL 不直接执行，先让另一个（或同一个）LLM 反思并改写 SQL，再执行。

### 评测方法

1. 收集 10–15 条问题，每条配一个**人工标注的正确答案**（ground truth）：
   - "2025 年 5 月卖了多少件商品？"
   - "库存中最贵的商品是什么？"
   - "店里一共有多少种款式？"
2. 分别跑"无反思"和"有反思"两条流水线。
3. 数对错，算正确率。

讲者的示例数字：

| 方案 | 正确率 |
|---|---|
| 无反思 | 87% |
| 有反思 | 95% |

→ 反思带来有意义的提升。

### evals 的另一个用途：调 prompt

一旦评测脚手架搭好，就可以快速试验：

- 改写反思 prompt（加一条"让 SQL 跑得更快"或"让查询更清晰"）。
- 调整初始生成 prompt。
- 每次跑同一套 evals，看正确率变化。

**有 evals 才能系统化地在多个 prompt 候选中选优**，否则只能凭感觉。

## 主观评测案例：图表生成

回到 L3 的例子——堆叠柱状图 vs 分组柱状图，"哪个更好"是主观判断，没有 0/1 的标准答案。

### 思路一：LLM-as-judge（成对比较，效果不佳）

把两张图同时喂给多模态 LLM，问"哪个更好"。

**常见坑**：

1. **结果对 prompt 的措辞高度敏感**。
2. **与人类专家的排序相关性不强**。
3. **位置偏置（position bias）**：很多 LLM 倾向于偏好第一个选项（少数偏好第二个）。讲者本人接触的大多数模型都有"先入为主"的倾向。

### 思路二：用 rubric 单项评分（更稳）

不做两两比较，而是**单独打分**，并把评分拆成清单：

- 图是否有清晰的标题？
- 坐标轴标签是否齐全？
- 图表类型是否合适？
- ……（5–10 条这样的小项）

**关键技巧**：不要让 LLM 给"1–5 分"或"1–10 分"——它在这种连续量表上**校准很差**。改成 **N 个 0/1 二元判断**，再把分数加起来，得到 0–N 的总分。这样结果**一致性显著更好**。

### 应用流程

1. 准备 10–15 条用户查询（不同的可视化需求）。
2. 生成"无反思"图组 vs "有反思"图组。
3. 用上面的 rubric 给每张图打分。
4. 比较两组平均分。

后续调 prompt（无论是初始生成还是反思），都重跑这套评测就能量化新版是否更好。

## 客观 vs 主观评测：实务总结

| 任务类型 | 评测方式 |
|---|---|
| 有明确正确答案（SQL 查询、数学题、分类） | **代码化客观评测**：ground truth + 自动比对，最容易管理 |
| 答案没有唯一正解（图表好看程度、文风、创意） | **LLM-as-judge + rubric**：需要花心思设计评分量表，校准更费力 |

## 核心 takeaway

- **会做 evals 是搭好 agentic 工作流的硬功夫**——后续课程会反复回到这点。
- 反思值不值得加上、prompt 怎么调，都靠 evals 给出答案。
