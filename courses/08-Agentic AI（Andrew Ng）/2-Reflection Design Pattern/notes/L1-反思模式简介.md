# L1 反思设计模式简介（Reflection to Improve Outputs）

## 核心思想

人类写完邮件后会重读、修改；LLM 也可以用同样的方式改进自己的输出。这就是**反思设计模式（Reflection）**——实现起来出乎意料地简单，却在很多应用中带来明显提升。

## 典型工作流

最朴素的形式是把同一个 LLM 调用两次：

1. **第一次调用**：用 prompt 让模型生成初稿（email v1 / code v1）。
2. **第二次调用**：把初稿喂回去，配一个新的 prompt 让它"反思并改写"，得到 v2。

可以是同一个模型，也可以是不同模型。

## 示例一：写邮件

- 快速打字写出的初稿往往不够好：日期写得模糊（"下个月"）、有错别字、忘记署名。
- 自己重读时会发现这些问题并改写："Tommy，5–7 号你有空吃饭吗？……"
- LLM 走完全一样的流程：先生成，再反思，再改写。

## 示例二：写代码

- 让 LLM 写一段实现某功能的代码 → v1。
- 把 v1 交给同一个或另一个 LLM，让它"检查 bug 并改写" → v2。
- **模型选择的小技巧**：不同模型各有强项。Reasoning / Thinking 类模型擅长找 bug，所以可以用普通模型直接生成初稿，用推理模型做反思。

## 关键洞察：外部反馈让反思更强大

仅靠模型自己反思已经有用，但如果能引入**外部信息**（来自 LLM 之外的新信息），反思的效果会显著提升。

代码场景中最简单的外部反馈就是**直接运行代码**：

- v1 跑出来报语法错误。
- 把代码 + 报错日志一起喂回 LLM，让它基于这些"额外信息"重写。
- v2 通常质量大幅提升，远好于纯靠模型自反思。

## 要记住的两点

1. 反思不是魔法，不会让 LLM 100% 正确，但通常能带来"温和"的性能提升。
2. **只要有机会接入外部信息，反思就会变得更强**——这是后续模块会反复回到的设计原则。
