# L1 规划设计模式（Planning Workflow）

## 本模块定位

最后一个模块，讲**高度自主 agent** 的两个设计模式：

1. **Planning（规划）**——不再硬编码步骤顺序，让 LLM 自己决定怎么做。
2. **Multi-agent（多智能体）**——多个 agent 协作。

## 核心思想

之前的 agentic 工作流，步骤顺序基本由开发者预先规定。Planning 让 LLM **自己制定执行步骤**——对复杂、多样化的任务更灵活。

## 案例一：太阳镜零售客服 agent

数据库里有库存信息。用户问："你们有圆框、库存中、低于 100 美元的太阳镜吗？"

这条 query 需要**三步组合**：先筛圆框 → 看库存 → 看价格。

### 给 agent 的工具集

- `get_item_descriptions` —— 查商品描述（用于判断款式）
- `check_inventory` —— 查库存
- `process_item_returns` —— 处理退货
- `get_item_price` —— 查价格
- `check_past_transactions` —— 查历史交易
- `process_item_sale` —— 处理销售

### 让 LLM 制定计划

prompt 告诉 LLM："你可以使用以下工具……请返回一个分步骤计划。"

LLM 可能输出：

1. 用 `get_item_descriptions` 找出圆框款。
2. 用 `check_inventory` 判断哪些有货。
3. 用 `get_item_price` 筛 < $100。

### 逐步执行

把第 1 步的文字 + 上下文喂给 LLM → 它真的去调用 `get_item_descriptions`。
拿到结果 → 拼上第 2 步指令 → 再调 LLM 执行。
依此类推 → 最后 LLM 综合所有中间结果给用户回答。

> 实际 LLM 写的计划往往**比这几行简单描述更详细**。但骨架不变：先写计划，再分步执行。

### 为什么强大

同一个 agent 还能应对完全不同的 query，例如"我想退掉之前买的金框，但留下金属框"——LLM 会自己规划出一条不同的步骤序列（查历史交易 → 定位金框 → 调用退货）。**不需要为每种 query 硬编码流程**。

## 案例二：邮件助手

需求："请帮 Bob 在纽约的晚餐邀请回个'我会参加'，然后归档这封邮件。"

工具：`search_email`、`move_email`、`delete_email`、`send_email`。

LLM 制定的计划：

1. `search_email` 找 Bob 关于晚餐 + 纽约的邮件。
2. 生成并 `send_email` 确认参加。
3. `move_email` 把原邮件移到归档。

执行同样是**逐步骤喂给 LLM**，每步附上必要上下文。

## 现状评价

- **高度 agentic 的编程助手**里 planning 已经非常成熟好用——能为一个复杂项目列出"先建 A 组件、再建 B 组件"的清单，逐项打勾完成。
- 其它领域 planning 还在**实验阶段**，普及度有限。
- 主要难点：**控制性差**——开发者运行前不知道 LLM 会出什么计划。给了灵活性，但也牺牲了可预测性。
