# L3 用代码做规划（Planning with Code Execution）

## 核心思想

不让 LLM 输出 JSON 计划再一步步执行，而是**让 LLM 直接写一段代码**——代码本身就把多个步骤串起来了：调函数 A → 拿结果 → 调函数 B → ……执行这段代码就完成了整个计划。

## 案例：咖啡机销售数据问答

数据存在 CSV 表里：日期、品类、价格……

### 方案一：给 LLM 一堆"细工具"

提供工具：`get_column_max`、`get_column_mean`、`filter_rows`、`get_column_min`、`get_column_median`、`sum_rows` ……

**问题在哪？**

- 用户问"热巧克力哪个月销量最高？"——可以用这些工具拼出来，但要：筛 1 月 → 算统计；再筛 2 月 → 再算；……一直到 12 月 → 再取最大值。**笨重且容易出错**。
- 用户问"上周有多少笔不重复的交易？"——现有工具拼不出来 → 加 `get_unique_entries`。
- 用户问"最后 5 笔交易金额？"——又得加一个工具。
- ……新 query 不停来，**工具不停加**。脆弱、低效、edge case 永远处理不完。

### 方案二：让 LLM 写 Python 代码

prompt："请写代码解答用户问题，把 Python 代码放在 `<execute_python>...</execute_python>` 中。"

LLM 给出的代码可能：

1. 用 `pandas` 加载 CSV。
2. 解析日期列。
3. 排序、筛选、取最后 5 行、取价格列……

**关键观察**：代码本身的步骤序列就是一份"计划"——每一行注释就像一个 step。

### 为什么强大

- Python + pandas/numpy 等库自带**成百上千个函数**。
- LLM 在训练数据里**见过海量代码示例**，知道什么场景用哪个函数。
- 等价于一下子获得了"几千种工具"的工具库——而且 LLM 早就熟悉它们的用法。
- 任意复杂的数据处理都能现场组合出来。

## 第二个例子："上周有多少笔不重复的交易？"

LLM 写出的 4 步代码大致：

1. 读 CSV，解析日期列。
2. 定义时间窗口（上周）。
3. 过滤 + 去重。
4. 计数返回。

每一步都用一行 pandas 表达——计划即代码，代码即执行。

## 研究证据

引用 Xinyao Wang 等人的论文（讲者改编自该图）：

> Code-as-Action > JSON-as-Plan > Plain-text-as-Plan

在多个模型和多类任务上，**让 LLM 写代码并直接执行，效果优于先写 JSON 计划再翻译执行；后者又优于纯文本计划**。

## 安全提醒

执行 LLM 生成的代码 = 之前在 Tool Use 模块讨论过的风险（`rm *.py` 事故那种）。生产环境建议放沙箱（Docker / E2B）。

> 讲者坦言：很多开发者实际并不用沙箱——风险大小看具体应用。

## 适用范围

- **适合**：任务本身能用代码自然表达（数据处理、数学计算、文件操作、API 调用串联……）。
- **不适合**：需要调用一组高度定制的领域工具——这时还是回到"工具 + JSON 计划"的范式更可控。

## 规划模式的整体小结

- **agentic 编程助手**是 planning 落地最成熟的场景：自动列任务清单 → 逐项构建 → 边建边测，能完成相当复杂的项目。
- 其它领域 planning 仍在快速发展，**主要代价是可控性下降**：开发者不能预知 LLM 会出什么计划。
- 让出一部分控制，换来覆盖**更广任务空间**的能力——这就是 planning 的核心权衡。
