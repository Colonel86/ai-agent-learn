# L3 更多错误分析案例（More Error Analysis Examples）

错误分析这件事，**多看几个例子才能练出直觉**。本讲走两个新场景：发票处理 和 客户邮件回复。

## 案例一：发票处理——是 PDF→text 错了，还是 LLM 错了？

回顾流水线：PDF → PDF-to-text → LLM 抽取 4 个字段 → 写入数据库。

L1 已知问题：**到期日期经常错**。但错在哪一步？

### 可能元凶

- **PDF→text 阶段**：文本提取本身就把日期搞乱了，连人看了输出文本都看不出哪个是到期日。
- **LLM 阶段**：文本完全正常，但 LLM 把"开票日期"当成了"到期日期"，挑错了那一个。

### 错误分析做法

1. 找 10–100 张**确认日期错了**的发票（满意的不看）。
2. 对每张人工判断：
   - PDF→text 输出已经看不出真实日期了？→ 记 PDF→text 出错。
   - 文本里到期日清晰可辨，但 LLM 挑错了？→ 记 LLM 出错。
3. 表格统计两类各占多少。

### 讲者举例的结论

LLM 阶段贡献的错误**远多于** PDF→text。所以应该**优先调 LLM 抽取的 prompt**，而不是去优化 PDF 解析。

> 提醒：一个样本可能两步都有错，所以**列百分比加起来未必等于 100%**。

### 这种分析为什么值得做

不做的话，团队很容易花几周几个月去调 PDF 解析，最后发现根本不是瓶颈。

## 案例二：客户邮件回复 agent

流水线：客户邮件 → LLM 生成数据库查询 → 查数据库 → LLM 起草回复 → 人工审核。

### 可能元凶

1. LLM 写的查询不对——拿不到正确订单信息。
2. 数据库里数据本身就坏。
3. 查询和数据都没问题，但 LLM 起草的邮件写得不行。

### 错误分析做法

挑一批**最终回复不满意**的样本，逐个判断错在哪步：

| 邮件 # | 查询是否正确 | 数据库是否有数据 | 邮件起草是否合格 |
|---|---|---|---|
| 1 | 错（查错了表）| — | — |
| 2 | 对 | 错（数据本身有错）| 还连带写错了 |
| …… | | | |

### 讲者举例的结论

- 查询写错占了大约 75% 的错误。
- 数据库数据本身错占小部分。
- 邮件起草错约 30%。

→ **第一优先级：改进 LLM 写查询的部分**（不只是提示词，可能要给更多 schema 信息、few-shot 例子等）。
→ 第二优先：改进起草邮件的 prompt。

### 关键洞察

> 系统大部分时候是好的；在"少数出错"的样本里，**75% 都来自同一个组件**——这就是黄金诊断信息。没有这种统计，凭感觉调，效率会差好几倍。

## 小结

错误分析的套路在不同场景里其实一致：

1. **只看错的样本**。
2. **拆到组件级**判断每一步的对错。
3. **数出频次**，把判断从"感觉"升级为"数据"。
4. **决定下一步在哪个组件投入精力**。
