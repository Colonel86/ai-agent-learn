# L2 错误分析入门（Error Analysis）

## 为什么要做错误分析

agentic 工作流由很多组件拼成。同样的开发时间，**投在哪个组件上**差别巨大：

- 选对：几周改完，整体性能跳一个台阶。
- 选错：花了几个月，发现对整体几乎没影响。

讲者的观察：**能否做有纪律的错误分析**是高效团队和低效团队最大的区分点之一。

## 直觉做决定 vs 错误分析做决定

回到研究 agent 的"漏关键点"问题。链路上几乎每个组件都可能是元凶：

- 第一个 LLM 生成的搜索词不好？
- web search 引擎本身质量差？
- 给 LLM 一堆搜索结果，它选的 top 5 不好？
- web fetch 失败？
- 拿到网页后 LLM 忽略了关键内容？

凭直觉挑一个组件去做——**有时蒙对，有时白干几个月**。错误分析的目的就是把这件事变得可量化。

## 工具：trace 与 span

- **trace**：一次完整运行中，所有中间步骤的输出**合在一起**。
- **span**：单个步骤的输出。

> 这两个词来自计算机可观测性（observability）领域。课程主要用 trace。

读 traces 就是看每一步中间产物，找出**哪一步明显比人类专家做得差**。

## 案例走一遍：研究 agent

输入 query："写一篇关于黑洞科学最新进展的文章"。

### Step 1：检查搜索词

LLM 输出了 `black hole theories Einstein`、`Event Horizon Telescope`…… → 让专家看，结论：合理，**搜索词没问题**。

### Step 2：检查搜索结果

返回的 URL 里有一条：`小学生声称破解 30 年黑洞谜题 — Astro Kid News`。明显不是科研级来源。

通览全部返回结果 → 太多博客/科普文章，**缺少科学论文**。问题出在 web search 这一步。

### Step 3：检查"选 top 5"

LLM 从已有候选里选了 Astro Kid News、SpaceBot 2000……

**这一步不算它的错**——给它的候选全是非严肃文章，没人能从里面选出好的。**评估时要排除"输入本身就烂"的连带责任**。

## 把错误分析做系统化：用表格统计

只看几个例子是"直觉"。要更可靠，应当：

1. 挑出**最终输出不满意的样本**（满意的先放一边——这是"error analysis"的字面意思）。
2. 对每个样本，逐组件标注"这一步是否明显差于人类专家"。
3. **多个组件可同时出错**（不互斥）。
4. 在表格里数出每个组件的出错占比。

讲者示例数字：

| 组件 | 不满意比例 |
|---|---|
| 搜索词 | 5% |
| 搜索结果 | 45% |
| ……（其它）| …… |

→ 结论清晰：**先去改 web search**，而不是其它组件。如果搜索词只 5% 出问题，但很怀疑搜索词其实拖累了搜索结果，再回头细看；否则就专心调 web search 引擎、参数、日期范围等。

## 实操要点总结

1. **养成读 trace 的习惯**：建完原型先翻几个 trace，对每步质量有体感。
2. **用表格做系统统计**：从"感觉"升级到"数字"。
3. **结合"错误频次 × 改进想法的可行性"决定优先级**：
   - 高频出错 + 你有明确改法 → 立刻投入。
   - 高频出错 + 完全没思路 → 优先级反而降低。
4. **错误分析是抗"投错地方"的关键武器**：复杂系统里随便挑个方向能做几个月还没产出，错误分析帮你避免这种浪费。
