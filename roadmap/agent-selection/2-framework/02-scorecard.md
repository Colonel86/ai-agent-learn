# 02 · 加权评分卡:量化对比候选

> 目的:当决策树给出 ≥2 个候选时,用统一维度**加权打分**,把"手感"变成"可解释的分数"。
> 用法:① 按业务调权重 → ② 给每个候选每维打分(1-5) → ③ 加权求和 → ④ 高分者首选,但**看清它在你最重的维度上是否丢分**。

---

## 一、十个评分维度(定义 + 怎么打分)

| # | 维度 | 含义 | 打 5 分的样子 | 打 1 分的样子 |
|---|---|---|---|---|
| D1 | **控制力 / 透明度** | 能否看透并干预每一步 | 完全控制循环/prompt/状态 | 黑盒,难插手 |
| D2 | **编排表达力** | 能表达多复杂的流程 | 状态+分支+循环+多agent全支持 | 只能线性 |
| D3 | **生态 / 集成广度** | 现成组件、连接器、模型支持 | 几乎都有现成集成 | 啥都要自己写 |
| D4 | **学习曲线** | 上手与心智负担(分越高越易学) | 半天能跑通 | 概念多、文档差 |
| D5 | **可观测性 (tracing)** | 能否打 trace、对接观测平台 | 原生 LangSmith/Phoenix/Langfuse | 只能 print |
| D6 | **Eval 友好度** | 能否接评估框架做回归 | 官方 eval + 易接第三方 | 无从测起 |
| D7 | **生产部署 / Serving** | 上线运维成熟度 | 官方部署方案 + 横向扩展 | 只能自己包 API |
| D8 | **成本 / 开销** | 框架引入的 token & 运行开销(分越高越省) | 几乎零额外开销 | 大量隐藏 prompt/调用 |
| D9 | **成熟度 / 社区** | 稳定性、活跃度、踩坑可搜 | 大社区、API 稳定 | 小众、频繁 break |
| D10 | **可移植性 / 反锁定** | 换模型/换底层的代价(分越高越自由) | 换组件即可 | 绑死单一厂商 |

> 打分主观没关系,**关键是同一套尺子量所有候选**,且把理由写在备注里。

## 四、加权计算示例

场景:**生产严肃系统**,候选 = LangGraph vs Haystack。用上表生产权重:

```
加权分 = Σ(维度原始分 × 维度权重) / 100
```

| 维度(权重) | LangGraph 原始×权重 | Haystack 原始×权重 |
|---|---|---|
| D1(12) | 4×12=48 | 4×12=48 |
| D2(15) | 5×15=75 | 4×15=60 |
| D3(10) | 4×10=40 | 4×10=40 |
| D4(6)  | 2×6=12  | 3×6=18 |
| D5(15) | 5×15=75 | 3×15=45 |
| D6(12) | 5×12=60 | 3×12=36 |
| D7(15) | 5×15=75 | 4×15=60 |
| D8(6)  | 3×6=18  | 4×6=24 |
| D9(6)  | 4×6=24  | 4×6=24 |
| D10(3) | 4×3=12  | 4×3=12 |
| **合计/100** | **4.39** | **3.67** |

> 结论:生产严肃场景且看重编排+可观测+部署 → **LangGraph 胜**。但若团队完全不熟、且业务是 RAG-first,D4/场景因素会把天平拉回 Haystack——**这就是为什么评分后还要过 `04` 场景手册交叉验证**。
