# L2 · 护栏的定义、位置与实现技术（Input Guard / Output Guard 总框架）

> 课程：Safe and reliable AI via guardrails（DeepLearning.AI × GuardrailsAI）
> 本课任务：L1 复现了 RAG chatbot 的四种不可靠行为，本课给出解药的**概念总框架**——回答三个问题：guardrail 的精确定义是什么、放在 LLM 调用链的哪个位置、内部用什么技术实现；最后落到护栏提升可靠性的三重机制。

## 0. 衔接：从"看到问题"到"验证一切"

L1 展示了会拖垮 POC 的各种 unreliable LLM behavior。本课的主张一句话：AI guardrails 通过**验证与核实（validating and verifying）应用做的每一件事**来缓解这些问题。

## 1. 定义：护栏 = 对 LLM 调用的二次检查

**Guardrails 是二次检查/验证（secondary checks or validations），确保一次 LLM 调用的输入或输出符合预期（as expected）。**

"预期"是一条从平凡到复杂的光谱：

| 复杂度 | 预期（expectation）示例 |
|---|---|
| 很平凡 | LLM 输出格式对不对？字符串有没有按要求切成 list？ |
| 中等 | JSON 输出是否符合我预期的 schema？ |
| 很复杂 | 输出没有幻觉？没有检测到 jailbreak 尝试？ |

不管检查什么，本质是同一句话：**不盲目信任 LLM 会做对（not blindly trusting the LLM to do the right thing），而是显式验证（explicitly verifying）你对这次调用的预期 / 成功标准**。

## 2. 位置：在裸 LLM 调用链上加两道闸

L1 的 RAG chatbot 要推向 production-ready，护栏加在哪？先看**裸调用链**：prompt（含 RAG 检索结果、system prompt 等全部拼进一个盒子）→ LLM 做 next-token prediction → 输出回给应用。

护栏版调用链在前后各加一道**显式验证套件（verification suite）**：

```
prompt（用户输入+检索+system prompt）
        │
        ▼
  [Input Guard]  ← 输入验证套件，内含多个 guardrail
        │ 通过
        ▼
       LLM
        │
        ▼
  [Output Guard] ← 输出验证套件，内含多个 guardrail
        │ 通过
        ▼
   返回给 GenAI 应用
```

每道 guard 内含**若干 guardrail**，各自显式校验一条预期，按你在建什么而定：

| 侧 | 典型检查（预期） |
|---|---|
| **Input Guard**（进 LLM 前） | prompt 含 PII 就不发出去；问题是否 off-topic、不属于 chatbot 的用途；是否检测到 jailbreak 尝试 |
| **Output Guard**（出 LLM 后） | 文本里有没有幻觉；响应是否跑题；有没有 profanity / 不安全输出 |

先确认 prompt 里不含会让应用不可靠的源头，才放行给 LLM；LLM 的输出同样先过输出验证套件，才回给应用。

> **对比 7-safety-guardrails.md**：本课的 Input/Output Guard 正是选型文档"五段护栏链路"里的 **① 输入护栏、② 输出护栏**两个卡点——课程对象是 chatbot，所以没展开 ③ 工具权限边界、④ 沙箱（那是 Agent 有副作用后才升级的卡点）。可迁移的骨架是一致的：**卡点是位置、guardrail 是检查器，一个卡点可以挂一组检查器**。

## 3. 内部实现：三类技术 + 组合拳

一个 guardrail 在 under the hood 可能是什么？三类技术，能力与成本递增：

| 实现 | 是什么 | 典型检查 |
|---|---|---|
| **规则引擎** | 最简单，如 regex 规则 | LLM 输出里是否出现某类文本 |
| **小型微调 ML 模型** | 在 guardrail **进程内**运行的 fine-tuned 小模型 | 文本里的命名实体（NER）、特定话题、脏话输出等 |
| **二次 LLM 调用** | 再调一次 LLM 当裁判 | "给这个输出打分：它多好地回答了用户问题 / 多符合某些规则" |

很常见的形态是**以上技术的组合（combination）**——mix and match，才能精确捕捉你想要的 LLM 应用行为。

> **对比 Red Teaming LLM Applications 课**：本课在 Input Guard 里列的"jailbreak 检测"，正是红队课攻方视角的**防守镜像**——红队用规则变形、提示注入系统性地找洞（发布前、离线），护栏把同类检测器搬到**运行时热路径**上逐请求拦截。攻防两侧共享同一套失效分类，先学攻再学防，检查器清单就是现成的。

## 4. 护栏如何提升可靠性：三重机制

回到 L1 的问题——护栏怎么缓解现代 GenAI 应用里的 unreliable behavior？

1. **显式验证不可违背的约束（inviolable constraints）**：那些错一次代价太高的规则，如 **never leak PII**——泄露有真金白银的罚款和风险。护栏保证你不是"依赖 AI 系统自觉"，而是显式核实这条约束从未被违反。
2. **度量不良行为的发生率**：哪怕只挂了几个护栏，也能持续统计"LLM 拒答了多少次""某类话题被问了多少次"。把"我的 chatbot 帮客户解决问题解决得怎么样"这种**很难度量的大问题，拆解成一组小检查**，拼出系统整体表现。
3. **包住多步应用的级联误差（cascading error）**：面向 agentic / multi-step 应用尤其关键——给每个 AI 模型能做的事**画一个 bounding box**，串联多个 LLM 调用时误差被逐级包住，不会复利式放大。

三者合起来：**限制 GenAI 应用的 worst-case risk**。

> **架构师视角**：这三重机制其实是护栏的三个不同身份——**合规闸门**（机制一，挡事故）、**在线度量仪**（机制二，护栏的 pass/fail 日志天然是免费的生产观测数据，不用另起炉灶打点）、**误差边界盒**（机制三，Agent 时代真正的刚需：单步 95% 可靠的模型串十步只剩 ~60%，每步一个 bounding box 是把乘法变回加法的唯一办法）。评估"要不要上护栏"时别只算机制一的账——机制二、三往往才是长期收益的大头。

## 5. 本课总结

| 要点 | 一句话 |
|---|---|
| 定义 | 护栏 = 对 LLM 调用输入/输出的二次检查，显式验证预期而非盲信模型 |
| 预期光谱 | 从格式 / JSON schema 到无幻觉 / 无 jailbreak，平凡到复杂都是同一件事 |
| 位置 | Input Guard 进 LLM 前拦（PII / off-topic / jailbreak），Output Guard 出 LLM 后拦（幻觉 / 跑题 / 不安全） |
| 实现 | 规则引擎（regex）→ 进程内微调小模型 → 二次 LLM 调用，常见为组合拳 |
| 三重价值 | 守住 inviolable constraints、把大问题拆成小检查来度量、包住多步级联误差 → 限制 worst-case risk |

> **记忆点（引出 L3）**：概念框架已齐——guard 是位置、guardrail 是检查器、三类技术是弹药。L3 从概念落到代码：给披萨店 chatbot 实现**第一个护栏**，一个非常简单的例子——不许 chatbot 泄露披萨店正在做的秘密项目，走通 Validator → Guard → Guardrails Server 的完整链路。
