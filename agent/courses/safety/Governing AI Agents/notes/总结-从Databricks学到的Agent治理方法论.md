# 课程总结 · 从 Databricks 学到的 Agent 治理方法论

> 课程：Governing AI Agents（DeepLearning.AI × Databricks）
> 这份总结**不落代码/命令**（那些在 L4/L6/L7 笔记和实操手册里），只提炼**换个平台也成立的治理方法论**——即"如何治理一个生产 AI Agent"这件事本身的思维框架。Databricks（Unity Catalog + MLflow）只是这套方法论的一种落地实现。

---

## 一、一句话拿走

> **能在数据层/平台层用确定性机制解决的约束，永远不要留给 prompt 和护栏去赌概率。**
> 治理管"不依赖模型行为的确定性边界"，护栏与 eval 管"依赖模型输出内容的概率性约束"——两者是**不同层的不同工具**，不可互替。

这一句是全课的题眼，其余七条都是它的展开。

---

## 二、治理的坐标系：四大支柱（L1）

Agent 治理不是一个模糊的"要安全"，而是**四个可分别验收的维度**：

| 支柱 | 回答的问题 | 验收标准（四问 checklist） |
|---|---|---|
| **Lifecycle Management** | agent 怎么版本化、晋级、回滚？ | 能否带评审与回滚地跨环境安全晋级变更？ |
| **Risk Management** | 数据分级、合规过滤、失效回滚做了吗？ | 是否有多层防护在问题冲击生产前拦住？ |
| **Security** | 谁能访问什么、以什么身份运行？ | 所有数据源是否只对被授权的 agent/用户可见？ |
| **Observability** | 能追溯 agent 干了什么吗？ | 能否追溯用了哪个工具、何时运行、访问和返回了什么？ |

> **方法论价值**：把"治理"从形容词变成**四条可打勾的工程清单**。评估任何 agent 平台/方案，就问这四支柱各落到什么程度——比"它安不安全"这种模糊问题有用得多。

**课程的核心警示（L1）**：`prototype-first` 让**性能压过治理**是最大隐患。demo 起步不是错，**性能压过治理才是错**——治理债和技术债一样，越晚还越贵。

## 三、七条可迁移的治理原则（全课精华）

### 原则 1 · 治理下沉到数据/平台层，不在 agent 代码里

治理面有三层，**没有一层住在 agent 代码里**：

- **数据层**（L4）：谁能读哪张表、PII 是否匿名——用视图 + 列掩码 + 权限；
- **身份层**（L3）：agent 以什么身份运行——用 Service Principal；
- **流量层**（L5）：端点之上的过滤/审计/成本——用 AI Gateway。

> 为什么关键：agent 内部实现可以随便换（换框架、换模型、换 prompt），**治理面不动**。治理散在 agent 代码里 = 每换一次实现就要重新审一遍安全。下沉到平台层 = 一次定义，任何 agent／任何访问路径都受同一套规则约束。

### 原则 2 · 确定性边界 vs 概率性约束——治理与护栏的分工判据

**这是全课最重要的裁决。** 判据只有一句：**看约束是否依赖模型行为。**

| 约束类型 | 例子 | 交给谁 | 为什么 |
|---|---|---|---|
| **不依赖模型的确定性边界** | 谁能读哪张表、PII 是否匿名、以什么身份运行 | **治理层**（权限/视图/掩码/身份） | 它不会被 prompt injection 说服 |
| **依赖模型输出内容的概率性约束** | 语气是否有害、答案是否切题/幻觉 | **护栏 + eval**（LLM judge / 运行时拦截） | 只能概率性度量与兜底 |

**课程的黄金案例**：用户问 "John Smith 的 SSN 是多少？"——agent 拒答，**不是被 output guardrail 拦下的，而是 agent 的身份从一开始就 SELECT 不到那一列**。
> 能下沉到治理层用确定性机制解决的，永远不要留给护栏赌概率。护栏只兜治理层管不到的部分（生成内容的语义安全）。

### 原则 3 · 纵深防御——每层都假设上一层会被绕过

单层防护都有洞，治理靠**多层确定性机制叠加**：

- 分类打标 → 只是元数据，**本身不拦访问**；
- 匿名化视图 → 好，但**谁拿到底表直接访问权就被绕过**；
- **列掩码 → 由引擎在每次查询强制执行，无论从哪条路径都绕不过**（admin 也不例外）；
- UC 函数工具 → agent 接触数据的**唯一通道**，锁死到匿名视图。

> 方法论：设计每一层时都问"如果这层被绕过，下一层还拦得住吗？"。视图能被绕过，所以要有列掩码兜底——**这就是纵深防御的判断动作**。

### 原则 4 · 最小权限——爆炸半径 = 身份的权限上限

假设 prompt injection 总有打穿的一天，**被打穿时 agent 能造成的破坏上限 = 它的身份权限**。所以：

> 风险 = 概率 × 损失。**护栏层压"概率"（降低事件发生率），身份层压"损失"（封顶事件破坏）**——两层各压一个因子，缺一不可。

只有 eval 没 guardrail = 事后诸葛；只有 guardrail 没最小权限 = 一旦打穿就是灾难。

### 原则 5 · 身份即审计的主语——用专用身份部署，绝不用开发者身份

**agent 上线那一刻用什么身份，决定了此后所有审计日志的主语。** 用开发者账号（人 + admin 权限）部署 agent：
- 爆炸半径 = admin 能摸到的一切；
- 审计日志永远混着"人的操作"和"agent 的操作"，无法追溯。

正解：预建 **Service Principal（非人类身份）**，以它的最小权限身份部署。SP 部署的六个理由（L5）：爆炸半径、清晰审计、注入防御、合规、凭证隔离、完整治理。

### 原则 6 · group 是权限的"间接层"——把 N×M 降成 N+M

权限授给 **group** 而不是逐个主体：新开发者入职、新 agent 上线，都**不触发权限变更**，变更收敛到"加/移一个成员"。
> 和代码里"依赖接口不依赖实现"同一招——加一层稳定的中间抽象，把授权关系从 N×M 降到 N+M。

### 原则 7 · eval 与 enablement 都要内嵌进治理边界

- **eval → monitoring 一次定义两阶段复用**（L5/L7）：发布前 eval 是门控（gate），发布后同一批 scorers 加阈值就是监控（monitor）。设计 eval 时就按"未来要 7×24 跑"写，别上线后监控另起炉灶。
- **enablement 内嵌治理**（L6）：低代码入口（Playground）生成的 agent，用的工具本来就是治理过的 UC 函数、生成的代码天然带审计日志。
  > 判据：**enablement 工具生成的产物是否自动落在治理边界内**——落在内则规模化安全，落在外则每个低代码 agent 都是影子 IT。

## 四、Databricks 是怎么落地这套方法论的（"两件套"）

方法论要有确定性机制承载，Databricks 用两个组件：

| 组件 | 角色 | 承载哪些原则 |
|---|---|---|
| **Unity Catalog** | 控制平面（谁能对什么做什么） | 原则 1/2/3/4/6：权限、视图、列掩码、分类标签、group、UC 函数工具 |
| **MLflow** | 生命周期平面（agent 的版本/追踪/注册/部署） | 原则 5/7：模型注册、版本回滚、tracing、eval→monitoring |

> 关键认知：**治理是"控制平面 + 生命周期平面"的组合**，不是单一功能。UC 管"能不能"，MLflow 管"从开发到上线到监控的全过程"。换平台（如 AWS 用 Lake Formation + SageMaker）时，找的也是这两类平面的对应物。

## 五、架构师的裁决（最该带走的三条判断）

1. **治理引入时机 = 数据准备的第一天，不是部署前一周。**
   课程的顺序本身就是答案：L4 先把视图/身份/授权做完，L6-L7 的 agent 从出生起就只见治理过的断面。反过来先造 agent 后补治理 = 要在已经四处直连裸表的代码里逆向收权，成本高一个量级。

2. **治理 vs 护栏的分工，用"是否依赖模型行为"一刀切开**（原则 2）。这是面试和实战都能直接用的判据。

3. **什么时候值得上这整套重治理？** 当"**数据规模 + 治理合规**"同时是硬需求时（金融/医疗/HR 等必须零 PII 泄漏的场景）。只有其中之一（比如只想跑个 agent、数据不敏感），这套就是杀鸡用牛刀——回到选型矩阵"按需求强度选型、别过度工程"的主线。

## 七、全课一句话地图

> **L1** 立四支柱 → **L2** Unity Catalog 做治理基座 → **L3** 三类身份、agent 归 Service Principal → **L4** 数据层五件套（标签/视图/权限/掩码/工具函数）→ **L5** 生产就绪概念（eval/MLflow/SP 六理由/Gateway）→ **L6** 写 agent（工具即治理函数、ResponsesAgent 部署契约）→ **L7** eval→注册→以 SP 部署→Playground 验证治理闭环。
>
> 收官四问全打勾：**职责分离 · 纵深防御 · 最小权限 · 可审计一切**。
