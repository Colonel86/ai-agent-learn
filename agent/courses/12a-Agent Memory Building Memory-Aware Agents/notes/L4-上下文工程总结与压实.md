# L4 · 上下文工程：总结、压实与工作流记忆

## 1. 问题：上下文窗口是稀缺资源

再大的窗口也会满。当记忆越攒越多，不能无脑全塞。本课给两种**上下文窗口缩减（context window reduction）**手段，核心区别是**信息是"丢掉"还是"搬走"**。

## 2. 两条路线：Summarization vs Compaction

| | **Context Summarization（总结）** | **Context Compaction（压实/卸载）** |
|---|---|---|
| 本质 | 有损压缩（lossy） | 无损搬移（offload） |
| 做法 | 擦掉原文，注入一段摘要 | 原文存进 DB，上下文只留 `ID + 描述` |
| 能否还原 | **不能**，细节永久丢失 | **能**，LLM 按需 `expand_summary(id)` 拉回 |
| 代价 | 省 token，损细节 | 省 token，多一次检索 |

> **架构师视角**：这两者不是二选一，而是**分层配合**。本课的实现其实是"压实"为主：总结产出一个 summary_id 存进 `SUMMARY_MEMORY`，上下文里只留 `[Summary ID: xxx] 描述`，需要细节时再 `expand_summary` 展开原始对话。这等于给上下文做了"分页/虚拟内存"——热数据在窗口内，冷数据在 DB，按需换入。这是我在面试包 `04-multi-layer-memory` 里该重点讲的机制，比单纯"滑动窗口/摘要"高级一档。

## 3. 关键代码：上下文用量监控 + 80% 自动触发

### 估算用量（粗略但够用）
```python
def calculate_context_usage(context: str, model="gpt-5-mini") -> dict:
    estimated_tokens = len(context) // 4          # ~4 字符 ≈ 1 token
    max_tokens = MODEL_TOKEN_LIMITS.get(model, 128000)
    percentage = (estimated_tokens / max_tokens) * 100
    return {"tokens": estimated_tokens, "max": max_tokens, "percent": round(percentage,1)}
```

> **注记**：`len//4` 是廉价的字符估算，不是真 tokenizer。生产里对成本敏感时该换成 `tiktoken` 精确计。但作为"要不要触发总结"的阈值判断，估算完全够——这是典型的"够用就好"工程取舍。

### 80% 阈值触发（确定性操作）
```python
usage = calculate_context_usage(memory_context)
if usage['percent'] > 80:
    memory_context, summaries = offload_to_summary(memory_context, memory_manager, client, thread_id=thread_id)
```

> **记忆点**：80% 是"确定性触发（deterministic）"的经典例子——**代码而非 LLM 决定何时压缩**（呼应 L2 的两种触发方式）。同一个总结能力也暴露成工具让 LLM 主动调用（agent-triggered），两条触发路径共用一套底层函数。

## 4. 总结的五步法（`summarize_conversation`）

这是把"总结"做成**可审计、不重复**的关键：

1. **读**：`SELECT ... WHERE thread_id=:t AND summary_id IS NULL`——只读**未被总结过**的行
2. **总结**：喂给 LLM，产出结构化摘要（模板见下）
3. **存**：写进 `SUMMARY_MEMORY`，拿到 summary_id
4. **标记**：把刚才那几行的 `summary_id` 字段更新掉——**下次不会重复总结**
5. **返回**：摘要对象供继续拼上下文

结构化摘要 prompt 强制四个固定小标题，保证摘要可复用：
```
### Technical Information
### Emotional Context
### Entities & References
### Action Items & Decisions
规则：保留具体细节(名字/日期/API/错误/决策)；区分已确认事实与开放问题；不得杜撰。
```

> **架构师视角**：第 4 步的 `summary_id` 回填是整个设计的精髓——它把"哪些对话已归档"这件事**持久化到数据行本身**，而不是靠内存里的游标。任何时候崩溃重启，只要查 `summary_id IS NULL` 就知道还有哪些没总结。这是"记忆系统要有事务性/可恢复性"的具体体现，也是为什么 L1 强调记忆核心得是**数据库**而非临时结构。

## 5. Compaction 的实现细节（`offload_to_summary`）

只替换 **对话段**，保留其它记忆段：找到 `## Conversation Memory` 标题，把该段换成一个 stub（"旧对话已总结，用 Summary Memory 引用 + expand_summary(id) 取细节"），其余段（知识库/工作流/实体）原样保留。

> **记忆点**：压缩要**精准打击**——只压对话这种最膨胀、最可再生的部分，不动知识库这种高价值段。这体现了对不同记忆类型"可压缩性"的差异化对待。

## 6. Workflow Memory（工作流记忆）

把**有序的执行步骤**存下来供复用——智能体做过一遍的任务流程，下次遇到相似任务可以参考（"adapt patterns, do not copy blindly"，见 L5 系统提示）。这是**程序性记忆**的又一实例：不只是存"能用什么工具"（toolbox），还存"上次是按什么顺序把事办成的"。
