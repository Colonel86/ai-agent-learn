# AI Agents in LangGraph —— 总结回顾

> 课程：**AI Agents in LangGraph**（DeepLearning.AI × LangChain × Tavily，讲师 Harrison Chase、Rotem Weiss）
> 用途：一页式快速回顾。逐课详记见各 `L0*` 笔记。

---

## 一句话主线

> **Agent 的行为本质是一个循环图（cyclic graph）：LLM 负责推理与决策，runtime 负责状态维护、工具调度和循环控制。LangGraph 把这套 runtime 标准化为 State + Nodes + Edges，再用 Checkpointer 持久化解锁多会话、Human-in-the-Loop 和时间旅行——可控性（controllability）是做出真正能跑的 agent 的关键。**

全课一条演进线：手写 ReAct（裸 Python）→ LangGraph 重写 → 换上 Agentic Search → 加持久化/流式 → 加人工干预 → 综合项目 Essay Writer → 前沿架构展望。

---

## 总纲：五大设计模式（L01，Andrew Ng）

| 模式 | 含义 | 本课对应 |
|---|---|---|
| **Planning** | 先规划步骤再执行 | Essay Writer 的 planner 节点 |
| **Tool Use** | 知道有哪些工具、怎么调 | function calling + Tavily |
| **Reflection** | 多轮迭代互相批评改进 | reflect → research_critique 循环 |
| **Multi-Agent** | 不同 prompt 扮演不同角色协作 | 五个 system prompt 调同一模型 |
| **Memory** | 跨步骤跟踪进度与中间结果 | AgentState + Checkpointer |

Agent 近年能落地的两大推手：**Function Calling LLMs**（工具使用变可预测）+ **为 agent 优化的工具**（如 agentic search）。

## 逐课速查

### L02 — 从零手写 ReAct Agent（无框架）

- **ReAct 循环**：`Thought → Action → PAUSE → Observation → …… → Answer`。
- 三样核心零件：维护 messages 列表的 Agent 类；定义循环规则 + 工具清单 + **one-shot 示例**的系统 prompt；正则解析 `Action:` + `known_actions` 字典 dispatch + `max_turns` 上限的自动循环。
- **本节核心洞察——LLM vs Runtime 分工**：LLM 管思考/选工具/决定何时停；runtime 管解析输出、执行工具、回填 observation、维护状态、限制循环。LangGraph 就是把 runtime 这一半标准化。

### L03 — LangGraph 组件（用框架重写同一个 agent）

- 三大积木：**Nodes**（agent/函数）、**Edges**（固定下一步）、**Conditional Edges**（按状态决定走向）。
- **Agent State**（最重要概念）：`TypedDict` + 注解定义合并语义——
  ```python
  class AgentState(TypedDict):
      messages: Annotated[list[AnyMessage], operator.add]  # 追加；不注解 = 覆盖
  ```
- 经典两节点图：`llm` →（条件边 `exists_action`）→ `action` → 回到 `llm`，否则 `END`。
- 关键 API：`model.bind_tools(tools)` 告诉模型可用工具；节点返回 `{'messages': [...]}` 自动合并进状态；`graph.compile()` 产出 Runnable。
- **容错**：LLM 幻觉出不存在的工具名 → 返回 `"bad tool name, retry"` 让 agent 下一轮自愈。
- 一次 invoke 自动覆盖三种模式：单步查询、**并行 tool_calls**（一次发多个）、**顺序依赖查询**（第二次查询依赖第一次结果，需要更强模型）。

### L04 — Agentic Search（Tavily）

- 核心区别：**普通搜索返回链接给人浏览；agent 需要"答案 + 可预测格式"**。"Agent 不需要好看，需要好解析。"
- Agentic search 内部流程：理解问题 → 拆子问题 → 按类型选数据源 → 抽取相关片段（chunking + 向量 top-K）→ 评分过滤 → 结构化返回。
- 两种用法：`client.search(q, include_answer=True)["answer"]` 一句话答案；默认 `results` 结构化 JSON 喂 agent。
- 对比实验：DuckDuckGo + BeautifulSoup 手动爬页面 → 冗长难解析；Tavily 直接给干净 JSON。

### L05 — 持久化与流式输出（生产化两件套）

- **Checkpointer = 每个节点执行后自动保存状态**：`graph.compile(checkpointer=SqliteSaver.from_conn_string(":memory:"))`；生产换 Redis/Postgres。
- **`thread_id` = 会话身份证**：`thread = {"configurable": {"thread_id": "1"}}` 作为 stream 第二参数；同 id 接着历史跑（记得"哪个更暖和"在比什么），换 id 从零开始。
- 两级流式：

| 方法 | 粒度 | 用途 |
|---|---|---|
| `graph.stream(...)` | 消息级（AI/Tool 消息） | 调试、可观察性 |
| `graph.astream_events(...)`（async，配 `AsyncSqliteSaver`） | token 级（`on_chat_model_stream` 事件） | 打字机前端体验 |

- 细节：工具调用阶段模型没有 content，所以 token 流只在最终回答阶段出现。

### L06 — Human-in-the-Loop（全部建立在 Checkpointer 之上）

- 两个关键改造：① **自定义 reducer**（同 id 替换、新 id 追加）取代 `operator.add`，支撑"改写历史消息"；② `graph.compile(interrupt_before=["action"])` 在工具执行前暂停。
- 四种模式：

| 模式 | 做什么 | 核心 API |
|---|---|---|
| 人工批准 | 工具执行前停下等确认 | `interrupt_before` + `stream(None, thread)` 续跑 |
| 修改当前状态 | 断点处改 tool_calls（保留原 id → 替换） | `update_state(thread, values)` |
| 时间旅行 + 分支 | 回到任意历史快照继续/改写，原历史保留 | `get_state_history` + `stream(None, past.config)` |
| 伪造工具结果 | 不调工具，手工注入 ToolMessage | `update_state(..., as_node="action")` |

- 关键语义：`stream(None, thread)` = "从 checkpoint 继续"而非新输入；`as_node` 让 graph 知道这个 update 算哪个节点的输出，从而正确推进 `next`。

### L07 — 项目实战 Essay Writer（融会贯通）

- 五节点循环图：`planner`（大纲）→ `research_plan`（生成查询→Tavily→收集文档）→ `generate`（写草稿，`revision_number+1`）→ 条件边 `should_continue`（超过 `max_revisions` 则 END）→ `reflect`（批评）→ `research_critique`（按批评补调研）→ 回到 `generate`。
- **复杂多字段 State**：`task / plan / draft / critique / content / revision_number / max_revisions`——每个字段有明确的所有者节点；累积字段（content）显式合并；循环终止靠计数器 + 条件边。
- 多角色 = **五个不同 system prompt 调同一个模型**（multi-agent 的朴素实现）。
- **结构化输出**：`model.with_structured_output(Queries)`（Pydantic）拿查询列表，不靠正则。
- GUI（Gradio）把 L05/L06 全部 API 可视化：interrupt、改 state、续跑、时间旅行、多 thread。

### L08 — 延伸资源

- 生态分层：**LangChain Docs**（Core / Community / 各 partner 包）→ **LangServe**（一键变 Web 服务）→ **LangSmith**（调试 + 生产监控 + Playground）→ LangGraph 仓库（tutorials/how-to）→ Prompt Hub。
- 前置课推荐：《Functions, Tools and Agents with LangChain》（即课程 9）。

### L09 — 高级 Agent 架构（五种前沿模式）

| 架构 | 核心特征 | 选型要点 |
|---|---|---|
| **Multi-Agent** | 多角色操作**同一份共享 state** | Essay Writer 即此模式的朴素版 |
| **Supervisor** | 中心 supervisor 调度独立 sub-agent（各有内部 state） | supervisor 要配**最强的 LLM**——路由/规划最吃推理力 |
| **Flow Engineering**（AlphaCodium） | 线性流水线 + 关键节点嵌小循环 | 精心设计信息流，别给 agent 过高自由度 |
| **Plan-and-Execute** | 先列完整计划→逐步执行→可 replan | 思考与行动分离，长任务更稳 |
| **LATS**（树搜索） | 对动作空间做 MCTS 式展开+反思+回溯 | **强依赖 Persistence**（要能回到历史状态） |

- Harrison 收官观点：**LangGraph 的差异化 = Controllability**，高可控性是 agent 真正能跑起来的关键。

## 关键 API 速查

| API | 用途 |
|---|---|
| `StateGraph(AgentState)` / `add_node` / `add_edge` / `add_conditional_edges` / `set_entry_point` / `compile()` | 建图 |
| `Annotated[list, operator.add]`（或自定义 reducer） | 状态字段合并语义：追加 / 替换 |
| `model.bind_tools(tools)` | 让 LLM 知道可用工具 |
| `model.with_structured_output(PydanticModel)` | 结构化输出，替代正则解析 |
| `graph.compile(checkpointer=, interrupt_before=[...])` | 持久化 + 断点 |
| `graph.invoke / stream / astream_events` | 调用 / 消息级流 / token 级流 |
| `{"configurable": {"thread_id": "1"}}` | 会话隔离与恢复 |
| `get_state / get_state_history / update_state(…, as_node=)` | 查状态 / 时间旅行 / 改状态 |
| `stream(None, thread_or_config)` | 从 checkpoint 继续（含历史分支） |
| `TavilyClient.search(q, include_answer=True)` | agentic search |

## 架构师视角的四个要点

1. **先手写一遍再用框架**：L02 的价值在于看清 LLM/runtime 的职责边界——评估任何 agent 框架时，问的就是"它把 runtime 的哪些部分标准化了、代价是什么"。LangGraph 的取舍是用图的显式性换可控性，与"全自由 prompt 驱动"的框架（早期 AutoGPT 式）形成两极。
2. **State 设计是 agent 架构的核心决策**：字段拆分、合并语义（追加 vs 覆盖 vs 自定义 reducer）、所有者节点分工、循环终止条件——Essay Writer 演示了从"单 messages 列表"到"多字段业务状态"的跃迁。状态没设计好，图再漂亮也跑不稳。
3. **Persistence 不是附加功能，是能力底座**：多用户会话、断点续跑、人工审批、时间旅行、LATS 树搜索全部架在 Checkpointer 上。生产 agent 选型时"状态能不能存、能不能回放"应当是一票否决项。
4. **可控性 vs 自主性的光谱**：L09 五种架构本质是在这条光谱上取点——Flow Engineering 最受控（线性为主），LATS 最自主（树搜索探索）。Harrison 的立场（也是当下工程共识）：**宁可多设计信息流，少给 agent 自由度**；自主性随模型能力增强再逐步放开。
