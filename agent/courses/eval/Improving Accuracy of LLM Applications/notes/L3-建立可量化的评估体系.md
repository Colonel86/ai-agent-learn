# L3 · 建立可量化的评估体系（LLM-as-judge + 确定性校验 + Pipeline）

> 课程：Improving Accuracy of LLM Applications（DeepLearning.AI × Lamini/Meta）
> 讲师：Sharon Zhou（Lamini CEO）、Amit Sangani（Meta Llama 团队）
> 本课任务：为 text-to-SQL 应用搭一套**系统化、可量化、可扩展**的评估框架，量出 base Llama 3 到底行不行、错在哪、下一步往哪推。

## 0. 承上：L2 留下的问题

L2 里已经把 SQL agent 接通了——用户问一句自然语言，Llama 3 生成 SQL，SQL 打到 nba_roster 数据库，返回结果给用户。但同一个模型「有的问题答得好、有的直接幻觉」。凭「看几个例子感觉不错」没法回答「它到底改好了没有」。本课就是把这种主观感受换成**能对比 A/B、能指方向、能自动跑**的分数。

## 1. 评估的四个目标

Sharon 把「什么是好评估」拆成四条，缺一不可：

| 目标 | 含义 |
|---|---|
| **量化（quantitative）** | 给出可信的可比较分数——model A vs model B，能说清 good / better / best |
| **指出下一步** | 好评估不能「高高在上」到没法告诉你这一轮迭代该改什么，要精确地把「下一个 frontier」标出来 |
| **回答「我试的东西有没有用」** | Did what I tried work？yes/no 且可靠 |
| **可扩展 & 自动化** | 用 LLM 帮你程序化打分，才能把评估集和被评模型都规模化铺开 |

> **架构师视角**：这里的「评估」不是上线后的监控大盘，而是**开发内循环的方向盘**。它同时回答两个正交问题——「刚才那步对不对」（回归）和「下一步往哪走」（探索）。缺了后者，评估就退化成一个只会亮红灯却不会指路的仪表盘。

## 2. 初始评估集：小而精，别搞史诗工程

一个反直觉但反复强调的点：**从小开始，20 到 100 条即可**。

- 很多人一上来就立志攒一个巨型评估集，其实不实际——目标是**快速迭代、每次只改一个东西并看到模型变好**；模型一变好，评估集自然要跟着调整，过早 commit 到超大集合反而绑住手脚。
- **质量 > 数量**：高质量评估才「不 noisy」、才敢信；然后再做**迭代式扩展**。
- **聚焦改进区**：优先收那些「模型差一点点就对、但就是不对」的例子，以及正在幻觉的地方——这就是给模型设的 North Star。
- **要有 breadth**：NBA 例子里问题覆盖面很广（「勇士队的控卫是谁」「公牛队 25 岁及以下有几人」），因为评估集实际上在教模型「它会遇到的全部面」。

### 如何设好「下一个 frontier」

1. **收「最简单但仍失败」的例子**——它几乎够得着，是最合理的下一个攻克目标；
2. **对抗性 playground**：把模型挂上去主动去搞坏它，摸清边界，这也往往就是真实用户的用法；
3. **设下一个准确率目标（想要几个 9）**：先把评估集缩到极窄极聚焦，让准确率从 ~20% 爬到 90/95/99%（先在小集合上相信它能到），**再把评估变难**——准确率掉回 20%，再往上爬。如此循环。

> **对比课程 21《Evaluating AI Agents》**：课程 21 讲的是 agent 轨迹级评估（工具选得对不对、路径、trajectory）；本课的评估更「窄」也更「狠」——只盯单点任务的**事实正确性**，且明确服务于「下一轮改什么」。两者不冲突：agent 级 eval 管「流程走通没」，任务级 eval（本课）管「每一步的输出精不精确」。

## 3. 三种打分手段：LLM-as-judge / 确定性 / exact match

### 3.1 LLM 打分（另起一次 LLM 调用）

给判分 LLM 喂「问题 + 生成答案（+ 参考答案）」，让它输出分数。要拿到**可靠的数值**分，关键是 **structured output**——强制输出 int / float / list of ints（比如要匹配的 product ID 列表），保证「量化且一定量化」。

本课的判分 prompt 是比较两个 dataframe：

```python
# system：比较两个 dataframe，almost identical 或传达相同信息就算 similar
# 强制 JSON 输出：先 explanation（str）再 similar（bool）
system_prompt = ("Compare the following two dataframes. They are similar if they are "
                 "almost identical, or if they convey the same information ... "
                 "Respond with valid JSON {'explanation': str, 'similar': bool}")

llm_similarity = llm.generate(
    prompt,
    output_type={"explanation": "str", "similar": "bool"},  # 先解释后布尔
    max_new_tokens=200)
```

> **小技巧（藏在 output_type 里的 CoT）**：把 `explanation` 排在 `similar` **前面**，就是用严格结构化输出实现 chain-of-thought——逼模型先想清楚再给结论，比直接吐 bool 稳。

### 3.2 为什么需要「模糊匹配」

生成的 SQL 常常是**语义等价但非字面相同**。课程的经典例子：生成结果和参考结果里 salary 和 name 两列**顺序颠倒**了——做 exact match 会判 False，但对 SQL 输出而言完全正确。LLM judge 能吃下这种模糊匹配。

### 3.3 确定性校验（不用 LLM，更该优先）

- **把生成的 SQL 真打到数据库里执行**：能不能跑，先分出「valid / invalid」——invalid 显然就是错的（本课 lab 里正是靠 `try/except pd.read_sql` 抓语法错）；
- 跑得通再和参考结果做 exact match；
- **memory tuning 的额外红利**：如果把模型教成输出某种固定格式 / 固定 exact-match 形态，评估就能直接用 exact match，省掉一层 LLM judge。

> **对比 `5-observability-eval.md` 与 DSPy 自动优化**：本课的 judge/exact-match/DB 执行三件套，正是 `5-observability-eval.md` 里「LLM-as-judge + 规则校验 + 参考对齐」那一层的具体落地。而 DSPy 把「评估分数」当作 metric 直接喂给优化器去自动搜 prompt/权重；本课则是**人在环里**看分、做 error analysis、手动决定下一步。判断用哪种：评估指标能写成稳定可微/可搜的 metric 且搜索空间清晰 → 交给 DSPy 自动优化；指标本身还在演化、要靠人判断「什么算对」→ 先走本课这种手动迭代把 metric 磨稳。

## 4. 把评估拼成 Pipeline

Lab 把三步固化成可复用的类，方便对**每一次模型迭代**都跑一遍：

```python
# QueryStage：生成 SQL → 打到 DB → 记录 generated_df / reference_df / query_succeeded
class QueryStage(GenerationNode):
    def postprocess(self, obj):
        try:
            df = pd.read_sql(obj.response["sqlite_query"], con=engine)
            obj.data["query_succeeded"] = True          # 语法有效
        except Exception:
            obj.data["query_succeeded"] = False         # 无效即错
        obj.data["reference_df"] = pd.read_sql(obj.data["sql"], con=engine)

# ScoreStage：LLM judge 判 similar，再与 exact match 取或
class ScoreStage(GenerationNode):
    def is_matching(self, data, response):
        return (str(data.get('df')).lower() == str(data['reference_df']).lower()
                or response['similar'] == "true")       # 字面等 或 语义相似

# 组装：先 query 再 score
class EvaluationPipeline(GenerationPipeline):
    def forward(self, x):
        return self.score_stage(self.query_stage(x))
```

`save_eval_results` 落盘时两条纪律很重要：
- **带时间戳 + experiment_name**，随时回溯「哪个模型跑出哪个结果」；
- 分别存 `sql_results.jsonl`（对的）和 `sql_errors.jsonl`（错的），并算两个指标：**Percent Valid SQL Syntax**（能跑）和 **Percent Correct SQL Query**（跑对）。

## 5. Lab 实况：base Llama 3 的成绩单

- 单条「NBA 中位数体重」→ base 模型生成的 SQL **语法非法**，跑不起来；
- 试 **agent reflection**（把报错回喂让它改）——依然失败（同样的错）；对照给出正确 SQL 才跑通。这类「听起来简单、实际难写」的查询正是评估集该收的好样本；
- 全量 20 条评估：**Valid SQL 55%，Correct 只有 30%**。
- 一个值得记的投入产出比：这 20 条评估集**只花约 20 分钟**写好，就把准确率从 ~20-30% 顶到 **75%**；后面再花约一小时迭代评估集 + 训练数据，能推到 **95%**。

## 6. 迭代纪律

- 评估**标准本身会随迭代更新**（judge 的 prompt、要不要从 bool 升级成多维度打分如 SQL 效率）；
- 评估集持续扩 breadth、加难例；
- 打分机制从简单起步再升级（确定性 exact match / valid SQL 校验 / LLM judge 多 prompt）；
- **严格记账**：哪个模型版本产出哪个结果——迭代会非常多、命名很难，但这是能不能持续推进的命根子。

## 7. 本课总结

| 要点 | 一句话 |
|---|---|
| 评估四目标 | 量化、指方向、验证「有没有用」、可扩展自动化 |
| 小而精 | 20-100 条起步，质量优先，迭代式扩展 |
| 下一个 frontier | 收「差一点就对」的例子 + 对抗 playground + 设「几个 9」目标 |
| 三种打分 | LLM judge（结构化输出保数值）/ DB 执行确定性校验 / exact match |
| 模糊匹配 | 语义等价≠字面相同（salary/name 换序仍对）→ LLM judge 兜底 |
| Pipeline | QueryStage + ScoreStage，带时间戳记账，两指标：valid% / correct% |
| base 成绩 | 20 条评估集，valid 55% / correct 30%，20 分钟评估集把准确率推到 75% |

> **记忆点（引出 L4）**：评估告诉你 base Llama 3 只有 30% correct，且 prompt/reflection 都顶不上去。当 prompt 工程见顶，下一个杠杆就是**改模型权重**——L4 讲 fine-tuning：instruction fine-tuning、以及把幻觉「loss 打到零」的 memory tuning，还要破除关于 fine-tuning 成本与难度的三个 myth。
