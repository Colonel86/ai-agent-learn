# L5 · 向量库做日志异常检测（Sentence Transformers + Pinecone）

> 课程：Building Applications with Vector Databases（DeepLearning.AI × Pinecone）· Lesson 06
> 本课任务：训练一个**很小**的机器学习模型，在 Cisco ASA 日志里揪出**异常条目**。用有监督学习在小数据集上训练（为了课堂可跑、训练时间短），再喂一段样本日志，找出其中埋的那条异常。

## 0. 从 L4 衔接：同一接口，翻转信号方向

L4 用 Pinecone 找"最像的脸"——取相似分**最高**的结果。本课反过来：日志绝大多数是规整、彼此相似的行，**相似分最低**的那条恰恰是异常。查询接口不变，读结果的方向从 top 翻到 bottom，就从"检索"变成了"异常检测"。

本课路线：**① 小规模有监督训练一个句向量模型 → ② 用它把样本日志编码进 Pinecone → ③ 拿一条"已知正常"的日志去查，最差分的那条即异常**。

## 1. 数据：训练集与样本日志

| 文件 | 作用 | 格式 |
|---|---|---|
| `training.txt` | **有标签**训练集（有监督） | `日志A ^ 日志B ^ 相似度标签`，`^`（caret）分隔 |
| `sample.log` | 待检样本，内藏 1 条异常 | 标准 Cisco ASA 行：日期 + 时间 + 日志标识 + 消息 |

Cisco ASA 日志行的结构：`date`、`time`、日志标识符、以及真正的**日志消息**。训练集的标签是 **0~1 连续值**的相似度——两条日志"像不像"，1 = 几乎相同，0.9 = 很像，越低越不像。讲师提示看文件底部有一批标注得"不一样"的样本对。

> **架构师视角**：这门课刻意用**极小的有监督数据**训一个专用小模型，而非直接拿通用大嵌入模型硬套。原因是"什么算异常"高度依赖领域——通用模型不知道 Cisco ASA 日志的正常长什么样。用几百对"(日志, 日志, 相似度)"就能把通用 BERT 微调出领域语感，这是**小数据 + 领域微调 > 大而泛的零样本**的典型场景。判断依据：当"正常"的定义强绑定某个狭窄领域时，一点点标注数据的收益极高。

## 2. 模型：BERT + Pooling + Dense（256 维）

用 `sentence-transformers` 搭三层小模型：

```python
# 口播摘录：词嵌入层用 bert-base-cased（基础款），再池化，再压到 256 维
word_embedding_model = models.Transformer("bert-base-cased")   # 基础 word embedding
pooling_model = models.Pooling(...)                             # 小池化层
dense_model = models.Dense(out_features=256)                    # 降到 256 维嵌入
model = SentenceTransformer(modules=[word_embedding_model,
                                     pooling_model, dense_model])
print(device)   # 输出 CPU / CUDA；本课 CPU 足够，有 CUDA 会更快
```

`bert-base-cased` 作词嵌入基座 → 一个小 pooling 层 → 一个小 dense 层把维度收到 **256**。设备打印显示跑在 CPU（有 GPU 更快，但这个规模 CPU 无压力）。

## 3. 训练：InputExample + model.fit

把 `training.txt` 逐行读入，按 `^` 切成 (logA, logB, label)，包成 `InputExample` 交给有监督训练：

```python
train_examples = []
for line in open("training.txt").read().splitlines():
    a, b, label = line.strip().split("^")          # caret 分隔的三段
    train_examples.append(
        InputExample(texts=[a, b], label=float(label)))  # 带标签 → 有监督

# 100 warm-up steps + data loader + 损失函数
model.fit(train_objectives=[(train_dataloader, train_loss)],
          warmup_steps=100, ...)                    # 训练约几分钟
```

`model.fit` 跑几分钟即完成。训练同时顺手准备好 `sample.log` 的样本数据（讲师把两件事塞进同一个 cell）。训练完用模型对 samples 生成嵌入存进 `emb`。

## 4. 灌库：熟悉的 upsert 套路

```python
preps = []
for s in samples:                     # 遍历已编码的样本
    preps.append((id, embedding, metadata))
index.upsert(preps)                    # 灌进 Pinecone，很快
```

这套"建数组 → 逐条造向量 → upsert"的模式在前几课已反复出现，本课复用。

## 5. 检测：查已知正常行，取最差分

关键手法——**不直接找异常，而是拿一条"已知正常"的日志去查，看谁离它最远**：

```python
good_log_line = sample[0]             # 已知第 0 条是正常的
print(good_log_line)                  # 确认它确实规整

# 用这条正常行查 Pinecone，要 top 100
results = index.query(vector=embed(good_log_line), top_k=100, ...)
```

读结果：

- **top 10**：与正常行高度相似（第一条就是它自己，score = 1.0），其余也都很像；
- 因为库里不足 100 条，实际返回**少于 100** 个结果；
- **取最后一个（最差分）**：一条长得像 Cisco ASA、但消息是 **`segfault detected in the matrix`** 的行，相似分只有 **0.32**。

这条就是埋进去的异常——用一条极规范的日志去检索，**排在最末、分数最低的那条即异常**。

```python
worst = results.matches[-1]           # 最后一条 = 最差分
print(worst.score)                    # 0.32 → 异常
# 消息 "segfault detected in the matrix" 明显不属于正常 ASA 日志分布
```

> **对比 L1 的 RAG 检索**：RAG（Lesson 02）里 top-K 检索是为了把**最相关**的上下文喂给 LLM——要的是分布**中心**、最贴题的那几条。本课要的是分布**边缘**、离参照点最远的那一条。同一个 `index.query`，RAG 消费头部、异常检测消费尾部。这也提示一个通用心法：**只要你能定义一个"正常锚点"并嵌入它，向量库就能免训练地做离群检测**——锚点可以是一条样本、也可以是一簇正常样本的质心。

> **架构师视角**：整套异常检测没有专门的"异常检测算法"（无 Isolation Forest、无 autoencoder 重构误差），只是**微调嵌入 + 一次最近邻查询 + 读尾部**。它的软肋也清楚：依赖"库里绝大多数是正常样本"且"存在可信正常锚点"的假设；当异常成规模或分布漂移时，尾部信号会失真。作为架构师要能说清它便宜在哪、什么时候会失效——而不是把它当通用异常检测银弹。

## 本课总结

| 要点 | 一句话 |
|---|---|
| 应用形态 | 日志异常检测 = 领域微调嵌入 + 最近邻查询 + 读最差分 |
| 训练数据 | `training.txt`：`logA ^ logB ^ 相似度(0~1)`，有监督 |
| 模型 | bert-base-cased + Pooling + Dense → 256 维，CPU 几分钟 |
| 检测手法 | 拿"已知正常"行查 top 100，返回列表**末尾**即异常 |
| 结果 | `segfault detected in the matrix`，相似分 0.32 |

> **记忆点（引出 L6）**：至此六种应用（语义搜索、RAG、推荐、hybrid search、人脸相似、日志异常）跑完——它们共享同一套"编码成向量 → 存 Pinecone → 相似度查询"的骨架，只在**嵌入来源**和**读结果的方式**上分叉。L6 收官篇把这六者摆到一张表上横向对照，并给出"何时用向量库、Pinecone 托管 vs. 自建"的架构裁决。
