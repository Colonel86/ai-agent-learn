# L2 · 归一化多格式内容：partition_html / partition_pptx / PDF 走 API

> 课程：Preprocessing Unstructured Data for LLM Applications（DeepLearning.AI × Unstructured）
> 本课任务：动手把三种完全不同的文档——**HTML 博客、PowerPoint 演示、PDF 论文**——各自解析（partition），归一化成**同一种 document elements 列表**，再序列化为 JSON。核心是体会"一套下游代码通吃所有格式"的价值。

## 1. 为什么要归一化：四条收益

Matt 先讲动机。组织里的文档格式五花八门（PDF / Word / HTML），而**构建 LLM 应用时，你不该关心文档从哪来**，只想让它们以统一格式被同样对待。第一步就是把文档打散成通用元素（titles、narrative text 等）。收益有四：

| 收益 | 说明 |
|---|---|
| **一套代码处理所有格式** | 比如过滤页眉页脚（headers/footers），归一化后一段代码通吃；否则 HTML 和 PDF 得各写一套逻辑 |
| **下游操作统一** | chunking 等操作不必按文档类型分别设计策略 |
| **降低处理成本** | 预处理**最贵的是初始内容抽取**；chunking 等下游操作很便宜 |
| **可快速试验** | 内容归一化后，可用极低算力反复试不同 chunking 策略 |

> **架构师视角**：第三条"抽取贵、下游便宜"是个关键的成本结构洞察。它决定了正确的工程姿势——**抽取只做一次并落盘（序列化），下游 chunking/filtering 反复迭代**。如果每次调 chunk 参数都重新解析 PDF，就是把最贵的一步重复执行 N 次。这也是下一节"数据序列化"存在的根本理由：把昂贵的抽取结果缓存成可复用的资产。

## 2. 数据序列化：为什么选 JSON

归一化之后通常紧接着**序列化**，好处是"抽一次、以后反复用，不必重新预处理"。本课统一序列化成 **JSON**，理由：

- 通用、结构清晰、人人都懂；
- 是标准 HTTP 响应格式——处理 PDF/图像时要走 API，返回的天然就是 JSON；
- 跨语言：可以 Python 预处理 → 存 JSON → JavaScript 应用读取；
- 支持流式：存成 **JSON-L** 即可用于 streaming 场景。

## 3. 环境与两个入口：开源库 vs API

```python
# 从 unstructured 开源库导入规则解析函数（本地跑）
from unstructured.partition.html import partition_html
from unstructured.partition.pptx import partition_pptx
from unstructured.staging.base import dict_to_elements, elements_to_json

# Unstructured API 客户端（处理 PDF/图像这类模型化重活）
from unstructured_client import UnstructuredClient
from unstructured_client.models import shared
from unstructured_client.models.errors import SDKError

s = UnstructuredClient(
    api_key_auth=DLAI_API_KEY,
    server_url=DLAI_API_URL,
)
```

**两个入口的分工**是本课的骨架：

| 入口 | 处理谁 | 为什么 |
|---|---|---|
| `unstructured` 开源库（本地） | HTML、PPTX | **规则化（rules-based）**解析，轻量、可本地跑 |
| Unstructured API（远程） | PDF、图像 | **模型化（model-based）**重活，算力贵、本地难搭，API 已把模型备好 |

## 4. HTML：靠标签 + NLP 判定元素类型

HTML 场景对应"从互联网抓内容进 LLM"。解析时主要看 **HTML 标签**：`<h1>` 大概率是 title，`<p>` 大概率是 narrative text。但光看标签不够，还叠加 **NLP 能力**看文本本身：

- `<p>` 里是"多句长文本" → 更可能是 narrative text；
- `<p>` 里是"短且全大写" → 更可能是 title。

即**结构化信息（标签）+ 非结构化信息（文本内容）联合判定**元素类型。

```python
# 解析一篇 Medium 博客 HTML —— 只需一行
filename = "example_files/medium_blog.html"
elements = partition_html(filename=filename)

# 元素列表 → 字典 → JSON 序列化（观察第 11~14 个元素）
element_dict = [el.to_dict() for el in elements]
example_output = json.dumps(element_dict[11:15], indent=2)
print(example_output)
JSON(example_output)          # IPython 的 JSON 组件，便于折叠浏览
```

运行后能看到某元素被正确识别为 **NarrativeText**（博客第一段），文本被抽进归一化输出。HTML 预处理对"web scraping 把互联网知识灌进 LLM"很关键。

## 5. PPTX：现代 PowerPoint 本质是一堆 XML

PowerPoint 在咨询/商务场景极常用，是扩展 LLM"组织内知识"的关键。它的抽取过程**和 HTML 很像**——因为现代 `.pptx` 文件底层就是一堆 **XML**，可以用规则逻辑解析。（老的 `.ppt` 只要先转成 `.pptx` 即可。）

```python
# 解析一份微软关于 OpenAI 的 PPTX —— 与 HTML 几乎一模一样的写法
filename = "example_files/msft_openai.pptx"
elements = partition_pptx(filename=filename)

element_dict = [el.to_dict() for el in elements]
JSON(json.dumps(element_dict[:], indent=2))
```

结果里能看到：加粗列表的第一项被正确识别为 **ListItem**，`ChatGPT` 被识别为 **Title**。**注意此处的关键收获**：PPTX 抽出的 title，和后面 PDF、前面 HTML 抽出的 title，**拿到的是同一种归一化类型** `Title`——这正是归一化的意义：一旦归一化，应用里就能"一视同仁"。

> **对比已学课程 04「Chat with Your Data」的 loader**：课程 04 的 `UnstructuredPowerPointLoader` 底层也是调 unstructured，但 LangChain 把结果直接摊平成 `Document(page_content, metadata)`，元素类型信息被吃掉了。本课直接用 `partition_pptx` 拿到**带 `type` 字段的元素**（Title/ListItem/NarrativeText），保留了下游 element-aware chunking 所需的类型信号。选择依据：需要"遇标题断块""按类型过滤"就直接用 unstructured 原生元素，只做粗粒度问答用 LangChain 封装更省事。

## 6. PDF：从"半结构化线索"切换到"视觉线索"

PDF/图像是更复杂的场景。HTML/PPTX 靠**半结构化信息**（标签、XML）找元素分界；PDF/图像则要看**视觉线索（visual cues）**：

| 视觉特征 | 更可能是 |
|---|---|
| 加粗 + 下划线、字号大 | Title |
| 较长、成块、多句、无强调 | NarrativeText |
| 网格排布 | Table |

因此 PDF 走 **API**——因为这是模型化工作负载（model-based workload），算力贵、本地难跑，API 那端模型已备好。

```python
# 解析一篇 Chain-of-Thought 论文 PDF —— 改走 API
filename = "example_files/CoT.pdf"
with open(filename, "rb") as f:
    files = shared.Files(content=f.read(), file_name=filename)

req = shared.PartitionParameters(
    files=files,
    strategy='hi_res',                 # 高精度策略：跑版面检测模型
    pdf_infer_table_structure=True,    # 额外推断表格结构（后续课程深入讲表格）
    languages=["eng"],
)
try:
    resp = s.general.partition(req)    # 模型化工作负载，需等几秒
    print(json.dumps(resp.elements[:3], indent=2))
except SDKError as e:
    print(e)

JSON(json.dumps(resp.elements, indent=2))
```

**关键收获**：API 返回的 JSON 和前面开源库序列化出来的 JSON **长得几乎一样**——同样是 document elements 列表。文档顶部加粗的 "All experimental results" 被识别为 **Title**，拿到和 PPTX、HTML 中 title **完全相同的归一化类型**。表格也被识别出来（细节留到后续课程）。

> **对比 Document AI（LandingAI 那类抽取）**：PDF 这一步和 Document AI 走的技术路线其实撞车——都用**版面检测 + 视觉模型**读非文本流的 PDF。区别在目标：Document AI 把"发票金额""合同甲方"抽成结构化字段入库；本课把整页打散成 Title/NarrativeText/Table 元素流灌进 RAG。同一套 document layout analysis 技术，服务两种下游诉求。判断用哪条：**要字段就用 Document AI，要语料就用 Unstructured**。

## 7. 归一化的全景：三种格式，一种输出

```
medium_blog.html ─ partition_html ─┐   (规则, 本地)
msft_openai.pptx ─ partition_pptx ─┼─→ [ document elements 列表 ] ─→ JSON 序列化落盘
CoT.pdf ───────── Unstructured API ┘   (模型, 远程)
   不同解析路径                          统一的 Title/NarrativeText/List/Table
```

课程还演示了 File Upload 小组件，可上传自己的文件（如 `el_ninu.html`）复用 `partition_html` 流程试跑。

## 本课总结

| 要点 | 一句话 |
|---|---|
| 归一化动机 | 一套下游代码通吃所有格式，抽取贵、下游便宜 |
| 序列化选 JSON | 通用/HTTP 标准/跨语言/可流式（JSON-L） |
| 两个入口 | 开源库规则解析 HTML+PPTX（本地）；API 模型解析 PDF+图像（远程） |
| HTML | 标签（`<h1>`/`<p>`）+ NLP 联合判定元素类型 |
| PPTX | 底层是 XML，规则可解析，写法与 HTML 几乎相同 |
| PDF | 靠视觉线索，模型化重活走 API，`strategy='hi_res'` |
| 统一收敛 | 三种格式最终都是同一种 elements 列表 + 相同 `Title` 等类型 |

> **记忆点（引出 L3）**：本课把三种格式都归一化成了 elements 列表，但只用到了元素的 **text 和 type**。每个元素其实还挂着一堆 **element metadata**（page number、parent_id、file type……）。L3 就来兑现这批元数据的价值——用它做 **hybrid search**（Chroma 里语义相似 + 元数据过滤），并用元素类型做 **element-aware chunking**（`chunk_by_title`，遇标题断块）。
