# L4 · 从 10-K 文本从零构建知识图谱（chunking → Chunk 节点 → 向量索引 → RAG 链）

> 课程：Knowledge Graphs for RAG（DeepLearning.AI × Neo4j）
> 本课任务：前两课都在用现成的图。这次从一份真实的 SEC **Form 10-K**（NetApp 年报）出发，走通完整构建管道：LangChain 切 chunk → 每个 chunk 变成图节点 → 建向量索引算 embedding → 接 LangChain RAG 链与文档对话。

## 0. 数据源：SEC Form 10-K

美国上市公司每年必须向 SEC 提交 Form 10-K 年度报告，公开可查（EDGAR 数据库）。里面有大段大段的文本：行业趋势、技术综述、风险因素——正是 RAG 想"聊"的非结构化数据。

课前预处理（讲师已做好，非本课重点）：下载的原始文件是 XML → 清洗抽取 → 存成 JSON。抽了两类东西：

- **标识元数据**：`cik`（Central Index Key，SEC 给公司的唯一标识）、`cusip6`、公司名 `names`、`source`；
- **四大文本节**：`item1`（业务）、`item1a`（风险因素）、`item7`（管理层讨论）、`item7a`——之后要 chat 的大文本体。

本课只处理**一份** 10-K（NetApp）；实际场景成百上千份，同样的步骤逐份重复即可。

**作战计划**：① 每节文本切 chunk（LangChain）→ ② 每个 chunk 成为图节点（原文 + 元数据作属性）→ ③ 建向量索引 → ④ 算 embedding 填充 → ⑤ 相似度检索 + RAG 问答。

## 1. 常量先行：向量索引的四件套

```python
VECTOR_INDEX_NAME = 'form_10k_chunks'        # 索引名
VECTOR_NODE_LABEL = 'Chunk'                  # 索引哪种节点
VECTOR_SOURCE_PROPERTY = 'text'              # 源文本属性
VECTOR_EMBEDDING_PROPERTY = 'textEmbedding'  # 向量属性
```

后面 Neo4j 侧建索引和 LangChain 侧 `Neo4jVector` 都引用同一组常量——两个系统对齐配置的锚点。

## 2. Chunking：RecursiveCharacterTextSplitter

先读 JSON 确认结构（`json.load` → dict，key 就是 item1/item1a/... + 元数据字段），`item1` 一节文本就非常长——这正是要 chunking 的原因：不能把整节塞进一条记录。

```python
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size = 2000,      # 每块 2000 字符
    chunk_overlap = 200,    # 相邻块重叠 200，语义不被切断
    length_function = len,
)
item1_text_chunks = text_splitter.split_text(item1_text)  # item1 切出 254 块
```

关键的 chunk 记录构造函数——**每个 chunk 带全套元数据**：

```python
def split_form10k_data_from_file(file):
    chunks_with_metadata = []
    file_as_object = json.load(open(file))
    for item in ['item1','item1a','item7','item7a']:   # 只处理四大文本节
        item_text_chunks = text_splitter.split_text(file_as_object[item])
        chunk_seq_id = 0
        for chunk in item_text_chunks[:20]:            # 演示用：每节只取前 20 块
            form_id = file[file.rindex('/')+1 : file.rindex('.')]  # 文件名 → 表单 ID
            chunks_with_metadata.append({
                'text': chunk,                          # 原文
                'f10kItem': item,                       # 属于哪一节
                'chunkSeqId': chunk_seq_id,             # 节内序号
                'chunkId': f'{form_id}-{item}-chunk{chunk_seq_id:04d}',
                # ↑ 全局唯一 ID：表单-节-序号，之后 MERGE 的幂等键
                'formId': form_id, 'names': ..., 'cik': ..., 'cusip6': ..., 'source': ...,
            })
            chunk_seq_id += 1
    return chunks_with_metadata
```

> **架构师视角**：`chunkId = formId-item-chunk0004` 这种**确定性、可读、含出处**的 ID 设计是整条管道的承重墙——它同时服务三件事：MERGE 幂等（重跑不重复建节点）、溯源（answer 能指回 10-K 第几节第几块）、以及 L5 要做的结构化关系（`chunkSeqId` 让"下一块"可计算，才能连出 NEXT 链表）。chunking 时把元数据一次带够，比事后回填便宜得多——这正是 3-retrieval.md 子决策 0"摄取/解析是检索质量真正瓶颈"的具体写照。

## 3. Chunk → 图节点：MERGE + 唯一约束

```cypher
MERGE (mergedChunk:Chunk {chunkId: $chunkParam.chunkId})
-- 按 chunkId 匹配，不存在才创建（幂等 upsert）
ON CREATE SET                       -- 只在"新建"时才写这些属性
    mergedChunk.names  = $chunkParam.names,
    mergedChunk.formId = $chunkParam.formId,
    mergedChunk.cik    = $chunkParam.cik,
    ...
    mergedChunk.text   = $chunkParam.text
RETURN mergedChunk
```

```python
kg.query(merge_chunk_node_query,
         params={'chunkParam': first_file_chunks[0]})
# 整条 chunk 记录作为一个参数字典传入，字段名两侧对齐
```

批量导入前先加**唯一性约束**（防重复 chunk 的保险丝，本身也是索引）：

```cypher
CREATE CONSTRAINT unique_chunk IF NOT EXISTS
FOR (c:Chunk) REQUIRE c.chunkId IS UNIQUE
```

然后 for 循环对所有 chunk 逐条 MERGE → 建出 **23 个节点**（每节限 20 块，item1 满 20、其余三节各只有 1 块），`MATCH (n) RETURN count(n)` 验证通过。此时图的形状：一堆孤立的 Chunk 节点，**还没有任何关系**。

> **对比《Knowledge Graphs for AI Agent API Discovery》(SAP) 的 SPARQL CONSTRUCT 构图**：SAP 课把图形状写在 CONSTRUCT 模板里、Python 只是通用执行器（声明式），源头是**有 schema 的结构化 CSV**，映射完全确定；本课是 **Python 过程式循环 + MERGE 逐条 upsert**，源头是**非结构化文本**，"schema"（Chunk 节点长什么样）隐含在 chunk 记录的字典结构里。共同点是两边都没让 LLM 抽实体——chunk 化是**无损、零幻觉**的构图：不理解文本，只切分和编目。GraphRAG 那种 LLM 抽实体-关系的构图是第三条路线，成本和幻觉风险都高一档。

## 4. 向量索引 + 填充：与 L3 同款，换了主角

```cypher
CREATE VECTOR INDEX `form_10k_chunks` IF NOT EXISTS
FOR (c:Chunk) ON (c.textEmbedding)
OPTIONS { indexConfig: {
  `vector.dimensions`: 1536,               -- 仍是 OpenAI 默认配置
  `vector.similarity_function`: 'cosine'
}}
```

```cypher
MATCH (chunk:Chunk) WHERE chunk.textEmbedding IS NULL
-- IS NULL 过滤 = 天然的增量语义：只补算还没有向量的节点
WITH chunk, genai.vector.encode(
    chunk.text, "OpenAI",
    { token: $openAiApiKey, endpoint: $openAiEndpoint }) AS vector
CALL db.create.setNodeVectorProperty(chunk, "textEmbedding", vector)
```

跑完 `kg.refresh_schema()` 让 LangChain 重新感知图 schema——Chunk 节点有了 textEmbedding（LIST）属性，关系仍然为零。

再包一个检索 helper（与 L3 的查询同构，参数化了索引名和 top_k=10）：

```python
def neo4j_vector_search(question):
    vector_search_query = """
      WITH genai.vector.encode($question, "OpenAI", {...}) AS question_embedding
      CALL db.index.vector.queryNodes($index_name, $top_k, question_embedding)
        YIELD node, score
      RETURN score, node.text AS text
    """
    return kg.query(vector_search_query, params={...})
```

问 "In a single sentence, tell me about Netapp." → 返回的是**带相似度分数的原始 chunk 文本**——检索有了，但这还不是"回答"。

## 5. 接上 LangChain：从向量检索到 RAG 问答

要真正**回答问题**而不是抛回原文，用 LangChain 把 Neo4j 包装成 vector store → retriever → QA chain 三级火箭：

```python
neo4j_vector_store = Neo4jVector.from_existing_graph(
    embedding=OpenAIEmbeddings(),
    url=NEO4J_URI, username=..., password=...,
    index_name=VECTOR_INDEX_NAME,            # 'form_10k_chunks'
    node_label=VECTOR_NODE_LABEL,            # 'Chunk'
    text_node_properties=[VECTOR_SOURCE_PROPERTY],      # 'text'
    embedding_node_property=VECTOR_EMBEDDING_PROPERTY,  # 'textEmbedding'
)   # 让 Neo4j "看起来像"一个向量库，底下仍是 Cypher 做相似度检索

retriever = neo4j_vector_store.as_retriever()

chain = RetrievalQAWithSourcesChain.from_chain_type(
    ChatOpenAI(temperature=0),   # 回答的 LLM
    chain_type="stuff",          # 检索结果直接塞进 prompt
    retriever=retriever,
)
```

配一个 `prettychain(question)` helper（调 chain、只取 answer 字段、`textwrap.fill` 排版）就能提问了：

| 问题 | 回答 |
|---|---|
| What is NetApp's primary business? | 企业存储与数据管理、云存储与云运维（真回答，不是原文块）|
| Where is NetApp headquartered? | San Jose, California ✓ |
| Tell me about NetApp（限一句）| 略啰嗦但服从指令 |
| **Tell me about Apple**（限一句）| 把 Apple 描述得和 NetApp 一样——**经典幻觉**：语料里根本没有 Apple |
| 同上 + "If you are unsure about the answer, say you don't know." | 老实说不知道 ✓ |

> **架构师视角**：Apple 这个失败案例是 RAG 的必考题——检索器**永远会返回 top-k**，哪怕最相近的块其实不相关，LLM 拿着无关上下文照样编。两道防线：prompt 侧给"不确定就说不知道"的出口（本课的修法，便宜但脆），检索侧加 score 阈值/reranker 把不相关块拦在 prompt 之外（3-retrieval.md 的正规修法）。评估维度上这就是 RAG Triad 的 groundedness——课程 05 用 TruLens 把它量化过。

## 6. 本课总结

| 要点 | 一句话 |
|---|---|
| 数据管道 | 10-K XML → JSON（四大 item + cik 等元数据）→ chunk 记录 |
| Chunking | RecursiveCharacterTextSplitter，2000 字符 / 重叠 200 |
| chunkId 设计 | `formId-item-chunk序号`：幂等键 + 溯源 + 为 L5 连边留钩子 |
| 节点创建 | MERGE + ON CREATE SET + 唯一约束，重跑安全 |
| 向量化 | 与 L3 同款：VECTOR INDEX + genai.vector.encode，IS NULL 增量填充 |
| RAG 链 | Neo4jVector.from_existing_graph → as_retriever → RetrievalQAWithSourcesChain |
| 幻觉修补 | "unsure 就说不知道" 的 prompt 出口 |

> **记忆点（引出 L5）**：讲师点破：到目前为止 Neo4j 只被当成**向量库**在用，"knowledge graph" 的图一点没发挥——23 个 Chunk 节点仍然互不相连，和 Chroma 里的 23 条向量没有本质区别。L5 开始**给节点连关系**（同节 chunk 的 NEXT 链、chunk 归属 Form 的 PART_OF 等），让检索命中一个 chunk 后能沿边拿到前后文和结构上下文——"graphy power"才真正上场。
