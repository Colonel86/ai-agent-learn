# L4 代码执行工具（Code Execution）

讲者在多个 agentic 项目里都给过 LLM "写代码 + 执行"的能力，反复被它给出的解题方案惊艳。如果还没玩过 code execution，强烈推荐试一下。

## 引子：算数应用的"工具爆炸"问题

想做一个能解数学应用题的 agent，最朴素的做法是：

- 提供 `add` / `subtract` / `multiply` / `divide` 四个工具。
- 用户问"13.2 + 18.9"，触发 `add`，没问题。

但马上就有麻烦：

- 用户问"根号 2 是多少？" → 需要新加 `sqrt` 工具。
- 又要指数？三角函数？对数？……

看一眼科学计算器有多少按键就知道：**给每个运算单独造个工具完全不可持续**。

## 解法：让 LLM 写代码，提供"代码执行"工具

只给一个工具：执行任意代码。prompt 大致是：

> 写代码解答用户问题。把 Python 代码用 `<execute_python>...</execute_python>` 标签包裹返回。

流程：

1. 用户："根号 2 是多少？"
2. LLM 输出包含两行 Python 代码的回答（带 `<execute_python>` 标签）。
3. 开发者代码用正则提取标签之间的代码。
4. 执行，得到 `1.4142...`。
5. 数值回传给 LLM，它写出格式化好的最终回答。

一个工具搞定无数运算需求。复杂一些的（如复利计算、更难的数学题）也能可靠完成。

## 执行代码的几种方式

- **Python 的内置 `exec()`**：直接跑 LLM 生成的代码字符串。简单粗暴，但有安全隐患（见下）。
- **沙箱环境**：在隔离环境里跑代码，更安全。

## 结合反思：执行失败 → 让它重试

如果生成的代码出错，把报错信息回传给 LLM，让它反思修正，再试一两次。这往往能拿到正确结果——和反思模块的思想一脉相承。

## 安全警告：真实事故

讲者团队里有人用一个 agentic coder，结果它执行了类似 `rm *.py` 的操作，把项目目录里的 Python 文件全删了。

后来这个 agent 还"道歉"了——"是的，我承认这是个非常愚蠢的错误"——但人家文件已经没了。幸好仓库有 GitHub 备份才没造成实际损失。

## 最佳实践

- **生产环境跑 LLM 生成的代码，应放进沙箱**。
- 推荐工具：
  - **Docker**：经典容器化沙箱。
  - **E2B**：轻量级沙箱环境。
- 这能限制"坏代码"造成数据丢失或敏感数据泄露的风险。

讲者坦白：实际中很多开发者图省事会直接 `exec`，单行代码的风险其实不大；但只要任务复杂或涉及敏感系统，**沙箱该上就上**。

## 它有多重要

代码执行重要到很多 LLM 训练团队会**专门优化**模型的代码生成 + 执行链路。把这个工具加进你的工具箱，应用能力会有质的跃升。

## 下一讲

到目前为止，工具都是**一个一个手工创建**接给 LLM 的。但很多团队在重复造类似的轮子。下一讲介绍一个新兴标准 **MCP（Model Context Protocol）**，能让开发者大批量地接入工具。

## 面试速答总结

**一句话**：与其给每个能力造一个工具，不如**只给"执行代码"这一个工具**——用图灵完备的代码覆盖无限能力（CodeAct 思想）；代价是必须**沙箱化执行 + 失败反思重试**来兜住安全与可靠性。

### 面试回答骨架（问"为什么要给 LLM 代码执行能力 / 怎么安全地做"）

> 1. **动机：工具爆炸**：朴素做法给每个运算造工具（add/subtract/sqrt/sin/log…），看一眼科学计算器就知道**不可持续**——能力是无限长尾，逐个造工具不收敛。
> 2. **解法：一个工具替代无数工具**：只给"执行任意代码"，LLM 写代码（如用 `<execute_python>` 标签包裹）→ 外层代码正则提取并执行 → 结果回传 → LLM 格式化输出。一个工具覆盖无限运算/数据处理需求。
> 3. **为什么强大**：代码是**图灵完备**的，能干的事极多；很多训练团队专门优化"代码生成+执行"链路，是能力上限的质变（接 CodeAct：以代码为动作空间，比 JSON 工具调用更紧凑、可组合）。
> 4. **可靠性：结合反思**：代码报错 → 把 traceback 回传 → LLM 反思修正再试一两次，往往能收敛到正确结果（接反思模式）。
> 5. **安全是硬约束（讲真实事故）**：直接 `exec()` LLM 生成的代码出过 `rm *.py` 删库事故；**生产必须沙箱**——Docker（经典容器）/ E2B（轻量沙箱），限制数据丢失与敏感信息泄露。

### 关键判断（加分点）

- **沙箱是"按风险分级"的工程取舍**：单行计算、无副作用、临时脚本——直接 `exec` 风险可接受；**一旦触及文件系统/网络/敏感系统或任务复杂，沙箱该上就上**。不是非黑即白，而是按 blast radius 决策。
- **代码执行 = LLM 的"通用工具"**：它把"工具设计"问题转化为"运行时安全"问题——杠杆极大，但把风险从"选错工具"上升到"执行任意代码"，所以隔离/权限/资源限额/审计成为新的卡点。

### 为什么这是高分答法

- 从"工具爆炸"痛点自然推导出 code execution，而非孤立背概念；
- 同时给出**能力面（图灵完备/CodeAct）+ 可靠性面（反思重试）+ 安全面（分级沙箱）**三条线，并落到真实事故与具体工具（Docker/E2B）。

**一句话收尾**：代码执行用**一个图灵完备的工具**换掉无限的工具长尾，是能力的质变；但它把风险从"选错工具"提升到"跑任意代码"，所以**沙箱化 + 失败反思**是把这把双刃剑握稳的前提。
