# L6 延迟与成本优化（Latency & Cost Optimization）

## 优先级排序：质量 > 成本/延迟

讲者给团队的建议：**先把输出质量做对，再优化成本和延迟**。

不是说成本/延迟不重要，而是：

- 把质量做高通常是最难的一步。
- 质量没到位前，成本/延迟优化得再好也没意义。

讲者亲历："上线后用户太多导致成本爆炸"——这其实是个**幸福的烦恼**。再去优化也不迟。

## 优化延迟：先 benchmark 每一步

跟错误分析的套路一致——**先量化，再下手**。

研究 agent 举例的耗时分布：

| 步骤 | 平均耗时 |
|---|---|
| LLM 生成搜索词 | 7s |
| Web search | 5s |
| ……中间步 | 3s |
| Web fetch | 11s |
| LLM 写最终文章 | 18s |

看完一目了然——**最后的写文章 LLM 调用 + Web fetch 是最大头**。

### 常见优化手段

1. **并行化**：能并行的步骤就别串行（典型例子：多个 web fetch 同时拉）。
2. **换小模型 / 快模型**：18 秒的那步换更小模型，看质量是否够用。
3. **换 provider**：不同 LLM API provider 的吞吐和延迟差距很大，有些公司有**专用硬件**让某些开源模型跑得飞快——值得对比。

## 优化成本：同样先 benchmark

每步算成本，找最大头：

- **LLM tokens**：按 input/output 长度计费。
- **API 调用**：很多服务按次数计费。
- **计算资源**：自己跑的步骤按服务器成本算。

把每步的钱算清楚（如"这一步平均 0.04 美分、那一步 1.6 美分"），就能锁定优化重心：

- 换更便宜的 LLM。
- 换更便宜的 API provider。
- 减少调用次数或 token 用量。

## 一个常被忽略的副作用

Benchmark 同样能告诉你**哪些步骤不值得优化**——占比太小，省了也没意义。这能避免在小头部上浪费时间。

## 核心方法论

> 延迟也好、成本也好——**先逐步骤量化，再决定改哪里**。和错误分析、组件级 eval 是同一个思路：用数据驱动决策，不要凭直觉乱投精力。
