# Long-Term Agentic Memory With LangGraph —— 总结回顾

> 课程：**Long-Term Agentic Memory With LangGraph**（DeepLearning.AI × LangChain，讲师 Harrison Chase）
> 用途：一页式快速回顾。逐课详记见各 `L*` 笔记。

---

## 一句话主线

> **没有长期记忆的 Agent 像每次都失忆的助理。把记忆按人类认知分成三类——Semantic（事实）、Episodic（案例）、Procedural（规则）——分别装进 Agent 的不同位置，配合 Hot Path / Background 两种更新模式，Agent 就能跨会话越用越懂你。**

全课贯穿一个**邮件助理**项目：Baseline（无记忆）→ 逐课加上三类记忆，每类记忆解决一个真实痛点。

---

## 核心心智模型（L0–L1，全课总纲）

### 三大记忆类型对照

| 类型 | 本质 | 人类类比 | Agent 中的形态 | 装在哪（本课） | 更新模式 |
|---|---|---|---|---|---|
| **Semantic** | 事实 / 知识 | 课本知识、别人的生日 | 向量库里的事实条目 | Response Agent 的读写工具 | Hot Path |
| **Episodic** | 经历 / 案例 | 去迪士尼的那次经历 | Few-shot 示例（输入+期望输出） | Triage Router 的 prompt 注入 | Background |
| **Procedural** | 规则 / 指令 | 骑自行车、做事原则 | **system prompt 本身** | Triage + Response 的 prompts | Background（优化器） |

### 设计任何 Agent 时必问的三个问题

1. Agent 需要记住**人/地/物的事实**吗？→ Semantic
2. Agent 需要从**过去案例**学习吗？→ Episodic
3. Agent 需要**学习更好的指令**吗？→ Procedural

### 两种更新模式

| 模式 | 流程 | 取舍 |
|---|---|---|
| **Hot Path** | Agent 响应当下即时读写记忆 | ✅ 立即生效 ❌ 增加响应延迟、Agent 职责变重 |
| **Background** | Helper Agent / 优化器异步整理 | ✅ 主路径不卡顿 ❌ 非即时生效、系统更复杂 |

选型：刚说的关键偏好→Hot Path；历史汇总/模式提取/prompt 演进→Background。

## 逐课速查

### L2 — Baseline 邮件助理（无记忆）

- **双层架构**：外层 `StateGraph` 编排（Triage Router → Response Agent / END）；内层 Response Agent 是 `create_react_agent` 一键生成的 ReAct 循环（工具：write_email / schedule_meeting / check_calendar_availability，均 mock）。
- **Triage 用结构化输出**：`Router(BaseModel)` 含 `reasoning` + `classification: Literal["ignore","respond","notify"]`，`llm.with_structured_output(Router)` 保证三选一；分诊用小模型（gpt-4o-mini）省钱。
- **关键新原语 `Command`**：节点返回 `Command(goto=下一节点, update=状态更新)`——路由和写状态一次完成；类型签名 `Command[Literal["response_agent", "__end__"]]` 供静态校验和画图。
- **Prompt 是函数不是字符串**：`create_prompt(state)` 每轮按 state 动态拼接。
- **模块化的远见**：profile / triage_rules / agent_instructions 故意拆出独立 dict——它们就是后面要变成"可被记忆系统自动迭代"的部分。

### L3 — + Semantic Memory（语义记忆，Hot Path）

- 两个新组件：**LangGraph Store**（`InMemoryStore(index={"embed": "openai:text-embedding-3-small"})`，记忆自动向量化）+ **LangMem** 工具（`create_manage_memory_tool` / `create_search_memory_tool`）。
- **Namespace 三层结构** `("email_assistant", "{langgraph_user_id}", "collection")`：模板变量运行时从 `config={"configurable": {"langgraph_user_id": "lance"}}` 注入，**多用户记忆完全隔离**。
- 接入只需两处：工具列表加上两个 memory 工具 + `create_react_agent(..., store=store)` 和 `graph.compile(store=store)`。
- **Agent 自主决定何时读写**："Jim is my friend" → 主动调 manage_memory 存；"who is jim?" → 主动调 search_memory 查。两次完全独立的邮件调用，靠记忆串联上下文——这就是长期记忆与对话历史的本质区别。
- 调试：`store.list_namespaces()` / `store.search(ns, query=...)`（返回余弦相似度 score）。

### L4 — + Episodic Memory（情景记忆 / Few-Shot，装在 Triage）

- 案例结构 = **完整输入 + 期望输出**：`{"email": {...}, "label": "ignore"}`，存进 namespace 末段 `"examples"`（同一 store，namespace 区分记忆类型）。
- **检索是节点代码自动做的**（不是 LLM 调工具）：`triage_router(state, config, store)`——LangGraph 自动注入 config/store；用当前邮件做 query 向量搜索相似案例 → `format_few_shot_examples` 格式化（正文截断 400 字符）→ 注入 prompt。
- 关键 prompt 工程：**"Follow these examples more than any instructions above"**——示例优先级压过通用规则。
- 端到端效果：用户对某封邮件打 "ignore" 标签存为案例 → 下次**语义相似**（换发件人、改措辞）的邮件也被忽略——**没有训练没有微调的 in-context few-shot learning**；换 user_id 则互不影响。

### L5 — + Procedural Memory（程序记忆 / 自我演化的 Prompt）

- 核心思想：**prompt 不再是源码里的固定字符串，而是住在 store 里、可被 LLM 改写的运行时数据**。四个 prompt 入库：`triage_ignore` / `triage_notify` / `triage_respond` / `agent_instructions`，namespace 为 `(user_id,)`。
- **Lazy-init 模式**：`store.get` 为 None 时把硬编码默认值播种进去——新用户首次运行也能正常工作。
- **优化器**：`create_multi_prompt_optimizer("anthropic:claude-3-5-sonnet-latest", kind="prompt_memory")`，输入 `trajectories`（对话轨迹+用户反馈字符串）和 `prompts` 列表（每条含 `name / prompt / update_instructions / when_to_update`），两阶段工作：先用 `when_to_update` 判断反馈影响哪些 prompt，再改写被选中的；输出与输入同构，diff 后写回 store。
- 演示："Always sign your emails \`John Doe\`" → 改写 main_agent prompt；"Ignore any emails from Alice Jones" → 改写 triage_ignore——**优化器自己路由反馈到正确的 prompt**。

### Episodic vs Procedural：两种"教 Agent"的对比（L5 重点）

| 维度 | Episodic | Procedural |
|---|---|---|
| 存储形式 | 完整案例（input + label） | 一段自然语言规则 |
| 生效方式 | few-shot 注入 prompt | system prompt 本身被改写 |
| 适用 | "类似这封的邮件这样处理"（具体例子） | "签名写 John Doe"（通用规则） |
| 泛化 | 靠向量相似度 | LLM 直接执行规则 |

生产中三类记忆**叠加共存**，互不替代：Semantic 管知识、Episodic 管经验、Procedural 管规则。

## 关键 API 速查

| API | 用途 |
|---|---|
| `InMemoryStore(index={"embed": ...})` | 长期记忆存储（生产换 Postgres/Redis） |
| `store.put(ns, key, value)` / `get` / `search(ns, query=)` / `list_namespaces()` | 记忆 CRUD + 语义检索 |
| `create_manage_memory_tool(namespace=)` / `create_search_memory_tool` | LangMem：给 Agent 的记忆读写工具 |
| `create_multi_prompt_optimizer(model, kind="prompt_memory")` | LangMem：反馈 → prompt 自动改写 |
| `("app", "{langgraph_user_id}", "collection"/"examples")` | namespace 模板：多租户 + 记忆类型隔离 |
| `config={"configurable": {"langgraph_user_id": ...}}` | 运行时注入用户身份 |
| `create_react_agent(model, tools=, prompt=fn, store=)` | 预制 ReAct Agent |
| `Command(goto=, update=)` | 节点同时控制路由与状态更新 |
| `def node(state, config, store)` | 节点函数的依赖注入签名 |
| `llm.with_structured_output(PydanticModel)` | 强约束分类输出 |

## 架构师视角的四个要点

1. **记忆类型选择是行为设计，不是存储设计**：三类记忆的差别不在存哪（都在同一个 store，靠 namespace 区分），而在**怎么影响 Agent 行为**——Semantic 补知识（LLM 主动调工具）、Episodic 改判断（节点代码自动注入 few-shot）、Procedural 改规则（重写 system prompt）。先问"想改变 Agent 的什么"，再选记忆类型。
2. **Hot Path vs Background 是延迟与复杂度的取舍**：即时生效的代价是主 Agent 职责变重、响应变慢；后台模式干净但有生效延迟。课程的分配（Semantic 走热路径、Episodic/Procedural 走后台）是合理默认，不是定律。
3. **"用户教 Agent"有三个杠杆，成本递增、泛化递增**：打一个标签（Episodic 案例）< 给一句反馈（Procedural 优化器改 prompt）< 改代码。把前两个杠杆做进产品，Agent 才能不发版就持续进化——这是个性化 Agent 与静态 Agent 的分水岭。
4. **多租户隔离要从第一天设计进 namespace**：`(app, user_id, type)` 三层结构 + config 注入，让"Harrison 教的规则不污染 Andrew"成为结构保证而非测试用例。任何面向多用户的记忆系统，隔离边界都该是一等公民。
