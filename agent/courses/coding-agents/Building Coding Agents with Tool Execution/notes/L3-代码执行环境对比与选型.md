# L3 · 代码执行环境对比与选型（Local / Container / gVisor / MicroVM / 托管沙箱）

> 课程：Building Coding Agents with Tool Execution（DeepLearning.AI × E2B）
> 本课任务（概念课，无代码）：认识运行 LLM 生成代码的各类环境——local execution、containers、sandbox（如 microVM）——并学会**按 use case 选对环境**。

## 0. 本课问题：LLM 生成的代码到底该在哪跑

L2 的 agent 用一行 `exec(code)` 在 notebook 本机裸跑生成代码。本课把"在哪跑"变成一个正式的选型问题，候选项三大类：**本地执行、Docker/容器、sandbox 环境**。选哪个取决于一系列因素，其中头号挑战是**安全**。

直接运行 LLM 生成的动作，可能出什么事？字幕里列了完整清单：

- 攻击者**读取系统敏感数据**，甚至**注入恶意代码**；
- LLM **意外泄露你的 API keys**；
- 恶意代码**搞崩整个应用**；
- 还有**扩展性问题**和数不清的其他漏洞。

## 1. Local Execution：coding assistant 的默认，production 的红线

用过 Claude Code 或 Cursor 就熟悉这个模式：**你期望 agent 直接在你机器上跑代码、改文件**——这是 coding assistant 的产品形态决定的。但它有硬伤：

- **没有完全隔离**：模型生成了不该生成的代码，就能读取或修改你机器上的**任何东西**；
- 安全之外还有资源上限：**笔记本资源很快耗尽**；
- 环境会**变脏**（包冲突）；
- **无法规模化**让其他用户使用你的 agent。

结论：想做 production 的东西，local execution 很快撞墙。Lovable、Rork 以及当下从 deep research 到 coding agent 的众多热门 agent 产品，**全部采用沙箱方案**来扩展到数千用户。

## 2. Docker / 容器：OS 级隔离，但共享宿主内核

Docker 通过 **namespaces** 在独立进程中跑代码，提供**操作系统级隔离**——比 local 强。但关键弱点：**所有容器共享同一个宿主内核（Host Kernel）**。

```
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ Container A │ │ Container B │ │ Container C │   ← 任一被攻破,
└──────┬──────┘ └──────┬──────┘ └──────┬──────┘     就有路径提权触达宿主
       │  syscall 直达  │               │
┌──────▼───────────────▼───────────────▼──────┐
│              Host Kernel（共享）              │   ← 攻击面大
└──────────────────────────────────────────────┘
```

- 只要**一个容器被攻破**，攻击者就有潜在路径**提权触达宿主机**；
- **同时跑多个不受信代码实例**（多容器）时，这个风险被放大——恰恰是 agent 平台的典型负载；
- 默认情况下**容器的 syscall 直达宿主内核**，意味着更大的攻击面。

## 3. gVisor：给容器加一层用户态内核

让 Docker 更安全的一个思路是**缩小攻击面**——例如 Google 开源的用户态内核 **gVisor**：

```
┌─────────────┐
│  Container  │
└──────┬──────┘
       │ syscall
┌──────▼──────┐
│   gVisor    │  ← 用户态自己实现大部分 Linux syscall 接口,
└──────┬──────┘     像"中间人"一样拦截 syscall,"关住"容器
       │ 少量必要调用
┌──────▼──────┐
│ Host Kernel │
└─────────────┘
```

gVisor 把容器"关进监狱"（jail）：限制其可访问的东西，自己实现了大部分 Linux syscall 接口，实际上是在**拦截 syscall**——容器先和 gVisor 说话，而不是直接对宿主内核。

**代价**：一定的性能开销、偶发的兼容性缺口、调试/追踪工具链不同。而且 **gVisor 也不是 100% 安全**——它仍依赖宿主内核，其复杂实现的内层漏洞依然可被利用。

## 4. Sandbox 与 MicroVM：让生成代码永远无法伤到宿主

至此目标已清晰：**LLM 生成的代码，永远不应有能力危害宿主系统**。好答案是 **sandbox**：

> Sandbox = 用于运行不受信代码的**受限隔离环境**，把对宿主机的任何影响降到最小。相比容器，sandbox 提供**真正的进程隔离**，因此成为安全运行不受信 / LLM 生成负载的通用地基。

Sandbox 的实现路线包括：OS 级隔离、**WebAssembly**、以及**轻量级 microVM**（Firecracker、QEMU、Cloud Hypervisor）。

其中对 coding agent 特别合适的是 **MicroVM**：

- 基于内核的**轻量级虚拟机**，剥掉了不必要的硬件仿真，为**快速启动、高效运行**而设计；
- **每个 microVM 跑自己的 guest kernel**——这是与容器的本质区别，隔离更强，同时保持接近原生的性能；
- 代表实现 **AWS Firecracker**：支撑着 AWS Lambda 和 Fargate。

```
容器:                          microVM:
┌───────────┐                 ┌───────────────────┐
│ Container │                 │  App              │
│  (进程)   │                 │  Guest Kernel ←自带│
└─────┬─────┘                 └─────────┬─────────┘
      │ 共享                            │ 虚拟化边界(VMM)
┌─────▼─────────┐             ┌─────────▼─────────┐
│  Host Kernel  │             │    Host Kernel    │
└───────────────┘             └───────────────────┘
  隔离弱、启动快                 隔离强、仍近原生性能
```

> **对比《AI Agentic Design Patterns with AutoGen》L5**：AutoGen 给的执行器选项是 `LocalCommandLineCodeExecutor`（宿主 shell 直跑，仅 timeout 一道闸）和 Docker 容器执行器两档——当时笔记里已按 7-safety-guardrails.md 判了"教学可以、生产是红线"。本课等于把那张隔离谱系图逐级讲透：AutoGen 的两档只覆盖谱系最左端，而 agent 平台真正的生产共识（Lovable、E2B 这批产品）落在 **microVM 档**——容器与 microVM 之间差的正是那个"自带 guest kernel"。

## 5. MicroVM 的运维代价与托管 Sandbox Provider

既然 microVM 隔离最强，为什么不到处用？**取舍**：

- **搭建更难**：不像 Docker 一条命令跑起来，需要更多工程知识与手工配置；
- **社区与生态更小**：没有同等的工具链支持，没有 Docker Hub 那样的公共镜像仓库；
- **扩展是自己的事**：基础设施要自己管——更新、编排、以及修补自己技术栈里的安全漏洞。

microVM 技术本身很好，但**直接自己跑的运维开销让多数团队难以采用**。于是随着 AI agent 兴起，出现了 **sandbox provider**（E2B、Deno、Modal 等），在 sandbox 技术之上叠加托管收益：

- **预构建 sandbox 模板**（面向不同 use case）；
- **长时运行会话**、**secrets 与 API 管理**；
- 服务千级甚至百万级用户所需的**可扩展性**——底层编排由 provider 管理，**你专注 agent，不管基础设施**。

用起来的形态：**创建一个 sandbox 实例，把代码传给它的 run 方法**——就这么简单（L4 实操）。

> **架构师视角**：本课暗含一条经典的 build-vs-buy 决策链——隔离需求逼你从 local 走到 microVM，运维成本又逼你从自建 microVM 走到托管 provider。判断题其实是两问：**① 跑的是谁的代码？**（自己写的可信代码 → local/容器就够；LLM 生成或用户提交的不受信代码 → 必须真隔离）**② 服务多少人？**（自用 → coding assistant 模式可接受；多租户产品 → 托管沙箱几乎是默认解）。注意讲师身份：本课由 E2B 讲授，"provider 比自建香"的结论方向正确，但成本/供应商锁定这一侧没展开——选型时要自己补上出口成本这一轴。

## 6. 选型总表

| 维度 | Local | Docker/容器 | 容器 + gVisor | MicroVM（自建） | 托管沙箱（E2B 等） |
|---|---|---|---|---|---|
| 隔离机制 | 无（同进程/同机） | namespaces，进程级 | 用户态内核拦截 syscall | 独立 guest kernel + VMM | microVM 等 + 平台托管 |
| 内核 | 宿主 | **共享宿主内核** | 仍依赖宿主内核 | **每 VM 自带 guest kernel** | 同 microVM |
| 攻击面 | 最大（直达一切） | syscall 直达宿主内核 | 明显缩小，仍非 100% | 最小（虚拟化边界） | 同 microVM |
| 上手/运维 | 零成本 | 一条命令，生态大 | 中等（兼容性/调试差异） | 难：手工配置、自管编排与补丁 | 创建实例即用，编排全托管 |
| 性能 | 原生 | 近原生 | 有性能开销 | 近原生（剥掉硬件仿真） | 近原生 |
| 典型场景 | 个人 coding assistant（Claude Code/Cursor） | 可信代码、内部工具 | 想继续用 Docker 生态但要更安全 | 有平台团队的大厂（AWS Lambda/Fargate 即 Firecracker） | 面向多用户的 agent 产品（Lovable、Rork 这类） |

> **对比 7-safety-guardrails.md（沙箱层）**：本课的谱系与选型包写的隔离强度谱逐点对上——"进程级 → 容器（Docker）→ 用户态内核（gVisor）→ microVM（Firecracker）→ 托管代码沙箱（E2B 类）/ WASM"。选型包还多给了本课没讲的**配套四件套**：网络出站白名单、文件系统只读/临时、CPU/内存/超时配额、**密钥不进沙箱**——注意托管 provider 的"secrets 管理"功能解的正是最后一条。两边互补成完整答案：本课给"隔离层怎么选"，选型包给"选完之后还要配什么"。

## 7. 本课总结

| 要点 | 一句话 |
|---|---|
| 核心目标 | LLM 生成的代码**永远不应能危害宿主系统** |
| Local | coding assistant 的默认形态，但无隔离、资源有限、无法多用户扩展 |
| 容器 | namespace 隔离，但**共享宿主内核** = syscall 直达 = 攻击面大 |
| gVisor | 用户态内核当中间人拦截 syscall；代价是性能/兼容性，且仍非 100% 安全 |
| MicroVM | 自带 guest kernel 的轻量 VM（Firecracker），强隔离 + 近原生性能 + 快启动 |
| Provider | E2B/Deno/Modal 把 microVM 的运维开销托管掉：模板、长会话、secrets、规模化 |
| 选型两问 | 跑谁的代码（可信 vs 不受信）× 服务多少人（自用 vs 多租户） |

> **记忆点（引出 L4）**：谱系走到头，答案落在"托管沙箱：创建实例、把代码递给 run"。L4 就动手兑现这句话——用 E2B sandbox 在云端跑 agent 生成的多语言代码、操作 sandbox 文件系统：上传数据集、保存产出，甚至托管一个小型 web 应用。
