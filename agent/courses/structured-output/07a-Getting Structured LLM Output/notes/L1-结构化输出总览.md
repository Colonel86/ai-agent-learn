# L1 结构化输出总览

## 核心问题:为什么不能只靠"提示词让模型输出 JSON"

聊天场景下自由文本没问题,人类能自己解析;但写软件要用代码解析模型输出。"手写规则去 parse 自由文本"是最朴素的做法,极易出错、难扩展——课程的例子:产品经理临时加一条"如果是投诉就转人工"的需求,手写解析器立刻变得又臭又长(既要解析"是不是投诉",又要解析回复正文)。而如果模型输出本身就是可预测的 JSON(如 `{"is_complaint": true, "response": "..."}`),这类改动只是多判断一个字段,复杂度几乎不涨。

这是全课主线:**从 "prompt hacking"(改提示词→看输出→再改)走向"真正的 AI 工程"(输出格式本身可预测、可编程)**。

## 三条技术路线的取舍

| 路线 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 供应商自带结构化输出 | OpenAI Structured Outputs、JSON mode、function calling | 上手最快,和聊天场景无缝衔接,供应商持续优化 | 绑定单一供应商,换供应商要重写;字段约束能力有限(只能字段名+类型,不能约束格式如日期正则);有说法认为强制结构化会轻微拉低某些评测表现 |
| 重提示库(re-prompting) | Instructor、LangChain | 跨供应商可移植(基本只换 base_url + key);比供应商原生支持更丰富的字段约束(如正则) | 失败要重试,增加延迟和 token 成本;不保证成功(重试次数用尽仍失败) |
| 结构化生成 / 约束解码 | Outlines、SGLang、Guidance、XGrammar | 直接操作 logits,保证 100% 合法输出,推理阶段几乎零额外开销,格式远超 JSON(正则能描述的都行) | 必须拿得到模型 logits——只能用开源模型或自托管模型;闭源 API 拿不到 |

## 约束解码的直觉(为 L4/L5 铺垫)

LLM 每一步生成本质是:给所有候选 token 算概率分布(logits)→ 采样一个 → 拼回 prompt → 重复,直到结束符。约束解码做的事:**在采样前,把不满足目标格式的 token 概率直接清零**,这样无论怎么采样,拼出来的字符串都必然合法。比"生成完再检查"高效得多,因为从根上就没有生成非法 token 的可能。

## 一条选型主线(贯穿全课)

先问一句 **"能不能拿到 logits?"**:
- 能(自托管开源模型)→ 优先约束解码(零成本、零重试、格式不受限)
- 不能,但要跨供应商 → 重提示库(Instructor)
- 只用单一供应商 + 追求最省事 → 供应商原生结构化输出 API
