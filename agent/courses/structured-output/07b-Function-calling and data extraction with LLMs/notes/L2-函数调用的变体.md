# L2 函数调用的变体:单个 / 并行 / 多函数 / 无调用 / 嵌套

## 先做个工程改进:从函数定义自动生成 prompt

上一课是手写函数描述进 prompt。这课改成用 Python 的 `inspect` 模块自动抽函数签名 + 用 `__doc__` 抽 docstring,写个 `build_raven_prompt(func_list, query)` 工具,自动为任意函数列表生成 prompt。**这是个通用工程习惯**——工具契约应该从代码自动派生,而不是手抄(手抄必然和实现漂移)。今天 MCP / 各框架的 tool 注册也是这个思路。

## 五种调用形态

| 形态 | 含义 |
|---|---|
| 单调用 | 一个查询 → 一个函数调用 |
| **并行调用** | 同一轮里模型吐出**多个**调用字符串(调同一函数多次或调多个函数)。例:一次画两个小丑,一红脸一蓝脸 |
| **多函数** | 给模型 f1…fN,它自己挑该用哪个(例:给了"画小丑"和"画领带"两个,用户只说画领带,模型就只调画领带) |
| **无调用(no call)** | 可以额外提供一个"没有相关函数"的兜底函数,模型判断没有工具能满足查询时就调它。**这点重要**——让模型能诚实地说"我没有合适工具",而不是硬凑一个错误调用 |
| **嵌套调用** | 一个函数的输入依赖另一个函数的输出:f1 的结果喂进 f2,模型在**一步内**完成 |

## 嵌套调用为什么值得单独讲

传统 agent 方案里,"先算中间结果、再算最终结果"往往要**两次 LLM 调用**。嵌套调用能把这个压进**一次**——模型直接生成 `f2(f1(...))` 这种嵌套调用串。课程例子:把"画小丑"拆成 draw_head / draw_eyes / draw_nose / draw_mouth + 一个组合函数,模型先分别调各部件、再把结果传进组合函数,一步搞定。**省 LLM 调用 = 省延迟省钱**,这是个真实的架构优化点。

## 本课最重要的实战教训:docstring 质量决定成败

课程故意演示了一个**失败案例**:让模型"画一个悲伤的小丑",结果画出来是笑的。原因是控制嘴巴弧度那个参数的 docstring 写得太模糊("控制嘴的起止角度"),模型没法把它和"悲伤"这个语义联系起来。**修复方法:把 docstring 改清楚**(明确说这个参数怎么影响小丑的情绪),模型立刻画对。

两条可迁移的结论:
1. **prompt/工具调用失败时,先检查工具描述(docstring)够不够清楚**,而不是急着换模型或加逻辑。工具描述是模型推理的输入,垃圾进垃圾出。
2. docstring 说不清的,可以**补几个 few-shot 示例**来传达。

这条直接对应你面试包 `02-tool-gateway` 里"工具契约即 prompt"那个点——工具的描述不是给人看的文档,它是模型推理的一部分,写得好不好直接影响调用准确率。
