# L0 · 课程介绍：把成熟数据库 + 向量检索拼成"省钱的 RAG"

> 课程：Prompt Compression and Query Optimization（DeepLearning.AI × MongoDB）
> 讲师：Richmond Alake（MongoDB Developer Advocate，前 ML 架构师）
> 一句话定位：这门课不教"怎么让 RAG 跑起来"，教的是**怎么让一个大规模 RAG 应用在保证相关性的前提下把成本压下来**——把一款成熟数据库（MongoDB）的传统能力和 vector search 结合起来。

## 这门课要解决的问题

开场用一个"租房推荐 RAG"贯穿全课。用户输入一句自然语言："想要一栋安静街道上的单层 ranch"——这是**语义**需求，靠 semantic search（把用户描述 embedding 后在 vector database 里找相似房源描述）来满足。但同一个用户往往还带**硬性**约束：三卧、两卫、不要泳池——这类需求更适合**传统的基于字段的检索**（数据库里显式存 bedrooms / bathrooms 等字段，按字段筛）。

课程的核心主张就是：**best of both worlds ——一个传统数据库 + 一个额外的 vector index**。不要在"纯向量库"和"纯关系库"之间二选一。

## 为什么成本是这门课的主线

RAG 把检索到的 context 塞进 prompt 交给 LLM 做最终处理。如果检索回来的 context 很长，prompt 就很长，费用随之飙升。课程给了一笔账，值得记住：

| 变量 | 取值 |
|---|---|
| 单次检索返回 | 10,000 tokens |
| 日查询量 | 1,000,000 次/天 |
| LLM 输入定价 | \$10 / 百万 tokens |
| **年成本** | **> \$36,000,000 / 年** |

结论：**在 RAG 里，"检索回来的东西越小越相关越好"不是优化项，是生存项。** 这门课后半程专门讲怎么把 retrieved results 压小。

> **架构师视角**：这笔账揭示了 RAG 成本的杠杆点不在"调用几次 LLM"，而在"每次喂进去多少 token"。token 量 = 检索命中数 × 每条文档长度。所以省钱有两条正交的路：① 检索阶段少返回、返回得准（filtering / projection / reranking，本课前半）；② 返回后再压缩（prompt compression，本课后半）。数据库能承担第①条的大部分工作——这是选 MongoDB 这类"数据库 + 向量"方案而非纯向量库的经济学理由。

## 全课要学的五种技术（按管道顺序）

1. **Pre-filter（前置过滤）**：在数据库 index 创建阶段就构建"只含常见查询字段"的索引。比如你知道用户高频按 bedroom 查，就建一个包含 bedroom 字段的索引，向量检索前先按字段裁掉不合格文档。
2. **Post-filter（后置过滤）**：先做 vector search，再对结果集应用 filter，选出满足条件的子集。大规模应用常**两者同时用**。
3. **Projection（投影）**：只返回查询结果里的**字段子集**。比如一条房源有 15 个字段，只回传 name / bedrooms / price 三个。
4. **Reranking（重排）**：语义检索出结果后，按其他数据字段（如 average star rating、number of ratings）重新排序，把更受欢迎的结果顶到前面，给 LLM 更好的 context。
5. **Prompt Compression（提示压缩）**：检索信息很长时，用一个**小而便宜、专门微调过的 LLM** 先压缩 prompt，再交给最终的大 LLM。

> **对比《Semantic Caching for AI Agents》(Redis)**：那门课省钱的思路是"**别重复算**"——把语义相近的 query 命中缓存，直接跳过 LLM 调用；省的是"调用次数"。本课省钱的思路是"**每次都算，但让每次都便宜**"——通过 filtering / projection / compression 把单次调用的 token 量压下来；省的是"单次成本"。两者正交、可叠加：生产级 RAG 通常是「semantic cache 挡掉重复查询 + 本课技术压缩未命中查询的 token」。这正是面试包 `05-context-engineering-and-caching` 里"成本优化不是单点，是一条管道"的论据。

> **一个架构判断**：这五种操作"能在应用层自己写吗？"能，但**不该**。数据库能对这些操作做性能优化，还能顺带强制执行 **role-based access control（基于角色的访问控制）**。所以它们最好在数据库里完成——把 filtering / projection 下推到数据层，既快又安全，是分层架构的默认选择。

## 课程路线

**从 vanilla vector search 起步，以 prompt compression 收尾。** 中间依次加 filtering、projection、reranking。数据集是 HuggingFace 上的 5000 条 Airbnb 房源（含 text + image embeddings），整门课围绕它搭一个"Airbnb 房源推荐 RAG"。

> **记忆点（引出 L1）**：L0 只给了"数据库 + 向量 = 省钱 RAG"的蓝图和一笔 \$36M 的账。L1 落到最朴素的一环——不带任何 filter 的 **vanilla vector search**：用 Pydantic 建模 Airbnb 数据、连 MongoDB、灌数据、建 vector search index，跑通第一条能返回结果的 RAG 管道。后面每一课都是在这条 vanilla 管道上"加一个省钱的 stage"。
