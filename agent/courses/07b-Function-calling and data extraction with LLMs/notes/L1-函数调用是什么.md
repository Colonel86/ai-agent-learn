# L1 函数调用是什么(动手第一课)

## 定义再明确一遍

Function calling = LLM 接收「自然语言查询 + 函数描述」,输出「一个能用来调用该函数的字符串」的能力。

例子:想知道纽约气温,你有个 `get_weather(city)` 函数。把查询("纽约多少度")+ 函数描述一起喂给模型,模型返回 `get_weather(city="New York")` 这个字符串。**你拿这个字符串去执行,把结果再连同原问题喂回模型,模型才给出最终自然语言回答。** 这就是完整的一个 function-calling 回合。

## 两组关键术语(面试常被追问区别)

- **function calling** = 模型"生成调用字符串"这个能力
- **tool(工具)** = 被调用的那个实际函数本身
- **通用模型 vs 专用模型**:通用模型(GPT-4 这类)什么都能答,也能做 function calling;专用模型(NexusRaven)专门为 function calling 微调,更小、延迟更低、在该任务上常能超过通用模型。这对应"模型选型"里一个真实取舍——**不是所有任务都需要一个全能大模型,一个微调过的小模型在特定任务上性价比可能更高**。

## 动手:本地 Python 工具

课程从一个 matplotlib 画图工具起步(`plot(x, y)`),演示流程:

1. 写好函数(带 docstring 说明用途)
2. 把**函数原型 + docstring 描述 + 用户查询**拼成 prompt
3. 调模型 → 拿到调用字符串(模型甚至会顺手做点数学:用户说"画 y=10x",模型把 x=[1,2,3] 算成 y=[10,20,30])
4. 执行这个字符串 → 出图

课程反复强调 **docstring 的作用**:它告诉模型"这个工具是干嘛的、什么时候该用",直接影响模型的判断质量。这点在 L2 会被放大成一个明确的教训。

## Raven 格式 vs OpenAI 格式

同一个例子,课程还用 OpenAI 的 function calling(GPT-3.5-turbo)做了一遍,对比:

- **NexusRaven**:工具用 **Python 函数格式**描述(它就是这么微调的)
- **OpenAI**:工具用 **JSON 格式**描述参数;返回的调用信息是结构化字段,需要你再抽取拼成可执行的 Python 调用

> ⚠️ 时效:Raven 的"Python prompt 格式"是它专属的历史产物。今天你用任何主流模型,都是走类似 OpenAI 那种「JSON schema 声明工具 + 结构化返回 tool_call」的标准路子(也就是 MCP 底层那套)。**记这个对比是为了理解"工具描述格式"这件事,不是记 Raven 语法。**

## 本课的本质

你做的事,是**在 LLM 训练所处的"非结构化文本世界"和代码所处的"高度结构化世界"之间架了一座桥**。这句话是整门课的主题句。
