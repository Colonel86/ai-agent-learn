# L5 · 生成数据与微调迭代闭环（working backwards + 过滤 + error analysis）

> 课程：Improving Accuracy of LLM Applications（DeepLearning.AI × Lamini/Meta）· **收官篇**
> 本课任务：用 LLM 把「其实已经够」的数据放大成训练集，跑通「生成→过滤→error analysis→再微调」的迭代闭环，把 text-to-SQL 准确率从 30% 一路顶到 95%+。文末做全课收官。

## 0. 承上：数据是最后也是最重的杠杆

L4 讲了 fine-tuning 的技术，但成败压在数据上。本课的核心反直觉是：**你的数据其实够，只是格式不对**——判据是「如果把这些数据交给一个有无限时间的人，他能不能推出正确答案？」能，就说明事实齐了，剩下的是格式转换。历史上转格式靠人肉标注，现在**只要你能说清目标格式，LLM 就能批量重塑**。

## 1. 识别「目标格式」是第一步

格式高度 application-specific，先想清楚**期望的 prompt 和期望的 response**：

| 应用 | 期望 prompt | 期望 response |
|---|---|---|
| text-to-SQL（本课） | schema + 问题 | SQL 语句 |
| 自然语言问答 | 「NBA 薪水最高的是谁」 | 自然语言答案（可由 SQL 结果转写） |
| 医疗编码 | 症状描述 | ICD code |

## 2. Working Backwards：从 schema 倒推造数据

对 text-to-SQL，**你只需要 schema**。为什么够：
- LLM **本来就会写通用 SQL**，只是不懂你的 schema 细节；
- **schema 本身包含 LLM 需要的全部事实**——就像把 schema 递给一个数据分析师，你不是指望它凭空知道事实。

于是两步链式生成：

```python
# 第一步：schema + 一个示例(问题+query) → 生成「相似但不同」的新 query
system += get_schema_s()
system += "Question: " + question + "\nQuery: " + sql + "\n"     # 给个范例
user = ("Write two queries that are similar but different to those above.\n"
        '格式化为 JSON: {"explanation": str, "sql_query_1": str, "sql_query_2": str}\n'
        # 先写解释再写 query = 编程式 CoT；并要求每条以 ; 结尾（prompt 工程小技巧）
        "First write an explanation ... then write valid sqlite queries ending with ;")

# 第二步：把生成的 query 反过来 → 生成对应的用户问题
user = ("Now consider the following query.\nQuery: " + generated_sql + "\n"
        "Write a question that this query could be used to answer.\n"
        '格式化为 JSON: {"explanation": str, "question": str}')
```

**关键注释（藏在 lab 代码里）**：生成的 query 要**尽量贴近正在失败的样本**，好让模型看到「正确该怎么写」的示范。生成出来立刻用 `check_sql_query`（打到 DB 能不能跑）过一道，无效的直接丢。

### 用采样制造 breadth

```python
# 每次从 gold set 里随机抽 3 条做示例，抽 sample_count 次
sample_size = 3
for i in range(sample_count):
    example_sample = random.sample(all_examples, sample_size)  # 每次 3 条都不同
# 每次看到不同的 3 条 → 轻推模型产出不同的 query，简单地把数据集撑大
```

> **架构师视角**：这是「用模型给模型造训练数据」的自举（bootstrapping）。廉价的多样性来自**采样组合**而非人工编写；而质量兜底来自**下游过滤**——因为「生成数据比过滤数据难得多」，所以策略是**过量生成 + 狠过滤**，而不是追求每条都完美。

## 3. 实战技巧

- **few-shot / in-context**：加「query-问题」示例帮 LLM 理解「什么是对」；**pro tip**——把**修正后的幻觉例子**也放进去，模型能学到它该学的边界；
- **生成变体**：让 LLM 换 persona（不只是「NBA 分析师」，还可以是要 executive 视角的高管），产出不同问题/query；
- **过滤生成**：复用 L3 评估里的方法（LLM judge + 确定性），可扩展地把生成结果**下采样成高质量集**；
- **error analysis**：翻「什么 work、什么不 work、各自的 pattern」——本课发现「越复杂的 query 越难」，据此调 prompt 去针对性生成。

## 4. 微调的最低要求与成本

- **技术上 1 条数据就能 memory tune / instruction fine-tune**，但 instruction fine-tuning 想保持泛化建议 **~1000 条**；
- 需要 **prompt/response 成对**；memory tuning 尤其要求**把想学的事实放进 response**；
- 一行 `llm.train(...)` 即可（Lamini 托管），也可自己 roll 超参与前后向。

**时间/算力基准（单卡 A100，~40% MFU，或等效 AMD MI250）**：

| 方式 | 准确率 | 时间 | 算力 |
|---|---|---|---|
| instruction fine-tuning（LoRA） | ~50% | 2.5 分钟 | 19.2 petaflops |
| memory tuning（**未优化** LoRA） | 千条事实上高得多 | **4 小时** | 1.9 **exa**flops |
| **Lamini memory tuning（优化后）** | 高 | **1 分钟** | 24 petaflops |

未优化版之所以慢，是因为要把特定事实的 **loss 打到零**；Lamini 用 L4 讲的那些优化把它压回分钟级。

## 5. 迭代是艺术：从 95% 到 nines

- 现实是**要很多轮**（10-30 轮，本课约 20 轮）跨不同数据 pipeline 才到 90/95%；
- **并行微调多个变体**可加速实验（数据 pipeline 的不同改法是正交路径，不必串行）；
- 到 95% 之后开始「谈 9」：95 → 99.9，**每加一个 9 都比上一个费力得多**，但这通常正比于该用例对准确率的苛刻程度。

### Lab 的两轮迭代实况

**第一轮**：在还不完美的生成数据上直接 memory tune（`is_public=True` 可共享，返回 dataset ID 可复用；未优化版约 30 分钟，排队期间用课程预置的模型 ID 继续）。评估发现：**报错大减、valid SQL 大增、correct 远超 base 的 ~30%**。注意此时**不再需要 structured output**——模型已被调成直接吐目标格式。

**第二轮（error analysis 驱动）**：翻 `sql_errors.jsonl` 找 pattern——
- 「75th percentile」类：生成的 query 去 select 身高/平均体重，**跟 salary 毫不相关**；
- 「median weight」类：用了 average 而非 median，且**本身还是非法 SQL**；
- 模型**过拟合到 `order by descending`**（老是降序）→ 补 1-2 条 ascending 示例找回 breadth。

对策是**扩数据 + 过滤 + 手工清洗**：

```python
filter_conditions = [
    is_not_valid_sql,          # 打到 DB 跑不通
    has_null_in_sql_or_question,
    returns_empty_dataframe,   # 跑通但空表/None
    uses_avg_on_ht_column,     # avg(ht)/avg(salary) 这种未 cast 就聚合的错法
]
# 去重(question/sql) + 补分号 + 过滤 → generated_queries_large_filtered.jsonl
```

清洗后**把 median 这类样本大量补进训练集**，再微调，模型就能正确处理 median（连没见过的「公牛队中位数年龄」也能答对）。最后换上更难更宽的 **gold-test-set-v2** 评估，final model 的 **valid SQL 与 correct 都大幅上升**。

> **对比 DSPy 自动优化**：本课的 error analysis + 手工加样本 + 手写 filter，是**人肉版的数据优化循环**；DSPy 会把「生成候选→按 metric 评分→保留优者」自动化成 teleprompter/优化器。二者同构，差别在**谁来判断「什么算对」**——当评估指标已稳定可自动打分，就该把这套手工循环交给 DSPy 这类框架跑；当「对」还在靠人 error analysis 定义时，手工迭代不可省。

### ① Conclusion 要点

- 收官视频（Sharon/Amit）：本课学会了**从少量示例出发、随时间迭代地共建评估集与微调数据集**，并且**fine-tuning 可以做到又快又成功**；

### ③ 架构师的裁决

> **架构师的裁决 —— 提升准确率的手段优先级**：
> 本课全程贯穿 Andrew 的定调——**fine-tuning 不是第一步，是穷尽更简单手段后才动的选项**。据此排出阶梯：
>
> 1. **Prompt engineering（含 self-reflection / few-shot）** —— 零训练、改一行就生效、可热调。先把它榨干；上限是它只能在「模型已有能力」范围内调度，撬不动模型不会的事实与格式。
> 2. **RAG** —— 事实可热更新、无需重训，把知识塞进 context 微调下一 token 概率。但**只在相似度空间工作**，对「正确答案和相似答案看起来不像」的硬事实无能为力，且长 context 推理时更贵。
> 3. **Fine-tuning（instruction）** —— 当需要稳定改变行为/UX（跟随指令、function calling、固定输出格式）且 prompt 顶不上去时。注意它优化的是**平均误差**，**不解决幻觉**。
> 4. **Memory tuning** —— 当要求**零幻觉的事实召回**（把特定事实 loss 打到零）时才上，成本最高、最费迭代，但配 PEFT/MoME 优化后可回到分钟级。
>
> 判断锚点：**知识高频变动 → 停在 RAG；行为/格式要固化 → instruction fine-tuning；核心事实要求确定性正确 → memory tuning**。而无论选哪一层，真正移动指针的都不是模型本身，而是**评估集 + 训练数据的迭代质量**，以及**敢在某个阈值停下来 ship**。

## 本课总结

| 要点 | 一句话 |
|---|---|
| 数据其实够 | 判据：有无限时间的人能否从数据推出答案；缺的是格式不是事实 |
| working backwards | text-to-SQL 只需 schema：schema→query→question 链式生成 |
| 过量生成 + 狠过滤 | 生成比过滤难，故多生成 + 复用 eval 方法下采样成高质量集 |
| 造 breadth | 每次随机抽 3 条示例 + 换 persona，轻推多样性 |
| error analysis | 翻错例找 pattern（复杂 query 难、过拟合 order-by-desc），针对性补样本 |
| 成本 | instruction/LoRA 分钟级、优化后 memory tuning 1 分钟；未优化 memory tuning 4 小时 |
| 迭代是艺术 | 约 20 轮到 95%，每加一个 9 更费力；关键是设好「何时 ship」的停止点 |
