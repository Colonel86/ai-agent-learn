# L0 · 课程介绍：从「无状态」到「记忆感知」智能体

> 课程：Agent Memory — Building Memory-Aware Agents（DeepLearning.AI × Oracle）
> 讲师：Richmond Alake、Nacho Martínez｜基础设施：Oracle AI Database 26ai + LangChain

## 一句话定位

这门课解决一个几乎所有 LLM 开发者都撞过的坑：**智能体在单个会话里表现良好，会话一结束就把学到的一切忘光**。课程的答案是把「记忆」当作**一等基础设施**来工程化，而不是塞进 prompt 里的临时字符串。

## 核心概念：Memory Engineering（记忆工程）

讲师给出一个关键的历史脉络判断，值得架构师记住：

| 阶段 | 关注点 | 边界 |
|---|---|---|
| Prompt Engineering | 单次调用怎么写 | 一次 LLM 调用内 |
| Context Engineering | 单次调用塞什么进上下文 | 单次调用的上下文窗口 |
| **Memory Engineering** | 跨天/跨周的持久记忆 | **模型外部、持久化、结构化的独立系统** |

> **架构师视角**：这条演进线不是"新概念取代旧概念"，而是作用域（scope）的逐层外扩。Prompt/Context 工程管的是"这一次调用"，Memory 工程管的是"这个智能体的一生"。三者叠加，不互斥。这跟我在 [[project_selection_matrix]] 里记忆层的选型判断一致——记忆不是框架附赠品，是要独立选型的一层。

关键论断：**长期记忆应当被当作 first-class infrastructure(一流的基础设施)**——外部于模型（external）、持久（persistent）、结构化（structured）。这三个词就是判断"你做的到底是记忆系统还是 prompt 拼接"的试金石。

## 本课要交付什么

课程承诺的不是理论，而是可改造进生产的工作代码：
- 构建 **Memory Manager**：对不同记忆类型做 存/取/操作（store / retrieve / operate）
- 用 LLM 驱动的 pipeline 做 **memory augmentation / extraction / tool retrieval**
- 处理记忆中的**矛盾（contradiction）**——即新旧信息冲突时怎么办
- 自更新的 agent loop：让智能体自主地精炼自己已知的东西

## 无状态智能体的失败，是本课的动机

Andrew 在开场点名的核心问题：**agents failing at long-horizon tasks（长程任务失败）**。记忆优先（memory-first）架构就是针对这个失败模式设计的。L1 会把失败模式逐条拆开。

## 与我的资产映射
