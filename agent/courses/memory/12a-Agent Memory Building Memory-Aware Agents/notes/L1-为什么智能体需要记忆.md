# L1 · 为什么智能体需要记忆：失败模式与记忆分类学

## 1. 智能体的定义（本课口径）

一个 AI 智能体 = **感知（perceive）+ 行动（act）+ 推理（reason）**，并由**记忆（memory）增强**。前三者是老生常谈，本课的重点是第四个：记忆不是可选装饰，而是让前三者能跨时间连贯的粘合剂。

## 2. 无状态智能体的四大失败模式

这是本课最该背下来的一页——面试被问"为什么要给 Agent 加记忆"时，直接列这四条：

| 失败模式 | 表现 | 根因 |
|---|---|---|
| **无法完成长程任务** | 跨越多步/多天的任务半途"断片" | 状态不持久 |
| **无跨会话上下文** | 新会话完全不认识你 | 会话结束即遗忘 |
| **无法适应/学习** | 同样的错误犯无数次 | 没有把经验写回 |
| **成本高** | 靠往上下文里"塞"历史来续命 | context stuffing，token 线性膨胀 |

> **架构师视角**：第四条最容易被忽视，但它是"记忆 vs 大上下文窗口"这个选型辩论的关键。有人说"模型上下文窗口越来越大，还要记忆系统吗？"——答案是要。context stuffing 是 O(n) 成本且信噪比递减；而外部记忆做的是**检索式按需注入**，是 O(log n) 量级的检索 + 定量注入。这跟我在 07a/07b 里对"通用 vs 过时"的判断同源：能力上限提高 ≠ 工程手段作废。

Context stuffing = 不做筛选，把所有可能有用的东西一股脑塞进上下文窗口——全部聊天历史、整份文档、全量工具定义，反正窗口够大，先塞进去再说。它是 context engineering 的反面：用"全塞"代替"该塞什么"的判断。

## 3. 对话记忆（Conversational Memory）——最基础的一层

结构极简，三个字段：**timestamp / role / content**，按时间排序。这就是 episodic（情景）记忆的雏形，也是后面 `CONVERSATIONAL_MEMORY` 表的原型。

## 4. 记忆分类学：短期 vs 长期

这是全课的骨架，务必内化：

### 短期记忆（Short-term）
- **Semantic Cache（语义缓存）**：命中相似 query 直接返回，省一次 LLM 调用
- **Working Memory（工作记忆）**：当前任务正在用的临时状态

### 长期记忆（Long-term）——三种，对应认知科学分类
| 类型 | 中文 | 存什么 | 本课对应表 |
|---|---|---|---|
| **Procedural** | 程序性 | 怎么做事的流程/工具 | WORKFLOW / TOOLBOX |
| **Semantic** | 语义 | 事实知识库 | SEMANTIC（知识库）/ ENTITY / SUMMARY |
| **Episodic** | 情景 | 发生过的对话事件 | CONVERSATIONAL |

> **记忆点**：程序性=「怎么做」，语义=「是什么」，情景=「发生过什么」。这三分法在 L2 建表时会一一对应到物理表，是理解整个 schema 的钥匙。

## 5. 从 RAG 到 Agent Memory 的映射

讲师给了一个关键的认知桥梁：**RAG pipeline ≈ Agent Memory 的语义记忆部分**。
- RAG 的"检索文档 → 注入上下文" = 语义记忆的读操作
- 但 Agent Memory ⊃ RAG：它还多了程序性、情景记忆，以及**写回 / 巩固 / 消解矛盾**的闭环

> **架构师视角**：如果团队里有人说"我们已经有 RAG 了，不需要 Agent Memory"，这就是最好的反驳框架——RAG 是记忆的一个子集（只读的语义记忆），缺了写回和多类型，撑不起长程智能体。

## 6. 关键论断：Agent Memory Core = 数据库

课程反复强调：**记忆核心（Memory Core）就是数据库**——因为绝大多数数据流量（data traffic）都经过它。这句话定调了整门课的技术选型：不是自己造存储，而是把成熟数据库（这里是 Oracle 26ai）当记忆核心，向量检索 + SQL 混合。

> **选型档案可复用点**：这为 [[project_selection_matrix]] 记忆层贡献一条硬判据——**记忆系统的存储底座应优先复用生产级数据库（带向量能力），而非自研或纯向量库**，理由是数据流量集中、需要事务/一致性/混合查询。可作为选型矩阵里"记忆核心存储"维度的默认推荐 + 反例（纯向量库缺 SQL 侧能力）。
