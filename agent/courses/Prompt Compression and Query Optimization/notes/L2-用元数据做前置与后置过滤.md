# L2 · 用元数据做前置与后置过滤（pre-filter vs post-filter）

> 课程：Prompt Compression and Query Optimization（DeepLearning.AI × MongoDB）
> 本课任务：在 L1 的 vanilla 管道上加**元数据过滤**——把 country / accommodates / bedrooms 这类结构化字段当过滤条件，分别用 **post-filter（检索后过滤）** 和 **pre-filter（检索前过滤）** 两种方式插进 aggregation pipeline，并亲眼对比两者返回结果的差异。这是"让检索返回得更小更准"的第一刀。

## 0. metadata：给向量配一份"说明书"

**metadata（元数据）** 就是关于某条数据的附加信息，用来补充主数据、提供更多上下文。讲师用蒙娜丽莎举例：

```
一个 document
├─ 主数据(key data)：图像本身的 vector embedding
└─ metadata：title / artist / location / ...（标题、作者、地点）
```

主数据和 metadata **一起存在 MongoDB 的同一个 document 里**。向量配上 metadata 后，整条数据"更有信息量、更好用"。

在 RAG 里 metadata 有两个用处：**① 给 embedding 加上下文，提升相关性与理解；② 支持基于属性的 filtering 和 sorting，从而缩小向量检索的作用域或结果集。** 本课就是用 metadata 做 filtering，插在 aggregation pipeline 里和 `$vectorSearch` stage 组合。

> **架构师视角**：L1 的 vanilla 版把"用户的硬约束"完全丢了——他要美国的房子，你返回加拿大的。根因是**纯向量检索只懂语义相似、不懂结构约束**。metadata filtering 补的正是这一块：country="美国"、accommodates∈[1,5] 这类是**布尔判定**，不该也不需要交给向量空间去近似。分层的直觉是——**能用确定性字段筛的，绝不用向量近似筛**；向量只负责"语义排序"，结构约束交给 filter。

## 1. 两种过滤：post-filter vs pre-filter

假设用户 query 里既有关键词（seaside、restaurant）又有约束（房间数、可住人数）。两种过滤顺序：

```
post-filter（后置）：  全量数据 ──$vectorSearch──▶ 语义 top-K ──$match──▶ 满足约束的子集
pre-filter（前置）：   全量数据 ──filter──▶ 满足约束的子集 ──$vectorSearch──▶ 语义 top-K
```

| 维度 | post-filter | pre-filter |
|---|---|---|
| 顺序 | 先向量检索，再按条件裁结果 | 先按条件裁数据，再在子集上向量检索 |
| 实现 | `$vectorSearch` 后追加 `$match` stage | 把 `filter` 写进 `$vectorSearch` stage 内部 |
| 返回数量 | **可能远少于 limit**（先取 20 再裁，剩几个算几个） | **稳定等于 limit**（先裁再取满 20） |
| 风险 | **可能丢信息**：语义相近但被 filter 裁掉的记录，本来该进候选却没进 | 候选池已按约束收窄，向量检索在合格集上取满 |

> **一句话记牢**：post-filter 是"先按语义挑 20 个，再从这 20 个里剔除不合格的"——很可能剔到只剩几个；pre-filter 是"先划定合格范围，再在范围内挑满 20 个"。**post-filter 有信息丢失风险，pre-filter 结果更稳。**

## 2. 代码前奏：custom_utils 收编 L1 的样板

L2 开头 `import custom_utils`——L1 里那些冗长的建模、连库、建索引代码被收进这个模块，正课只留业务逻辑：

```python
import custom_utils
listings = custom_utils.process_records(dataset_df)      # = L1 的 Pydantic 建模+清洗
db, collection = custom_utils.connect_to_database()      # = L1 的连库
collection.delete_many({})                               # 清空（本次删了 100 条）
collection.insert_many(listings)                         # 灌数据
custom_utils.setup_vector_search_index(collection=collection)  # 建 L1 那个 vector_index_text
```

> 建索引这步若报 `Duplicate Index` 是**预期内**的——L1 已经建过 `vector_index_text`，直接往下走即可。

## 3. Post-filter：pipeline 尾部追加一个 $match stage

关键改动：`vector_search` 的 pipeline 从 `[vector_search_stage]` 变成 `[vector_search_stage] + additional_stages`——把额外 stage 接在向量检索**之后**。

```python
import re
search_path = "address.country"          # 要过滤的 metadata 字段路径（嵌套用点号）

match_stage = {                          # $match 就是过滤 stage
    "$match": {
        search_path: re.compile(r"United States"),  # 只要美国的房源
        "accommodates": {"$gt": 1, "$lt": 5}         # 且可住人数 (1,5) 开区间
    }
}
additional_stages = [match_stage]

# vector_search 内部：pipeline = [vector_search_stage] + additional_stages
#   → 先跑 $vectorSearch 取 top 20，再用 $match 在这 20 条里筛
handle_user_query(query, db, collection, additional_stages)
```

`$gt`(大于) / `$lt`(小于) 是 MongoDB 的条件操作符，逻辑下推给数据库处理。跑同一个"warm and friendly、离餐厅近"的 query，结果：房源**全部落在美国**、accommodates **全在 1~5 之间**，系统推荐了 Chelsea 的一处单卧。

## 4. Pre-filter：把 filter 写进 $vectorSearch 内部（需专用索引）

pre-filter 要在检索前就按字段裁数据，因此**过滤字段必须先被索引**。所以先建一个新索引，把 `accommodates`/`bedrooms` 显式声明成 `number`：

```python
vector_index_with_filter = "vector_index_with_filter"

new_vector_search_index_model = SearchIndexModel(
    definition={"mappings": {"dynamic": True, "fields": {
        "text_embeddings": {"dimensions": 1536, "similarity": "cosine", "type": "knnVector"},
        "accommodates": {"type": "number"},   # ★ 显式声明过滤字段
        "bedrooms":     {"type": "number"},   # ★ 显式声明过滤字段
    }}},
    name=vector_index_with_filter,            # 用新名字区分 L1 的索引
)
collection.create_search_index(model=new_vector_search_index_model)
```

然后 `filter` 直接写进 `$vectorSearch` stage 内部——过滤在向量检索**之前**发生：

```python
vector_search_stage = {
    "$vectorSearch": {
        "index": vector_index,               # 传入 vector_index_with_filter
        "queryVector": query_embedding,
        "path": "text_embeddings",
        "numCandidates": 150,
        "limit": 20,
        "filter": {                          # ★ pre-filter：先裁候选池再算相似度
            "$and": [
                {"accommodates": {"$gte": 2}},   # 可住 ≥2
                {"bedrooms": {"$lte": 7}}        # 卧室 ≤7
            ]
        },
    }
}
# 调用时不再传 additional_stages，改成传入带 filter 的新索引：
handle_user_query(query, db, collection, vector_index=vector_index_with_filter)
```

`$and` 把多个条件组合，逻辑全交给数据库。跑同一个 query，系统这次推荐的是 **Sydney Hyde Park 的公寓**——与 post-filter 版的 Chelsea 单卧**完全不同**。

## 5. 亲眼对比：返回数量的差异

同样在 `$vectorSearch` 里设 `limit: 20`，两种过滤的实际返回量却不同：

| 方法 | limit 设定 | 实际返回 | 为什么 |
|---|---|---|---|
| **pre-filter** | 20 | **20 条** | 先在合格子集上检索，取满 20 |
| **post-filter** | 20 | **4 条** | 先取语义 top 20，再被 `$match` 裁到只剩 4 |

这就是第 1 节那句话的实证：**post-filter 会因为"先取后裁"损失记录**——那些语义上很相近但恰好不满足 country/accommodates 的房源，本可能是好候选，却在裁剪中丢了。pre-filter 因为"先裁后取"，候选池已经全合格，能稳定返回满额。

> **对比《Semantic Caching for AI Agents》(Redis)**：Redis 语义缓存里也有"相似度阈值 + metadata 过滤"的组合——命中缓存不仅要向量够近，还常要 tenant_id / user_id 等 metadata 匹配（否则串了租户的缓存）。那里 metadata filter 是**正确性/隔离**的护栏（过滤错了会泄露别人的答案）；本课 metadata filter 是**相关性/成本**的旋钮（过滤错了只是推荐不准、token 多花）。同样是"向量 + metadata 一起筛"，一个守安全边界，一个调质量成本——`3-retrieval.md` 里"metadata filtering 的两种动机"就是这组对照。

> **架构师视角**：pre vs post 不是"谁更好"，是取舍。**pre-filter 结果稳、无信息丢失，但要求过滤字段预先建进索引**（多一个索引、多一份维护，且过滤字段得提前想清楚）。**post-filter 灵活、任意字段临时筛，但可能把结果裁到不够用**，还白算了被裁掉那些文档的相似度。经验法则：**高频、已知的硬约束（国家/人数/价格档）走 pre-filter 建进索引；低频、临时、探索性的筛选走 post-filter。** 大规模应用两者并用——这正好呼应 L0 说的"large scale applications may use both simultaneously"。

## 本课总结

| 要点 | 一句话 |
|---|---|
| metadata | 关于数据的附加信息，与向量同存一个 document，既加上下文又支持 filter/sort |
| post-filter | `$vectorSearch` 后追加 `$match`；先取语义 top-K 再裁，**可能返回远少于 limit** |
| pre-filter | filter 写进 `$vectorSearch` 内部；先裁候选再检索，**稳定返回满 limit** |
| 前提差异 | pre-filter 的过滤字段必须先显式建进索引（新建 `vector_index_with_filter`） |
| 实证对比 | 同设 limit=20：pre-filter 返回 20，post-filter 只返回 4 |
| 核心取舍 | pre：稳/无丢失/需预建索引；post：灵活/任意字段/可能不够用；大规模两者并用 |

> **记忆点（引出 L3）**：L2 解决了"返回哪些**文档**"——用 filter 把不合约束的房源剔掉。但每条返回的文档仍是**全字段**（一条 listing 十几个字段全带出来），喂给 LLM 的 token 里有大量用不上的字段。L3 引入 **projection（投影）stage**：在 aggregation pipeline 里只挑出推荐真正需要的字段（如 name / bedrooms / price），把返回数据量再砍一刀——从"少返回几条"进到"每条也只返回几列"。
