# L0 · 课程介绍：用知识图谱解决 Agent 的 API 发现难题

> 课程：Knowledge Graphs for AI Agent API Discovery（DeepLearning.AI × SAP）
> 讲师：Pavithra G K（SAP Business Knowledge Graphs 负责人）、Lars Heling（SAP Business AI 高级知识工程师）；Andrew Ng 参与开场对谈。致谢名单：Christoph Meyer、Felix Sasaki、Johannes Hoffart（SAP），Esmaeil Gargari（DeepLearning.AI）。

## 一句话定位

**核心问题**：大企业里有几千个 API，由不同团队各自发布（买货/退货、差旅审批、数据访问的 IT 审批……）。API 越多，Agent 反而越难回答两个问题——**该用哪些 API？按什么顺序调？**

**本课答案**：把原始 API 规范导入**知识图谱**，获得所有 API 的结构化视图；再往图里追加**业务流程数据**，告诉 Agent 正确的调用顺序——图谱从"一份 API 清单"升级为"API 在真实流程中如何协作的网络"。

与同类方案的分野：纯向量检索（embed API 规范 + 相似度搜索）只能按"语义相似"找到 API，找不到"流程上必须先调"的前置 API——课程开场的例子：Agent 接到"采购一件商品"的任务，检索命中 purchase order API 就直接下单，却不知道大公司里要**先创建 purchase request、经审批之后**才能真正下 purchase order。这条流程信息**不在任何一个 API 的定义里**，缺了它，图谱和 Agent 对业务流程的理解都是不完整的。本课的方案是：语义检索起步，再用图谱扩展检索把流程要求的关联 API 及其顺序一并交给 Agent。

> **架构师视角**：这门课瞄准的是工具层的一个盲区——API/工具的**元数据（描述）**和**编排知识（先后依赖）**是两种不同的知识，前者可以从规范里抽，后者散落在业务流程里。大多数工具检索方案只解决前者；面试聊 tool use 时，"你的工具检索能不能表达调用顺序依赖"是一个很好的深挖点。

## 核心概念/类比

| 概念 | 类比 | 一句话 |
|---|---|---|
| API 知识图谱 | 把"一抽屉说明书"整理成"带索引的地图" | 原始 API 规范 → 结构化的全景视图 |
| 流程数据增强 | 在地图上画出"行车路线" | 图谱从 API 清单变成"API 如何在真实流程中衔接"的网络 |
| 语义检索 | 按"长得像"找工具 | embed 所有 API 及规范，相似度搜索找最佳匹配 |
| 图谱扩展检索 | 顺着路线把沿途站点都带上 | 从命中的 API 出发，沿图找出流程要求的关联 API 和调用顺序 |
| purchase 三步流程 | 公司报销不能跳过审批 | purchase request → 审批 → purchase order，顺序信息不在 API 定义里 |

## 课程路线

| 课 | 一句话预告 |
|---|---|
| L1 | 知识图谱入门：是什么、怎么构建，以及如何帮 Agent 理解并执行复杂多步流程 |
| L2 | 把原始 API 规范导入知识图谱，得到所有 API 的结构化视图 |
| L3 | 用业务流程数据扩展图谱：Agent 由此知道 purchase request API 必须先于 purchase order API 调用 |
| L4 | 语义检索（embedding + 相似度搜索）起步，再用图谱扩展检索补全流程要求的关联 API 及顺序 |
| L5 | 全部串起来：构建一个能按正确流程顺序执行真实任务的 AI Agent |

> **对比课程 10-MCP 的 list_tools**：MCP 给 Agent 的是**平面工具清单**——每个工具有名字和描述，但工具之间零关系。几十个工具时靠 LLM 自己读描述还撑得住；到"几千个 API、跨团队发布"的企业规模（4-tools.md 的工具爆炸问题），清单既塞不进上下文，也表达不了"先 request 后 order"的依赖。本课的图谱路线正是对平面清单的结构化升级。

> **记忆点（引出 L1）**：Andrew 收尾点题——用 agentic workflow 承接企业的复杂业务流程，是 AI 社区接下来的巨量工作，把它做对很重要。而做对的第一步是搞清楚地基：L1 讲**知识图谱到底是什么**（RDF、三元组、本体），以及它凭什么能帮 Agent 理解多步流程。
