# L1 · 知识图谱基础与企业级 API 发现（纯概念课）

> 课程：Knowledge Graphs for AI Agent API Discovery（DeepLearning.AI × SAP）
> 本课回答三个问题：知识图谱**是什么**、有哪些**构建方法**、以及它如何让 AI Agent 在企业环境里做更好的 **API discovery 与执行**。

## 1. 开场直觉：搜索引擎里的知识图谱

搜 "SAP"，结果页除了匹配网页列表，还有一张实体概览卡——它就来自知识图谱：

- **属性（properties）**：描述、官网链接……
- **到其他实体的关系（relations）**：总部所在地 → Walldorf；
- 点进 Walldorf，又是一个图谱条目：自己的属性 + 到其他实体的关系（如所属地区 Karlsruhe）。

实体之间可以一路"点下去"——这就是图谱与文档检索最直观的差别：**答案不是一段文本，而是一张可导航的网络**。

## 2. 技术基础：两个组成部分、两种表示法

知识图谱以图的形式表示结构化信息：**节点 = 实体（entities），边 = 实体间关系（relationships）**。两个主要组成部分：

| 组成 | 作用 |
|---|---|
| **Schema / Ontology（本体）** | 定义图里允许出现的实体类型、属性、实体间关系——图的"蓝图" |
| **Instance data（实例数据）** | 遵循 schema 定义的具体实例，构成图本身 |

两种主流表示法，都能建模实体与关系，但结构、表达力、目标场景不同：

| 表示法 | 一句话 |
|---|---|
| Labeled Property Graph（LPG） | 带标签的属性图 |
| **Resource Description Framework（RDF）** | **本课采用**：W3C 标准化的图数据模型 |

RDF 的关键特性（也是本课选它的理由）：

- **不强制 schema**：灵活，易于整合异构数据源的数据；
- **SPARQL** 是 RDF 的标准查询语言，语义定义良好——地位类似关系模型里的 SQL。

## 3. RDF 速成：triple → 图 → 推理 → 序列化

RDF 的原子构件是**三元组（triple）**：`subject — predicate — object`，每条 triple 就是图里一条**带标签的有向边**：

```
  subject ──predicate──▶ object
   (SAP)  ──locatedIn──▶ (Walldorf)      # "SAP 位于 Walldorf" 这一事实
```

用课上的例子从零搭一个小图谱：

```
        "1972"        "SAP"
          ▲             ▲
     founded │      name │
          │             │
  (Company)◀──a──  [SAP 节点/URI]  ──ceo──▶ [Christian Klein]
                        │
                 headquarters
                        ▼
                   [Walldorf] ──locatedIn──▶ [Germany]（推理得出）
```

四个要点：

1. **URI**：RDF 用 Unique Resource Identifier 全局唯一地标识图中的资源（节点）；
2. **Literal**：属性值（如创立年份、名字、"是一家公司"）是字面量；实体间关系则指向其他节点（CEO → Christian Klein，总部 → Walldorf）；
3. **推理（inference）**：图谱可以基于本体定义**推出数据里没写的事实**——把 `locatedIn` 定义为传递关系（transitive），就能从 "SAP 位于 Walldorf" + "Walldorf 位于德国" 推出 "SAP 位于德国"；
4. **序列化**：RDF 图通常存成机器可读格式，如 **N-Triples** 或 **Turtle** 文件（课上示例文件里有一条 triple：SAP 的 CEO 是 Christian Klein）。

> **架构师视角**：第 3 点是图谱区别于"向量库 + 元数据过滤"的本质能力——**推理是本体层面的，一条 transitive 声明即可让所有 locatedIn 链条自动闭合**，不需要逐条写入派生事实。面试聊 "KG vs RAG" 时，"能不能推出没存过的事实"是最干净的分界线。

## 4. 三条构建路线：按源数据的结构化程度选

| 源数据 | schema 特征 | 例子 | 构建手段 |
|---|---|---|---|
| **结构化（Structured）** | 固定 schema，同类实体属性一致 | 关系数据库 | 映射规则（如 **R2RML**） |
| **半结构化（Semi-structured）** | 灵活 schema，同类实体可以描述不一 | XML 文档 | 同样用映射规则 |
| **非结构化（Unstructured）** | 完全没有固定 schema | 自然语言文本、图片 | NLP 技术抽取 |

本课走**结构化路线**构建示例图谱。

> **对比 3-retrieval 的 GraphRAG**：GraphRAG 的典型构图方式对应上表第三行——LLM 从非结构化文本抽实体关系，有幻觉风险、需人工校验。本课源数据是结构化的 API 规范，走映射规则路线，**构图完全确定性、零幻觉**。选型判据一句话：源数据自带 schema 就走确定性映射，只有自然语言才动用 LLM 抽取。

## 5. 构建流程五步（Step 0–4）

```
Step 0          Step 1          Step 2           Step 3          Step 4
定义用例/范围 ──▶ 汇聚数据    ──▶ 分析与标准化 ──▶ 数据建模     ──▶ 交付价值
业务问题驱动     跨企业系统       统一"方言"        清洗数据 →      连通性带来
要抽什么元数据    CSV/XML/JSON    去重/解决不一致    RDF 三元组      新连接/分析/洞察
要建什么模型     各说各的语言     校验数据质量      s-p-o 镜像源系统关系
```

- **Step 0**：先定用例、范围、图谱要回答的业务问题——由它决定抽什么元数据、建什么模型；
- **Step 1（Foundation）**：连接各系统、抽取业务数据，每个源系统"说自己的语言"（CSV、XML、JSON……）；
- **Step 2**：把不同"方言"翻译成共同语言——识别重复信息、解决不一致、校验数据质量，保证图谱建在可信数据之上；
- **Step 3（Data modeling）**："魔法发生的地方"——干净数据转成标准化 RDF 三元组，每条业务信息都表示成 subject-predicate-object，直接镜像底层系统中的关系；
- **Step 4**：利用图谱的**连通性**交付价值——不只是源系统的复刻，而是把各源的元数据当作一个互联整体，产生新的连接、分析与洞察。

## 6. 企业场景：Agent + API 知识图谱

用户请求：**"在 purchasing group 002、purchasing organization 3000 下，为 5 支铅笔创建一张 purchase order"**，交给 Agent 执行。

没有上下文时这并不简单——企业系统版图可能有**几千个可能相关的 API**。做法：为系统版图中的 API 构建知识图谱，并用**业务流程信息**增强，给 Agent 提供完成请求所需的上下文。

课程给出企业环境下 Agent 面临的**四大挑战**，以及图谱的对应解法：

| # | 挑战（没有图谱时） | 知识图谱的解法 |
|---|---|---|
| 1 | **发现低效**：LLM 靠试错找 API，烧时间烧 token，显著拖慢执行 | 按业务流程和业务对象组织 API → 收窄搜索空间、规划更高效、减少无谓 replanning、整体提速 |
| 2 | **缺深层结构**：LLM/RAG 擅长拉相关内容，但丢掉领域逻辑、API 元数据这类深层上下文 | 结构化且语义丰富，显式表达 API-流程-数据模型三者关系 → grounding 响应、抑制幻觉，尤其在动态/定制化的业务环境 |
| 3 | **复杂执行乏力**：简单读操作没问题，但"按正确顺序调一串 API""理解允许的固定取值"就开始挣扎 | 图谱内建依赖与顺序结构 → 一步一步引导 Agent，降低出错概率 |
| 4 | **不可解释**：答案来自学到的模式或检索片段，看不到推导过程；同一查询结果还可能不同，难以追溯 | 推理过程透明化 → 可精确追踪用了哪些 API、什么过滤条件、系统返回了什么、源系统是哪个 |

> **架构师视角**：第 4 点在企业语境的分量最重——**trust、auditability、reproducibility 在企业环境是不可协商的**（字幕原话 non-negotiable）。这也是"为什么不直接把几千个 API 描述全喂给长上下文 LLM"的最强反驳：就算上下文装得下、检索足够准，黑盒推理也过不了审计这一关。图谱把"为什么选这个 API"变成一条可回放的路径。

> **对比 4-tools.md 的工具路由**：常见的工具爆炸解法是"分层路由/工具子集检索"——本质仍是**按描述相似度切子集**，解决的是挑战 1（搜索空间），解决不了挑战 3（顺序依赖）和挑战 4（可追溯）。图谱路线一次回应了四个挑战，代价是要先建图、先有流程数据——这就是 L2/L3 的工作。

## 7. 本课总结

| 要点 | 一句话 |
|---|---|
| 图谱两组件 | Schema/Ontology 定蓝图，Instance data 填内容 |
| 表示法选型 | LPG vs RDF；本课用 RDF（W3C 标准、不强制 schema、SPARQL 查询） |
| RDF 原子构件 | triple = subject-predicate-object = 一条带标签的有向边；URI 标识节点、literal 装属性值 |
| 推理 | 本体定义（如 transitive）可推出数据里没写的事实 |
| 三条构建路线 | 结构化/半结构化走映射规则（R2RML），非结构化走 NLP |
| 构建五步 | 用例定义 → 汇聚 → 标准化 → RDF 建模 → 连通性变现 |
| 四大挑战 | 发现低效、缺深层结构、复杂执行乏力、不可解释——图谱逐一对应 |

> **记忆点（引出 L2）**：概念课收官——你已经知道图谱是什么、RDF 怎么表达事实、构建分五步走。L2 把这套流程真正跑一遍：用 **SPARQL CONSTRUCT** 把描述 API 的 **5 张 CSV**（结构化路线！）声明式地转换成 API 知识图谱——正好落在本课"结构化源 + 映射规则"那一格。
