# MCP: Build Rich-Context AI Apps with Anthropic —— 总结回顾

> 课程：**MCP: Build Rich-Context AI Apps with Anthropic**（DeepLearning.AI 短课，讲师 Elie Schoppik @ Anthropic）
> 用途：一页式快速回顾。逐课详记见各 `L*` 笔记。

---

## 一句话主线

> **模型再聪明，也只能用它能拿到的上下文工作。MCP 用一个开放的 client-server 协议，把"LLM 应用 ↔ 工具/数据/提示模板"的连接从 N×M 份定制集成降为 N+M——写一次 server，处处复用。**

全课围绕一个 **arXiv 研究助手** 贯穿始终：普通 tool-use chatbot → 工具抽到 MCP server → 手写 client → 连多个 server → 补齐 resources/prompts → 接入 Claude Desktop → 部署到云端。

---

## 核心概念（L0–L2）

### 为什么需要（L1）

- **类比**：REST 之于 Web、LSP 之于 IDE —— MCP 标准化"应用 ↔ 外部能力"的边界。
- **痛点**：没有标准时，每个 AI 应用都要自己维护工具定义、prompt、数据访问、鉴权，N 个模型 × M 个数据源 = N×M 份重复集成。
- **MCP server ≠ API**：它是"API 之上的网关/封装"；**MCP ≠ tool use**：tools 只是三大原语之一。

### 架构（L2）

- **Host**：LLM 应用本身（Claude Desktop / Cursor / 你的 chatbot）。
- **Client**：跑在 host 内，**每个 client 与一个 server 1:1 连接**；一个 host 可持多个 client。
- **Server**：轻量程序，按协议暴露能力。模型无关、可插拔。

### 三大原语对照（全课总纲，L2 + L7）

| 原语 | 语义 | 谁触发 | server 装饰器 | client 发现 | client 调用 |
|---|---|---|---|---|---|
| **Tool** | 有副作用的操作（POST 语义） | LLM 自动调用 | `@mcp.tool()` | `list_tools()` | `call_tool(name, args)` |
| **Resource** | 只读数据/上下文（GET 语义），随数据动态更新 | 应用决定 | `@mcp.resource("uri")` | `list_resources()` | `read_resource(uri)` |
| **Prompt** | 服务端打磨好的提示模板，用户填参数 | 用户主动选择 | `@mcp.prompt()` | `list_prompts()` | `get_prompt(name, args)` |

FastMCP 的统一约定：**函数名 → 名称，docstring → 描述，类型注解 → JSON Schema**。

### Transport 对照（L2 + L9）

| 维度 | stdio | SSE | Streamable HTTP |
|---|---|---|---|
| 启动方式 | client 把 server 拉成**子进程** | server 独立运行 | server 独立运行 |
| 会话状态 | 进程级 | 有状态（长连接） | 可有状态/无状态 |
| 适用场景 | 本机开发 | 远程（早期方案） | 远程、云原生扩容（**新规范推荐**） |
| FastMCP 写法 | `mcp.run(transport='stdio')` | `transport='sse'` + `port=` | `transport='streamable-http'`（`stateless_http=True` 可选） |

## 动手主线逐课速查（L3–L9）

### L3 — 地基：普通 tool-use chatbot（无 MCP）
- 两个工具：`search_papers(topic)`（arXiv 搜索 → 写 `papers/<topic>/papers_info.json`）、`extract_info(paper_id)`。
- 手写 tool schema + `mapping_tool_function` 派发 + `process_query` 循环（text 打印 / tool_use 执行后追加 `tool_result` 再调模型）。
- 要点：**模型只"请求调用"，执行永远在开发者代码里**；每次 query 新建 messages，无跨轮记忆。

### L4 — 把工具抽成 MCP server
- `mcp = FastMCP("research")` + `@mcp.tool()` 装饰器照搬 L3 函数 → `mcp.run(transport='stdio')`。
- **MCP Inspector** 不写任何 client 就能测：`npx @modelcontextprotocol/inspector uv run research_server.py` → List Tools、直接调用、看自动生成的 schema。
- 价值：server 完全独立于 LLM，接入前先"沙箱体验"验证健康。
- 环境：`uv init / uv venv / uv add mcp arxiv`。

### L5 — 手写 MCP client
- 核心三层：`StdioServerParameters`（怎么拉起子进程）→ `stdio_client(...)` 返回 read/write 流 → `ClientSession(read, write)` 提供 `initialize / list_tools / call_tool`。
- `process_query` 与 L3 几乎一样，唯一差别：`execute_tool(...)` 换成 `await session.call_tool(name, arguments=...)`。
- `list_tools()` 返回的 `name / description / inputSchema` **正好是 Anthropic API 要的格式**。
- 全程 async；Jupyter 里要 `nest_asyncio.apply()`。

### L6 — 连接多个 server
- 配置外置 `server_config.json`（`mcpServers: {name: {command, args}}`），与 Claude Desktop 配置同构。
- 用现成参考服务器零安装即跑：`uvx mcp-server-fetch`（网页→Markdown）、`npx -y @modelcontextprotocol/server-filesystem <路径>`（路径参数即访问边界）。
- 关键改造：`AsyncExitStack` 动态管理 N 个上下文 + **`tool_to_session` 查表**把工具名路由到所属 session；`try/finally` 里 `cleanup()`。
- 多 server 串联演示：fetch 抓网页 → research 搜论文 → filesystem 写结果，agent 自己规划。
- 留的练手题：并行连接（`asyncio.gather`）、工具重名冲突处理。

### L7 — 补齐 resources 与 prompts
- Server：静态 URI `papers://folders` + 模板 URI `papers://{topic}`；`generate_search_prompt(topic, num_papers)` 把复杂 prompt engineering 做在服务端复用。
- Client 自定义 UI 约定：`@folders` / `@<topic>` 读资源，`/prompts` 列模板，`/prompt <name> k=v` 渲染后喂回 `process_query`。
- **MCP 不规定 UI**——展示与命令语法完全是 host 的自由；并非所有 server 都有 prompts/resources，发现时要兜异常。

### L8 — 接入 Claude Desktop（成品 host）
- Settings → Developer → Edit Config，写同款 `mcpServers` JSON；差别：**必须绝对路径**（`uv --directory ...`）、改完**重启生效**。
- Desktop 替你抽象掉 L5/L6 全部底层代码（子进程、stdio、session、cleanup），UI 直接暴露三大原语。
- 关键认知：**一份 server，自家 chatbot / Claude Desktop / Cursor 通吃**——你已经懂成品 host 底下在跑什么。

### L9 — 远程化与部署
- Server 端只改一行：`transport='stdio'` → `'sse'`（+ `port=8001`）；tools/resources/prompts 定义零改动。
- Client 端只换 transport 层：`stdio_client(params)` → `sse_client(url=".../sse")`，**其余代码不动——这就是协议抽象的价值**。
- 部署 render.com 流程：`uv pip compile pyproject.toml > requirements.txt` + `runtime.txt` → 推 GitHub → render 建 Web Service（start command: `python research_server.py`）→ 访问 `<url>/sse` 验证。
- stdio 是 client 拉子进程；远程是 server 先独立跑、client 网络连。

## 高级特性与展望（L10）

| 方向 | 一句话 |
|---|---|
| **OAuth 2.1 认证** | 2025-03 规范引入，远程 server 强烈推荐；本地 stdio 用环境变量传凭据即可 |
| **Roots**（client→server 原语） | client 给 server 划 URI 边界（目录/域名），安全 + 聚焦 |
| **Sampling**（server 反向调模型） | server 把大数据+问题发给 client 端 LLM 分析，避免塞爆上下文、避免数据外泄——server 也能"思考" |
| **可组合性** | 一个 agent 可同时是 client + server → 多智能体网络用同一种 MCP 语言协作 |
| **Unified Registry** | 集中发现、可信标记、版本锁定；配合 `.well-known/mcp.json` 实现"用户提需求才动态连接+授权" |
| **其它** | Streamable HTTP 取代 SSE、工具命名冲突治理（命名空间/分组） |

## 关键 API 速查

| API | 用途 |
|---|---|
| `FastMCP("name", port=)` / `mcp.run(transport=)` | 建 server / 选传输层 |
| `@mcp.tool()` / `@mcp.resource("uri")` / `@mcp.prompt()` | 暴露三大原语 |
| `StdioServerParameters(command, args, env)` | 描述如何拉起本地 server |
| `stdio_client(params)` / `sse_client(url)` | 建传输连接，返回 read/write 流 |
| `ClientSession(read, write)` → `initialize()` | 握手建会话 |
| `session.list_tools() / call_tool(name, arguments)` | 工具发现 / 调用 |
| `session.read_resource(uri)` / `get_prompt(name, arguments)` | 读资源 / 渲染模板 |
| `AsyncExitStack().enter_async_context(...)` / `aclose()` | 动态管理 N 个 server 连接 |
| `npx @modelcontextprotocol/inspector <启动命令>` | 不写 client 直接测 server |

## 架构师视角的四个要点

1. **MCP 的本质是"集成的关注点分离"**：工具定义、数据访问、prompt 工程从应用代码外化到 server，N×M → N+M。决策点：自己写 server（私有数据/能力）还是接社区 server（GitHub/fetch/filesystem 这类通用件）——通用件几乎永远不该自己重写。
2. **原语选型有语义纪律**：有副作用→tool（LLM 自动调），只读上下文→resource（应用决定塞不塞），可复用的专家提示→prompt（用户触发）。把一切都做成 tool 是最常见的误用——会让模型替用户做本该由应用/用户做的决定。
3. **transport 是部署决策，不是开发决策**：业务代码（三大原语定义）与传输层完全解耦，stdio 开发 → SSE/Streamable HTTP 上线只改一行。无状态 Streamable HTTP 才能横向扩容——要规模就别依赖连接级状态。
4. **协议的未竟之地决定生产可用性**：鉴权（OAuth 2.1）、信任（registry）、边界（roots）、工具重名治理都还在演化。现在上生产要自己补这些坑；这也正是"会接 MCP"和"能用 MCP 设计企业级 agent 架构"的差距所在。
