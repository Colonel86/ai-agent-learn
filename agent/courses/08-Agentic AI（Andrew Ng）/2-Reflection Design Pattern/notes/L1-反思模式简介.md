# L1 反思设计模式简介（Reflection to Improve Outputs）

## 核心思想

人类写完邮件后会重读、修改；LLM 也可以用同样的方式改进自己的输出。这就是**反思设计模式（Reflection）**——实现起来出乎意料地简单，却在很多应用中带来明显提升。

## 典型工作流

最朴素的形式是把同一个 LLM 调用两次：

1. **第一次调用**：用 prompt 让模型生成初稿（email v1 / code v1）。
2. **第二次调用**：把初稿喂回去，配一个新的 prompt 让它"反思并改写"，得到 v2。

可以是同一个模型，也可以是不同模型。

## 示例一：写邮件

- 快速打字写出的初稿往往不够好：日期写得模糊（"下个月"）、有错别字、忘记署名。
- 自己重读时会发现这些问题并改写："Tommy，5–7 号你有空吃饭吗？……"
- LLM 走完全一样的流程：先生成，再反思，再改写。

## 示例二：写代码

- 让 LLM 写一段实现某功能的代码 → v1。
- 把 v1 交给同一个或另一个 LLM，让它"检查 bug 并改写" → v2。
- **模型选择的小技巧**：不同模型各有强项。Reasoning / Thinking 类模型擅长找 bug，所以可以用普通模型直接生成初稿，用推理模型做反思。

## 关键洞察：外部反馈让反思更强大

仅靠模型自己反思已经有用，但如果能引入**外部信息**（来自 LLM 之外的新信息），反思的效果会显著提升。

代码场景中最简单的外部反馈就是**直接运行代码**：

- v1 跑出来报语法错误。
- 把代码 + 报错日志一起喂回 LLM，让它基于这些"额外信息"重写。
- v2 通常质量大幅提升，远好于纯靠模型自反思。

## 要记住的两点

1. 反思不是魔法，不会让 LLM 100% 正确，但通常能带来"温和"的性能提升。
2. **只要有机会接入外部信息，反思就会变得更强**——这是后续模块会反复回到的设计原则。

## 面试速答总结

**一句话**:Reflection = 让 LLM **"生成→反思→改写"**(最朴素就是把同一模型调两次);**实现极简、提升温和**,而**只要能接入外部反馈(如跑代码看报错),效果会显著放大**。

### 面试回答骨架(问"什么是 Reflection / 怎么用它提升 agent 输出")

> 1. **本质**:类比人写完邮件会重读再改。最简形式 = **两次调用**:①生成初稿 v1 → ②把 v1 喂回 + 新 prompt"反思并改写"→ v2。可同模型,也可换模型。
> 2. **关键升级——外部反馈 > 纯自评**:仅靠模型自我反思已有用,但**引入模型之外的新信息**会显著更强。代码场景最典型:**直接运行 v1 → 把代码+报错日志一起喂回 → 改出 v2**,质量远好于纯自反思。
> 3. **模型搭配小技巧**:不同模型有强项——**普通模型出初稿,推理/thinking 模型做反思找 bug**,性价比更高。
> 4. **给取舍**:反思**不是魔法**,不保证 100% 正确,通常是"温和"提升;且**每轮多一次调用 = 更慢更贵**,要设最大轮数。**有客观可验证信号(测试/编译/规则)时收益最大**。

### 最该背的一句(贯穿后续模块的设计原则)

> **"只要有机会接入外部信息,反思就会变得更强。"** —— 能用**确定性的外部反馈**(运行结果、单测、校验器)就别只靠 LLM 自评。

### 为什么这是高分答法

- 不止说"让它自我检查",而是点出**外部反馈才是 Reflection 的威力来源**——显示你懂"自评不可靠"这层;
- 带**模型搭配 + 成本/轮数取舍**,是工程视角而非概念复述。

**一句话收尾**:Reflection 用"生成→反思→改写"换质量,**核心不在自我批判,而在能否喂回确定性的外部反馈**;简单好上手,但要控轮数、控成本。
