# L1 端到端评测（End-to-End Evaluations）

## 本模块定位

整门课中讲者认为最重要的模块——"实战 tips"。掌握后能在 agentic 系统开发上比一般开发者高效得多。

## 起手心法：先快后好

agentic 系统**事先很难预测**哪里会出问题、该把精力花在哪。所以：

- **不要花几周纯理论推演**架构方案。
- 用一个**快糙的原型（quick and dirty）**先跑起来——前提是安全合理、不泄数据。
- 跑出来才有东西可看、可分析、可决定下一步。

## 案例一：发票字段抽取（每例都有 ground truth + 客观评测）

任务：从 PDF 发票里提取 4 个必需字段，存入数据库。

### 看 20 条样本，发现规律

人工过一遍 20 张发票的输出：

- 1 号 OK
- 2 号把"开票日期"和"到期日期"混了——而我们要的是**到期日期**（用来安排付款）
- 3、4 号 OK……
- 翻完发现"日期搞混"是高频错误模式

→ 下一步：**专门为"到期日期抽取"建一个 eval**。

> 如果发现错的是另一种字段（比如"账单方地址"，可能因为有非英文名字的国际账单方），那就为这类字段建 eval。看原型输出能帮你决定**评测重心应该放哪**。

### 建 eval 的具体做法

1. 找 10–20 张发票，**手写正确的到期日期**作为 ground truth，统一格式如 `2025-08-20`。
2. prompt 里**约束 LLM 也输出这种格式**——便于自动比对。
3. 写代码用正则提取 LLM 输出里的日期。
4. 比较：是否等于 ground truth → 算正确率。

迭代 prompt 或算法时盯着这个百分比涨没涨。

### 通用循环

> 建系统 → 看输出 → 发现问题 → 如果会修就直接修；不会修就建小 eval（20 例够了）→ 用 eval 驱动迭代。

> 后续如果发现 20 例覆盖不够，**随时扩充 eval 集**。

## 案例二：Instagram 文案助手（无每例 ground truth + 客观评测）

任务：根据商品图 + 用户需求生成营销文案，**要求 ≤ 10 词**。

### 发现的问题

模型生成的内容质量不错，但**字数经常超**：

- 太阳镜：17 词
- 蓝衬衫：14 词
- 搅拌机：11 词

→ 模型不擅长严格遵守长度限制。

### 建 eval

1. 准备 10–20 个测试输入（不同商品）。
2. 跑出文案。
3. 用 Python 代码数 word count。
4. `if word_count <= 10: correct += 1`。

### 与案例一的关键区别

- 案例一：**每条样本都有自己的 ground truth**（到期日各不相同）。
- 案例二：**目标对所有样本都一样**（≤ 10 词），不需要逐例标注。

## 案例三：研究 agent（每例有 ground truth + LLM-as-judge 主观评测）

发现问题：写"黑洞最新进展"漏了重要的高曝光成果；"机器人采摘水果"漏了头部企业。模型**漏关键点**。

### 建 eval

1. 准备一批 query（黑洞、采摘机器人、租 vs 买房 ……）。
2. 每条 query 由专家列出 **3–5 个 gold standard 讨论点**——每条不同，所以**有每例 ground truth**。
3. 用 **LLM-as-judge** 判断生成的文章命中了几个 gold standard 点。
4. 让 judge 输出 JSON：`{score: 0-5, explanation: ...}`。

为什么用 LLM-as-judge 而不是正则？同一个观点的表述方式太多，正则匹配不出来。

## 两个维度的评测矩阵（2×2）

|   | 代码客观评测 | LLM-as-judge 主观评测 |
|---|---|---|
| **有每例 ground truth** | 发票日期抽取 | 研究 agent 漏点统计 |
| **无每例 ground truth** | 文案字数限制 | 图表评分 rubric（W2 出现过） |

> 这些都属于**端到端（end-to-end）evals**：从用户输入到最终输出，整条链路一起评。

## 设计 end-to-end eval 的几条经验

1. **先糙后精**：很多团队被"建 eval 是大工程"的想法吓住，迟迟不动手。其实 10–20 例 + 简单脚本就够起步。
2. **eval 本身也要迭代**：当你直觉新版更好、但 eval 没反映出来——那是 eval 不够好的信号，去扩样本或换评估方式。
3. **找差点**：很多 agentic 应用在自动化人类任务，专挑**比人类专家差**的样本看，最容易找到改进方向。

## 下一讲

end-to-end eval 只告诉你"哪里不好"，但不告诉你**整个流水线里哪个组件**该背锅。下一讲讲 **error analysis（错误分析）**——agentic 高效开发的关键技能。

## 面试速答总结

**一句话**：agentic 系统该花精力在哪事先猜不准，所以**先快糙原型跑起来 → 看输出找高频错误模式 → 对那个模式建一个 20 例小 eval → 用百分比驱动迭代**；eval 按"有无每例 ground truth × 客观/LLM-judge"分四象限选型。

### 面试回答骨架（问"怎么给 agentic 系统做评测 / eval 怎么起步"）

> 1. **起手心法**：别花几周纯理论推演架构；先用**安全合理的 quick-and-dirty 原型**跑起来——有真实输出才知道精力该往哪投。
> 2. **核心循环（要会背）**：建系统 → **看输出**（人工过 ~20 条）→ 发现高频错误模式 → **会修就直接修，不会修就建小 eval**（10–20 例够起步）→ 用 eval 分数驱动迭代。看输出帮你决定**评测重心放哪**（发票里若是地址错就为地址建 eval）。
> 3. **eval 选型 2×2（关键框架）**：两个维度——**有无每例 ground truth × 客观代码评测 vs LLM-as-judge**：
>    - 有 GT + 客观：发票到期日抽取（约束输出格式 → 正则提取 → 比对 GT 算正确率）
>    - 无 GT + 客观：文案 ≤10 词（目标对所有样本一致 → Python 数词数）
>    - 有 GT + LLM-judge：研究 agent 漏点（专家列 3–5 gold points → judge 输出 `{score,explanation}`）
>    - 无 GT + LLM-judge：图表/创意按 rubric 打分
> 4. **为什么有时必须用 LLM-judge**：同一观点表述方式太多，**正则匹配不出来**——主观/语义类只能用 judge。

### 关键判断（加分点）

- **"看输出"是不可跳过的一步**：error pattern 不是想出来的、是看出来的；20 条样本人工过一遍的信息密度，远高于纸上推演。
- **eval 本身也要迭代**：当你直觉新版更好但 eval 没反映出来——这是 **eval 不够好**的信号，去扩样本或换评估方式，而不是相信直觉。
- **专挑"比人类专家差"的样本看**：agentic 应用多在自动化人类任务，差样本最容易暴露改进方向。
- **端到端的局限（引出下一讲）**：e2e eval 只说"哪里不好"，不说**流水线哪个组件该背锅**——需要 error analysis 做组件级归因。

### 为什么这是高分答法

- 不背"eval 很重要"的空话，而是给**可执行循环 + 2×2 选型框架 + 真实案例**；
- 点出"先糙后精""eval 也要迭代""看差样本"这些反直觉但高价值的实战纪律。

**一句话收尾**：eval 的关键不是一上来建大工程，而是**用快糙原型暴露真实错误、对高频模式建 20 例小 eval、用分数驱动迭代**；并按"有无 GT × 客观/judge"四象限选对评测方式——这是 agentic 高效开发与磕绊团队的最大分水岭。
