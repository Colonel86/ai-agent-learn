# L2 创建一个工具（Creating a Tool）

## 谜题：只会输出文本的 LLM 怎么"调函数"？

LLM 训练目标是生成文本 token，那"调用函数"到底是怎么发生的？本讲用**老式手写 prompt 的方式**拆开看，便于理解底层机制。

> 现代 LLM 已经被训练成原生支持工具调用，不再需要这种手写做法。但走一遍老流程能让你看清"魔法"背后的细节。

## 老式做法：用 prompt 约定一种输出格式

实现了 `getCurrentTime` 函数后，可以写一段 prompt 告诉 LLM：

> 你有一个工具叫 `getCurrentTime`。
> 想用它的时候，请输出全大写的 `FUNCTION: getCurrentTime`。
> 一旦我看到这串文字，就会替你调用并把结果告诉你。

### 完整流程拆解

1. 用户问："现在几点了？"
2. LLM 判断需要工具，输出：`FUNCTION: getCurrentTime`
3. **开发者写的代码**扫描 LLM 输出，发现这个标记串。
4. 解析出函数名 → 真正调用 `getCurrentTime()` → 拿到 `8 a.m.`。
5. **开发者代码**把 `8 a.m.` 拼回对话历史，再发给 LLM。
6. LLM 看到完整上下文（用户问题 + 自己的工具请求 + 函数返回值），生成最终回答："现在是 8 点。"

### 关键认知

**LLM 不直接调函数**——它只是按约定格式生成一段文本，开发者代码识别这段文本并代为执行，再把结果回传。

## 带参数的版本：getCurrentTime(timezone)

升级场景："新西兰现在几点？"——`getCurrentTime` 需要接收一个时区参数。

prompt 改成：

> 想用 `getCurrentTime` 时，请输出 `FUNCTION: getCurrentTime <时区>`。

LLM 输出例如：`FUNCTION: getCurrentTime Pacific/Auckland`

开发者代码：

1. 正则匹配出函数名和参数。
2. 调用 `getCurrentTime("Pacific/Auckland")` → 返回 `4 a.m.`。
3. 拼回对话历史。
4. LLM 输出："新西兰现在是 4 点。"

## 总结：让 LLM 用工具的通用流程

1. **提供工具**：实现函数，并告诉 LLM 它能用。
2. **LLM 请求调用**：以约定格式输出请求。
3. **开发者代码代为执行**：调函数，拿返回值。
4. **回传给 LLM**：把返回值加入对话历史。
5. **LLM 决定下一步**：可能直接给最终答案，也可能继续请求调下一个工具，循环。

## 老办法的缺陷

"全大写 FUNCTION + 名字"这种约定**笨拙**：

- prompt 要详细描述格式。
- 开发者要自己写解析逻辑（正则匹配等）。
- 不同项目格式不统一，容易出错。

## 下一讲

现代 LLM 已经被原生训练成支持工具调用，有**专用语法**让"请求调用"清晰可靠。下一讲展示现代写法。

## 面试速答总结

**一句话**：LLM 只会生成文本、**不会真的调函数**；工具调用本质是"**LLM 按约定输出请求 → 开发者代码解析并代为执行 → 返回值拼回上下文 → LLM 继续**"的闭环，现代原生 tool calling 只是把这套约定标准化、可靠化。

### 面试回答骨架（问"LLM 只输出文本，工具调用到底是怎么实现的"）

> 1. **拆穿魔法**：LLM 不直接执行函数，它只是**按约定格式生成一段文本**（老式手写如 `FUNCTION: getCurrentTime`）；真正调函数的是**开发者写的外层代码**。
> 2. **五步闭环（要能背）**：① 提供工具（实现函数 + 在 prompt/schema 里告诉 LLM）② LLM 以约定格式输出调用请求 ③ 开发者代码解析（正则/结构化）并真正执行 ④ 把返回值拼回对话历史 ⑤ LLM 看到完整上下文后决定——给最终答案 or 继续请求下一个工具，**循环**。
> 3. **带参数同理**：`FUNCTION: getCurrentTime Pacific/Auckland`，外层代码多一步解析参数再调用——说明"约定格式"要同时承载函数名 + 入参。
> 4. **老办法的缺陷（引出现代写法）**：全大写标记这种约定**笨拙且脆弱**——prompt 要详述格式、开发者要自写解析、跨项目格式不统一易出错；所以现代 LLM 被**原生训练**支持 tool calling，用**专用结构化语法**（function/tool schema + 结构化调用消息）取代手写约定，清晰可靠。

### 关键判断（加分点）

- **"控制权在外层代码"是安全/可观测的根**：因为执行发生在你的代码里，所以 sandbox、权限校验、参数校验、审计日志、人审（HITL）都卡在第 ③ 步——这点能接上工具安全话题。
- **第 ⑤ 步的"循环"就是 Agent loop 雏形**：多轮工具调用 = ReAct/agentic loop，由此可往多步推理、错误重试延伸。

### 为什么这是高分答法

- 不停留在"调 API"，而是讲清**底层机制 + 谁在执行 + 为何要标准化**；
- 用"老式手写 → 现代原生"的演进，自然带出 tool schema 存在的必要性。

**一句话收尾**：工具调用不是 LLM 自己执行，而是**"模型出意图、代码出执行"的协作**；现代 tool calling 把这套约定从手写 prompt 升级成结构化协议，换来可靠性与可控性。
