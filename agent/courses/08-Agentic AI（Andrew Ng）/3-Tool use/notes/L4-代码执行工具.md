# L4 代码执行工具（Code Execution）

讲者在多个 agentic 项目里都给过 LLM "写代码 + 执行"的能力，反复被它给出的解题方案惊艳。如果还没玩过 code execution，强烈推荐试一下。

## 引子：算数应用的"工具爆炸"问题

想做一个能解数学应用题的 agent，最朴素的做法是：

- 提供 `add` / `subtract` / `multiply` / `divide` 四个工具。
- 用户问"13.2 + 18.9"，触发 `add`，没问题。

但马上就有麻烦：

- 用户问"根号 2 是多少？" → 需要新加 `sqrt` 工具。
- 又要指数？三角函数？对数？……

看一眼科学计算器有多少按键就知道：**给每个运算单独造个工具完全不可持续**。

## 解法：让 LLM 写代码，提供"代码执行"工具

只给一个工具：执行任意代码。prompt 大致是：

> 写代码解答用户问题。把 Python 代码用 `<execute_python>...</execute_python>` 标签包裹返回。

流程：

1. 用户："根号 2 是多少？"
2. LLM 输出包含两行 Python 代码的回答（带 `<execute_python>` 标签）。
3. 开发者代码用正则提取标签之间的代码。
4. 执行，得到 `1.4142...`。
5. 数值回传给 LLM，它写出格式化好的最终回答。

一个工具搞定无数运算需求。复杂一些的（如复利计算、更难的数学题）也能可靠完成。

## 执行代码的几种方式

- **Python 的内置 `exec()`**：直接跑 LLM 生成的代码字符串。简单粗暴，但有安全隐患（见下）。
- **沙箱环境**：在隔离环境里跑代码，更安全。

## 结合反思：执行失败 → 让它重试

如果生成的代码出错，把报错信息回传给 LLM，让它反思修正，再试一两次。这往往能拿到正确结果——和反思模块的思想一脉相承。

## 安全警告：真实事故

讲者团队里有人用一个 agentic coder，结果它执行了类似 `rm *.py` 的操作，把项目目录里的 Python 文件全删了。

后来这个 agent 还"道歉"了——"是的，我承认这是个非常愚蠢的错误"——但人家文件已经没了。幸好仓库有 GitHub 备份才没造成实际损失。

## 最佳实践

- **生产环境跑 LLM 生成的代码，应放进沙箱**。
- 推荐工具：
  - **Docker**：经典容器化沙箱。
  - **E2B**：轻量级沙箱环境。
- 这能限制"坏代码"造成数据丢失或敏感数据泄露的风险。

讲者坦白：实际中很多开发者图省事会直接 `exec`，单行代码的风险其实不大；但只要任务复杂或涉及敏感系统，**沙箱该上就上**。

## 它有多重要

代码执行重要到很多 LLM 训练团队会**专门优化**模型的代码生成 + 执行链路。把这个工具加进你的工具箱，应用能力会有质的跃升。
