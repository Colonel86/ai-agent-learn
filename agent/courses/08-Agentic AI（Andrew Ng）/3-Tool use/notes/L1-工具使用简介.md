# L1 什么是工具使用（What are Tools）

## 核心思想

人类有了锤子、扳手能做的事比徒手多得多；LLM 有了"工具"也一样。

这里的工具不是物理工具，而是**函数（functions）**。"工具使用（tool use）"指的是：让 LLM 自主决定**何时请求调用某个函数**——去执行动作、获取信息或完成其它任务。

> 严格说 LLM 并不直接调用函数，而是"请求"开发者的代码替它调用。日常表达里大家常省略说"LLM 调用了工具"，但要记住底层机制。

## 一个最小例子：getCurrentTime

LLM 训练数据有截止日期，问"现在几点了？"它本来只能回答"抱歉，我不知道当前时间。"

给它一个 `getCurrentTime` 函数后，流程变成：

1. 用户：现在几点了？
2. LLM 检查可用工具集 → 决定调用 `getCurrentTime`。
3. 函数执行，返回值（如 3:20pm）。
4. 这个返回值被加入对话历史，再喂回 LLM。
5. LLM 输出最终回答："现在是 3:20pm。"

## 关键设计点：是否调用工具由 LLM 决定

同样配置下，如果用户问"绿茶里有多少咖啡因？"：

- LLM 判断这问题不需要当前时间。
- 直接回答，不调用 `getCurrentTime`。

讲者在课件里用**虚线框**标记"工具集"——表示这是提供给 LLM 自主选择的工具，而**不是开发者硬编码的固定步骤**。这跟之前 research agent 里"到这步必定执行 web search"的硬编码模式形成对比。

## 更多典型工具场景

| 用户提问 | LLM 可能调用的工具 |
|---|---|
| Mountain View 附近有哪些意大利餐厅？ | web search |
| 给我看买过白色太阳镜的客户 | query database |
| 存 $500，年利率 5%，10 年后有多少？ | interest calculator，或让 LLM 写一段数学表达式让代码执行 |

→ 作为开发者，要根据应用场景**预先想清楚需要哪些工具**并实现它们。

## 多工具协作：日历助手示例

请求："请在周四找一个空闲时段，跟 Alice 安排一个会议。"

可用工具集：

- `check_calendar`
- `make_appointment`
- `delete_appointment`

LLM 多步推理：

1. 先调 `check_calendar` → 返回周四空闲时段。
2. 把结果喂回 LLM → 它决定选 3pm。
3. 调 `make_appointment(Alice, 周四 3pm)` → 返回确认。
4. LLM 输出："已为你和 Alice 安排周四 3pm 的会议。"

这种"LLM 看返回结果再决定下一步"的循环，是工具使用的标准形态。

## 小结

- 工具使用让 LLM 应用能力跃升。
- 工具就是"开发者写好、LLM 可请求调用"的函数。
- 调不调、调哪个、按什么顺序调，都由 LLM 在运行时决定。

## 面试速答总结

**一句话**:Tool Use = 给 LLM 一组**函数**,让它**自主决定何时/调哪个/按什么顺序调**;底层关键——**LLM 不直接执行,只"请求"开发者代码替它调**,结果回填进对话再让它继续。

### 面试回答骨架(问"什么是 tool use / function calling 怎么工作")

> 1. **定义 + 纠正常见误解**:工具就是**函数**;tool use 指 LLM **请求**调用某函数去取信息/执行动作。**底层机制(必说)**:LLM 本身不调函数,它输出一个"我要调 X、参数是…"的请求,**由开发者的代码真正执行**,再把返回值喂回模型——"LLM 调用了工具"只是口语简化。
> 2. **标准执行循环**:用户提问 → LLM 看可用工具集、决定调谁 → 代码执行函数 → **返回值加入对话历史** → 喂回 LLM → 输出最终答案(或继续调下一个)。
> 3. **核心设计点——调不调由 LLM 运行时决定**:问"几点了"会调 `getCurrentTime`,问"绿茶含多少咖啡因"则不调直接答。这与"硬编码固定步骤"相反——工具是**给模型自主选择**的(讲者用虚线框标"工具集"=可选,非写死流程)。
> 4. **多工具协作**:日历助手("周四约 Alice"):`check_calendar` 拿空闲 → 喂回选 3pm → `make_appointment` → 确认。"**看返回结果再决定下一步**"的循环就是 tool use 的标准形态(= ReAct)。
> 5. **开发者的活**:按应用**预先想清楚需要哪些工具并实现**(web 搜索/查库/计算器/代码执行…)。

### 关键洞察(加分点)

- **tool use 是"自主性"的来源之一**:把"调哪个工具"的决策权交给 LLM = 往自主光谱右移(呼应 W1-L3)。
- **它把 Reflection 的"外部反馈"系统化了**:上一模块零散的"跑代码/搜索"反馈,在这里变成"系统化让 LLM 调函数"(呼应 L5)。
- **底层机制决定了工程重点在"开发者侧"**:工具的鉴权、参数校验、错误处理、副作用控制都在代码侧——这正是工具网关要管的(接 `02`)。

### 为什么这是高分答法

- 主动澄清"**LLM 不直接调、只是请求**"这层底层机制,区分会用 API 和懂原理;
- 用"调不调由模型决定 vs 硬编码"把 tool use 接到自主性光谱;
- 看到它和 Reflection 外部反馈、工具网关的结构关系。

**一句话收尾**:Tool Use 让 LLM 从"只会生成文本"变成"能请求执行动作";**决策权(调不调/调哪个/顺序)在模型,执行权和管控在开发者代码**——这一分工是后续工具契约/网关/沙箱的全部出发点。
