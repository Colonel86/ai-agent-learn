# W1-L7 智能体评估（Evaluating Agents / Evals）

> 原始字幕：`subtitles/W1-L7-evaluating-agents.vtt`

## 一、Evals 是最关键的技能

Andrew 的观察：
> 能不能构建出好的 agentic 工作流，**最大的预测因子**是能否推行一个**严谨自律的评估流程**。

你驱动 evals 的能力 = 你构建 agentic 工作流的能力。

---

## 二、Evals 的基本打法

**不要试图提前构建 evals。** 因为构建之前，你根本不知道会出什么错。

**推荐流程**：
1. 先把 agentic 工作流跑起来；
2. 查看输出，**手动寻找你希望它做得更好的地方**；
3. 把发现的问题编码成可自动评估的指标。

### 实例：客户订单咨询 Agent
手动审查输出，发现一个意料之外的问题：
> Agent **不应提到竞争对手**，但它在回复里说："我们比 ComproCo 好多了" "和 RivalCo 不一样，我们退货更简单"。

这种问题**很难事先预料**。所以：**先建后查，发现问题再加 evals。**

---

## 三、两大类 Evals

### 1. 客观指标（Objective Criteria）→ **用代码评估**
- "有没有提到竞争对手" 是非黑即白的；
- 维护一个竞争对手名单（ComproCo、RivalCo……）；
- 写代码搜索输出里是否出现这些名字；
- 统计出现频率 / 占比。

### 2. 主观指标（Subjective Criteria）→ **LLM 作裁判（LLM-as-a-Judge）**
- LLM 输出是自由文本，很多质量维度无法直接用代码评估；
- 可以用**另一个 LLM** 当裁判：
  ```
  请给下面这篇文章打 1-5 分，1 最差 5 最好：
  {{essay}}
  ```
- 随着迭代改进 agent，这个分数应该上升。

⚠️ **Andrew 的经验提示**：
> LLM 在 1–5 分这种分级上**并不擅长**。你可以试，但他自己**不太用**这种方式。后续模块会讲更准确的 LLM-as-judge 技巧。

---

## 四、两个层级的 Evals

| 类型 | 说明 |
|---|---|
| **端到端（End-to-End）** | 评估整个 agent 的最终输出质量 |
| **组件级（Component-level）** | 评估 agent 工作流中**单个步骤**的输出质量 |

这两种服务于开发流程的不同阶段。

---

## 五、错误分析（Error Analysis）

除了跑 evals，Andrew 经常做的事情：
- 查看 **中间输出 / LLM trace**；
- 逐步阅读每个步骤的输出，**寻找改进机会**。

Evals + Error Analysis 是核心技能，第 4 模块会深入讲。

---

## 六、本节要点

| 技能 | 做法 |
|---|---|
| 发现问题 | 先跑起来 → 手动看输出 → 找不满意的地方 |
| 客观问题 | 写代码计数指标 |
| 主观问题 | LLM-as-a-Judge（有局限，后续讲更好方法） |
| 定位问题 | 阅读中间 trace，做 error analysis |

> 下一节：**Agentic 设计模式** —— 构建智能体工作流最重要的几个模式。

---

## 面试速答总结

**一句话**:Evals 是构建好 agent 的**最大预测因子**;打法是**别提前建 eval,先跑起来→手动看输出找问题→把问题编码成指标**;客观问题用代码、主观问题用 LLM-as-judge,再配 error analysis 看 trace 定位。

### 面试回答骨架(问"你怎么评估 / 保证 agent 质量")

> 1. **先立观点**:能不能做好 agent,最大预测因子是**有没有严谨自律的评估流程**——"你驱动 eval 的能力 = 你构建 agent 的能力"。
> 2. **打法:先建后评,别提前造 eval**:**建 eval 之前你根本不知道会出什么错**。流程是 ①先把工作流跑起来 → ②手动看输出、找"希望它做更好"的点 → ③把发现的问题**编码成可自动评估的指标**。(经典例:客服 agent 意外**提到竞争对手**——这种问题事先想不到,只能跑出来才发现。)
> 3. **两类指标,分而治之**:
>    - **客观(非黑即白)→ 代码评估**:如"有没有提到竞品",维护竞品名单 + 写代码计数/占比。**能用代码就别用 LLM。**
>    - **主观(自由文本质量)→ LLM-as-a-Judge**:用另一个 LLM 打分。⚠️**坦诚局限**:LLM 在 1–5 分级上并不擅长(Andrew 本人少用),要用更可靠的判别式设计(成对比较/带 rubric 等)。
> 4. **两个层级**:**端到端**(整体最终输出)+ **组件级**(单个步骤输出)——分别服务开发的不同阶段;组件级 eval 才能定位是哪一步坏了。
> 5. **配 error analysis**:不只看分数,还要**读中间输出 / LLM trace**,逐步找改进机会——这要求系统**可观测**。

### 最该背的两个金句

- **"别提前建 eval——建之前你不知道会出什么错;先跑、手动看、再把问题变成指标。"**
- **"能用代码评的就别用 LLM 评;LLM-as-judge 是兜底,且分级打分不可靠。"**

### 为什么这是高分答法

- 给的是**流程**(先跑→手动找→编码成指标→迭代)而非"我会写 eval";
- **主动承认 LLM-as-judge 的局限**,显示真做过而非背概念;
- 区分**客观/主观**和**端到端/组件级**两套二分,体现框架化;
- 落到 **trace/可观测 + error analysis**,接得上工程实践。

**一句话收尾**:Eval 不是上线前的验收,而是**贯穿开发的迭代引擎**——先跑起来手动找问题,客观用代码、主观用(可靠设计的)LLM-judge,再靠 trace 做 error analysis 持续改进。
