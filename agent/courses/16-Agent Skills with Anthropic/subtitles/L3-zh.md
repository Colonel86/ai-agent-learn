# L3 Skills 在 Agent 生态中的位置 —— 与 MCP、工具、子 Agent 的关系

Skills 可以与工具（Tools）、MCP、子 agent（subagents）组合，搭建强大的 agentic 工作流。本节梳理它们各自的定位与配合方式。

## 一张图先看全貌

构建 AI 应用时，可以这样分工：

- **MCP 服务端**：注入外部上下文、数据、工具
- **子 agent**：在自己的主线程里并行执行，隔离上下文
- **Skills**：承载可重复的工作流

## Skills vs MCP

| 维度 | MCP | Skills |
|---|---|---|
| 解决什么 | 连接外部系统和数据 | 教 agent 用这些数据**做什么、怎么做** |
| 典型场景 | 接外部数据库、Google Drive、各种 API | 把工具串成可重复、可预测的工作流 |
| 类比 | 提供"原料和工具" | 提供"做这道菜的步骤" |

**配合关系**：用 MCP 接入底层工具与数据，用 Skill 编排这些工具，产出你想要的结果。

## Skills vs Tools（工具）

可以把**工具想成更底层**的东西：锤子、锯子、钉子；而 **Skill 是"如何造一个书架"** ——一个把工具组合起来的方法论。

工具的特点：

- 提供底层访问系统/能力的入口
- 是 Skill 能被读取、生成、执行的**底层支撑**（读 Skill 文件、跑脚本，都靠 bash + 文件系统这类工具）
- 来源多样：agent 生态内置、自己写、或通过 MCP 注入

**关键差异**：

- 工具定义**始终在上下文窗口**
- Skill 是**渐进式加载**

## Skills + Tools 协作

Skill 可以引用脚本——这些脚本相当于"按需启用的工具"。

> 如果某个工具不是每次都用，把它放进 Skill 里，让渐进式披露机制决定何时加载。

## Skills vs 子 Agent（Subagents）

### 子 agent 是什么

主 agent 派生（spawn）出来的 agent，可以向父 agent 回报。Claude Code、Agent SDK 都支持，也可以自己实现。

### 子 agent 的价值

- **隔离上下文**（isolated context）
- **细粒度权限**
- **并行执行**

### 子 agent 能访问什么

- 有限的工具权限
- 你**显式指定**的 Skill 集合

### 配合示例：Code Reviewer 子 agent

- 任务专一：分析与审阅代码
- 加载 Skill：内含**你的团队/公司**对代码审阅的具体要求

## 综合例子：Customer Insight Analyzer

把一切放到一起，假设要做客户洞察分析：

1. **主 agent** 持有从 MCP 拿来的工具/数据/资源
2. **派发子 agent**：并行分析客户访谈、客户调研
3. **Skills** 告诉它们如何归类反馈、如何汇总发现、如何分析访谈与问卷、如何按规则可预测地输出

→ MCP 注入数据，子 agent 并行隔离执行，Skills 让产出可预测、可复制、可移植。

## 整体地图

从原子到复杂：

- **Prompt**：最小通信单元，但难以跨团队/公司扩展
- **Skill**：把 prompt、代码、资源打包成可复用模块
- **子 agent**：把 Skill 用起来执行专项任务
- **MCP**：为 agent 注入底层工具与外部数据

## 何时用什么？把上下文窗口当公共资源

- **MCP**：需要外部数据/工具时
- **子 agent**：当某任务最好在独立线程、独立上下文中完成，或需要并行
- **Skills**：用于**程序化、可预测的工作流**

### 持久性维度

- **子 agent**：可跨多个会话持久化（父 - 子之间）
- **Skills**：跨对话持久化（与用户和 AI 应用之间）

### 选用准则

- **优先用 Skill 处理可预测的程序化工作流**
- **只在必要时才用子 agent 承担完整的 agentic 逻辑**
