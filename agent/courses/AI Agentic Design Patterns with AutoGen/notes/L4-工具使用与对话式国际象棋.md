# L4 · 工具使用与对话式国际象棋（register_function + 嵌套聊天执行工具）

> 课程：AI Agentic Design Patterns with AutoGen（DeepLearning.AI × Microsoft × Penn State，讲师 Chi Wang & Qingyun Wu）
> 本课任务：给 agent 加上 **Tool Use** 能力——两个棋手 agent 通过调用工具在棋盘上走**合法棋**，并用 L3 学过的嵌套聊天把"提议工具→执行工具"的回路藏在幕后。

## 0. 本课目标与路线

前几课的 ConversableAgent 只会用 LLM 生成回复；本课引入新能力——**工具调用**，并复用嵌套聊天（nested chat）这一对话模式让 agent 借工具完成任务。示例是一盘对话式国际象棋：Player White 与 Player Black 两个 agent 对弈，每步棋都必须通过工具落在真实棋盘上。模型用 `gpt-4-turbo`——讲师明说原因：它比 GPT-3 是好得多的棋手。

路线四步：**① 定义工具函数 → ② 创建棋手 + 棋盘代理 agent → ③ 注册工具（caller/executor 分离）→ ④ 注册嵌套聊天并开局**。

## 1. 定义工具：带 Annotated 注解的普通 Python 函数

用 `chess` 库承载棋局状态，一个全局变量跟踪"这一轮是否已走子"：

```python
import chess
board = chess.Board()   # 棋盘 = 共享的真实世界状态
made_move = False       # 跟踪"是否已走子"，后面做终止条件用
```

**工具一：查询合法走法**。返回 UCI 格式（agent 之间描述走子的"语言"）的合法走法列表：

```python
def get_legal_moves() -> Annotated[str, "A list of legal moves in UCI format"]:
    return "Possible moves are: " + ",".join(
        [str(move) for move in board.legal_moves]   # 合法走法由棋盘对象给出
    )
```

讲师强调 `Annotated` 这段注解**非常重要**：它让 agent 理解返回内容的格式和语义含义——这些文字之后会被自动搬进 OpenAI 工具定义的 schema 里。

**工具二：走子**。入参与返回值同样全部注解：

```python
def make_move(
    move: Annotated[str, "A move in UCI format."]
) -> Annotated[str, "Result of the move."]:
    move = chess.Move.from_uci(move)
    board.push_uci(str(move))        # 把走子推到棋盘上（非法走法会在这里抛错）
    global made_move
    made_move = True                 # 标记"已走子"→ 触发嵌套聊天终止
    display(chess.svg.board(board, ...))   # 顺手把棋盘画出来
    piece = board.piece_at(move.to_square) # 取棋子名做人话描述
    ...
    return f"Moved {piece_name} ({piece_symbol}) from {起点} to {终点}."
```

除注解外它就是普通 Python 函数——**用户不需要为 agent 消费工具做任何额外工作**。

## 2. 创建 agents：两个棋手 + 一个棋盘代理

两个棋手 agent 只差名字和执子颜色，system message 里明确告知工具使用顺序：

```python
player_white = ConversableAgent(
    name="Player White",
    system_message="You are a chess player and you play as white. "
    "First call get_legal_moves(), to get a list of legal moves. "   # 先查合法走法
    "Then call make_move(move) to make a move.",                     # 再走子
    llm_config=llm_config,
)
```

注意：system message 里"告诉"agent 有哪些工具还不够，**必须后续注册工具给它具体定义**。

第三个 agent 是 **Board Proxy（棋盘代理）**——不用 LLM，专职陪棋手核对走子直到走出合法一步：

```python
def check_made_move(msg):
    global made_move
    if made_move:
        made_move = False   # 读一次就复位，供下一轮复用
        return True
    return False

board_proxy = ConversableAgent(
    name="Board Proxy",
    llm_config=False,                      # 不用 LLM
    is_termination_msg=check_made_move,    # 已走子 → 结束本轮对话
    default_auto_reply="Please make a move.",  # 没走子就只会催这一句
    human_input_mode="NEVER",
)
```

机制：棋手若走非法棋，`make_move` 在 `board.push_uci` 处抛错、`made_move` 不会置 True，board_proxy 就一直回 "Please make a move." 逼棋手重试——**合法走子约束不靠 LLM 自觉，靠确定性代码 + 终止条件闭环保证**。

> **架构师视角**：这里出现了 AutoGen 工具使用的核心分工——**提议工具调用的 agent（caller，有 LLM）和执行工具的 agent（executor，无 LLM）是两个角色**。LLM 只产生"意图"（一个 JSON 的函数调用请求），真正碰状态（棋盘）的是确定性的 proxy。把"想"和"做"拆开，执行侧就成了天然的拦截点：校验、审批、限流都可以加在 executor 上而不污染 LLM 的提示词。

## 3. 注册工具：register_function 与 caller/executor

```python
from autogen import register_function

for caller in [player_white, player_black]:   # 两个棋手都要注册
    register_function(
        get_legal_moves,
        caller=caller,          # 谁有权"提议"调用（写进它的 llm_config.tools）
        executor=board_proxy,   # 谁负责真正执行
        name="get_legal_moves",
        description="Get legal moves.",
    )
    register_function(make_move, caller=caller, executor=board_proxy,
                      name="make_move", description="Call this tool to make a move.")
```

`register_function` 是一步到位的封装，等价于底层两个调用：**`register_for_llm`（把工具 schema 注入 caller 的 LLM 配置，使其能提议调用）+ `register_for_execution`（把函数实现挂到 executor，使其能执行）**。注册后可用 `player_black.llm_config["tools"]` 检视生成结果——一份标准 OpenAI 工具定义：

```
[{"type": "function",
  "function": {"name": "get_legal_moves",
               "description": "Get legal moves.",
               "parameters": {...}}},        # type/description/parameters 全部自动填充
 {"type": "function", "function": {"name": "make_move", ...}}]
```

这正是 `Annotated` 注解的去处：**用户不必手写 OpenAI 格式的工具 schema，AutoGen 从函数签名 + 注解自动生成**。

> **对比课程 09（Functions, Tools and Agents with LangChain）**：LangChain 用 `@tool` 装饰器 + Pydantic 模型生成 schema，绑定后**同一个链既提议也执行**；AutoGen 从第一天就把 caller 和 executor 拆成两个 agent，工具调用本身成为一条**对话消息**。再对比课程 10-MCP：MCP 把"工具定义在哪、由谁执行"进一步推到进程外的 server，schema 由协议层 `list_tools` 下发——三者其实是同一件事（LLM 拿到 schema → 产出调用意图 → 某处执行）在**进程内函数 / 进程内双 agent / 跨进程协议**三个尺度上的实现。选型见 `4-tools.md` 工具层。

## 4. 嵌套聊天：把"选合法棋"的回路藏进幕后

外层是两个棋手你来我往；但每次回复前，棋手要先和 board_proxy 打一轮**内层对话**把棋走掉。用 L3 学过的 `register_nested_chats`：

```python
player_white.register_nested_chats(
    trigger=player_black,        # 收到 player_black 的消息时触发
    chat_queue=[{
        "sender": board_proxy,       # 内层对话由棋盘代理发起
        "recipient": player_white,   # 对象是棋手自己
        "summary_method": "last_msg",# 内层最后一条消息作为摘要带回外层
    }],
)
# player_black 对称注册：trigger=player_white
```

一步棋的完整时序：

```
外层  player_black ──"Let's play chess! Your move."──▶ player_white
                                                          │ 触发嵌套聊天
内层  board_proxy ◀──────────────────────────────────▶ player_white
        │  ① white 提议 get_legal_moves()（caller 提议）
        │  ② board_proxy 执行，返回所有合法走法（executor 执行）
        │  ③ white 提议 make_move("e2e4")
        │  ④ board_proxy 执行 →"Moved pawn from e2 to e4."
        │     made_move=True → check_made_move 命中 → 内层终止
外层  player_white ──（last_msg 摘要：已走 e2e4）──▶ player_black
      player_black 同样进嵌套聊天走出 g8f6 …… 直到 max_turns=2 用完
```

开局代码：

```python
board = chess.Board()
chat_result = player_black.initiate_chat(
    player_white,
    message="Let's play chess! Your move.",
    max_turns=2,   # 外层限两轮
)
```

## 5. 加点乐子：chitchat 变体与 silent 开关

只改 system message 一句话，棋手就从"报棋谱机器"变成会互相叫阵的对手：

```python
system_message="... Then call make_move(move) to make a move. "
"After a move is made, chitchat to make the game fun.",   # 新增的唯一动作
```

重建 agent 后需**重复注册工具和嵌套聊天**（注册挂在 agent 实例上，新实例不继承）。这次 chat_queue 里多加 `"silent": True`——内层对话不再打印，只看外层两个棋手的交锋。效果立竿见影：白方走 e4 后附一句 "Let's see how you respond to this classic opening."，黑方回敬西西里防御并反问战略，你来我往。想加人类入局，把棋手的 `human_input_mode` 设为 `"ALWAYS"` 即可。

## 6. 通用模式提炼

讲师收尾点题：本例只是"嵌套聊天内用工具"的一种用法，但**通用规律不变——用工具就需要一个能提议工具调用的 agent 加一个能执行工具的 agent**。两种呈现选择：

| 呈现方式 | 做法 | 适用 |
|---|---|---|
| 隐藏式 | 把提议+执行藏进嵌套聊天 | 对外呈现"单个全能 agent"的体验，外部无需知道内部有两个 agent |
| 显式分离 | 提议者与执行者都暴露在外层对话 | 需要向用户/审计明示"谁提议、谁执行"的场景 |

> **对比 11-design-patterns.md 的模式层**：Tool Use 是 Andrew Ng 四大 Agentic 模式之一，但在我的选型体系里它**不占形态、属 augmented LLM 底座**（单步动作原语，归 `0-action-paradigm.md`/`4-tools.md`），而 Reflection/Planning/Multi-Agent 才是叠加维度。本课有意思之处正在于把这两层揉在一起演示：Tool Use（原语层）× Nested Chat（Multi-Agent 编排层）——工具是能力，嵌套聊天是把能力组织起来的形态。

## 7. 本课总结

| 要点 | 一句话 |
|---|---|
| Annotated 注解 | 函数签名 + 注解自动生成 OpenAI 工具 schema，无需手写 |
| caller/executor 分离 | LLM agent 提议调用，无 LLM 的 proxy 执行，`register_function` 一次挂两头 |
| register_for_llm / register_for_execution | `register_function` 的两个底层动作：schema 进 caller、实现进 executor |
| 合法走子约束 | 非法走子抛错 → made_move 不置位 → board_proxy 死循环催促重试 |
| 嵌套聊天藏工具 | 内层选棋走棋，last_msg 摘要回外层，对外只见"一个会下棋的 agent" |

> **记忆点（引出 L5）**：本课的工具是**预定义函数**——LLM 只能在 `get_legal_moves`/`make_move` 里二选一，安全但受限，且依赖模型原生的 function-call 特性。L5 换一条路：让 agent **自由写代码（freeform coding）**并真的执行，去完成一个金融分析任务——能力上限陡增，安全问题也随之登场。
