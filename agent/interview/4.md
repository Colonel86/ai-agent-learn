这也是一个很好的面试题，考点在于你是否理解 LLM 的概率本质，以及如何用工程手段逼近确定性。诚实的开场很重要：**LLM 是概率模型，无法从模型层面"保证"100%，但可以通过约束和工程兜底把可靠性做到接近 100%**。然后分层展开：

**1. API 层面的硬约束（最接近"保证"的手段）**

- `tool_choice` 参数：Anthropic/OpenAI 都支持强制调用。`tool_choice: {"type": "tool", "name": "xxx"}` 强制调用指定工具，`{"type": "any"}` 强制至少调用一个工具。这是唯一真正意义上的"100%"——模型被约束在 tool call 的输出空间里，不可能返回纯文本。
- 底层原理可以提一句：这本质是 constrained decoding / structured output，采样时用语法约束 mask 掉不合法 token，所以输出格式是有保证的。但注意：**格式有保证 ≠ 参数内容正确**，模型仍可能填错参数值。

**2. 架构层面：不该交给概率的就不要交给概率**

这是最能体现你资深度的一点。如果某个环节"必须"调用工具，那这个决策就不该由 LLM 做——在 LangGraph 里直接用确定性的边（edge）路由到 ToolNode，而不是让模型自由决定。原则是：**LLM 负责判断和生成，流程控制交给图结构**。你做 Mentis v2 时如果有类似设计可以直接举例。

**3. 提示与工具定义层面（提高自然命中率)**

- 工具的 name/description 写清楚触发条件和边界，这是最被低估的一环——工具描述本质上就是给模型的 prompt；
- 减少工具数量、避免功能重叠的工具（工具越多，选择错误率越高，必要时分层路由或动态检索工具）；
- system prompt 里明确规则 + few-shot 示例。

**4. 兜底与验证层面（工程闭环）**

- 输出校验：用 Pydantic/JSON Schema 校验参数，失败就带着错误信息重试（reflection loop）；
- 在 LangGraph 里加一个校验节点：检测到应调用工具但没调用时,路由回去重试或走 fallback；
- 设置最大重试次数 + 降级策略。

**5. 度量层面（你怎么知道它是不是 100%）**

用评估集持续测量 tool call 的触发率和参数正确率（LangSmith/Langfuse 上做 trace + eval），上线后监控漏调率。没有度量就谈不上保证。

**6. Hook

一个简洁的口头回答结构："严格说 100% 只有一种方式，就是 API 层强制 `tool_choice`；但更好的架构思路是——必须调用的场景不交给模型决策，用图结构确定性路由；模型自由决策的场景则靠工具描述、few-shot、参数校验加重试兜底，最后用评估和线上监控验证实际达到的可靠性。"

API 硬约束（tool_choice）→ 架构确定性路由（graph）→ 运行时拦截（hook）→ 评估监控闭环
