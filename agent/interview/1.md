# 1 - Long-Term Memory:semantic / episodic / procedural

AI Agent 记忆架构里的一组核心概念,借用自认知心理学(Tulving 的记忆分类),现在被 LangGraph / LangMem 这类框架拿来组织 Agent 的长期记忆。

下面按「**概念 → 工程落地**」的顺序展开。

---

## 1. 大框架:长期记忆 vs 短期记忆

- **短期记忆(short-term / working memory)**:通常就是 context window 里的对话缓冲,会话结束就没了。
- **长期记忆(LTM)**:持久化到外部存储(向量库、KV、图数据库等),跨会话存活。

LTM 内部,按「**存的是什么内容**」分成三类。

---

## 2. 三类长期记忆

### Semantic(语义)— 事实与知识,回答「是什么」

去情境化的事实、概念、用户画像。不关心「什么时候发生的」,只关心「这件事为真」。

- 例:`用户基于香港`、`用户偏好 LangGraph 而非 CrewAI`、`项目 Argus 是一个 DeFi 分析系统`
- 存储形态:profile 文档、三元组(subject-predicate-object)、知识库条目
- 检索:语义相似度召回,或直接按 key 取 profile

### Episodic(情景)— 具体经历,回答「发生过什么」

带时间戳的、具体的过往交互 / 事件。核心是「那一次」。

- 例:`上次用户让我做 meme coin 发现系统时,我用 Helius + DexScreener 的组合成功了`
- Agent 里最常见的用途是 **few-shot 示例检索**:把过去成功完成任务的完整轨迹存下来,下次遇到类似任务时召回作为示范
- 存储形态:对话片段、(task, trajectory, outcome) 三元组

### Procedural(程序)— 技能与规则,回答「怎么做」

「如何执行」的知识,本质是 Agent 自己的行为规则。

- 例:Agent 的 system prompt、工具调用的固定 pattern、随交互不断自我修正的指令
- 关键区别:前两类是 Agent「知道的东西」,这一类是 Agent「做事的方式」
- LangMem 里 procedural memory 的典型实现就是 **让 Agent 反思后改写自己的 system prompt / rules**(self-improving prompt)

### 对照表

| 类型 | 回答的问题 | 人类类比 | Agent 实现 |
|------|-----------|---------|-----------|
| Semantic | What(是什么) | 「巴黎是法国首都」 | 用户画像 / 知识库 |
| Episodic | When / What happened(经历) | 「去年我去过巴黎」 | few-shot 示例库 |
| Procedural | How(怎么做) | 「我会骑自行车」 | system prompt / 规则演化 |

---

## 3. 三种写入策略

三类记忆的本质差异,落到工程上就是三套不同的更新策略——这是把它们用同一套 upsert 处理会出问题的根因(episodic 被去重、procedural 没法回滚,都是没分清导致的)。

- **Semantic → 增删改**:矛盾事实必须主动删,否则召回打架。
- **Episodic → 纯追加**:过去发生过就是发生过,不改。
- **Procedural → 整体重写 + version bump**:规则演化要可回溯。

---

## 4. 映射到 LangGraph BaseStore

核心思路:用 **namespace 分层 + 每类独立的 schema**。

- `namespace`(元组)决定「这是哪类记忆、属于谁」
- `key` 决定「是哪一条」
- `value` 是结构化的 Pydantic 对象
- 语义检索靠 `index` 配置的 embedding

两个容易卡住的设计决策:

**namespace 分层是隔离边界,不只是命名。**
`(owner_id, mem_type, sub_bucket)` 这个元组,`store.search` 按 prefix 检索,所以 per-user / per-agent 的 scope 是天然的。其中 procedural 故意挂在 `agent_id` 而非 `user_id` 下——「怎么做」是 agent 的能力,不该随用户走;semantic / episodic 才是 per-user。

**embedding 只 embed 该 embed 的字段。**
episodic 只对 `observation`(触发场景)做向量化,召回时拿当前任务去匹配——你要找的是「和现在这个任务像的过去经历」,不是「措辞像的」;整条 embed 的话,`result` 里的复盘文字会污染匹配。procedural 直接传 `index=False`,它按固定 key 取,根本不走语义召回。

---

## 5. 短期 vs 长期在 LangGraph 里的落点(对照 DAPPOS V3 two-tier)

| 层 | LangGraph 组件 | 作用域 | compile 参数 |
|----|---------------|--------|-------------|
| 短期 | checkpointer | thread 内 | `checkpointer=` |
| 长期 | store | 跨 thread | `store=` |

这俩在 `compile()` 时是两个独立参数。

很多「两层」实现其实是 **working memory + semantic**,缺了:

- episodic 的成功轨迹召回(让 Agent「想起上次怎么做对的」)
- procedural 的自我改写(就是 LangMem 那套 prompt optimizer 干的事)

这两块往往是后续拉开 Agent 表现的抓手。

---

## 6. 实现选择:裸 Store vs LangMem

- **要细控制** → 用裸 `BaseStore` 自己写三套读写。
- **要快** → 上 LangMem(封装好了 semantic / episodic 抽取 + procedural prompt optimizer)。

LangMem 底层 semantic 的可靠增量更新用的是 **trustcall 的 JSON-patch**,避免每次让 LLM 重吐整个 profile 对象导致字段丢失——这个坑自己实现时也一定会踩到。


# 2 - agent 当有human in the loop的时候如何恢复对话呢？
好问题,这正好接上前面 checkpointer 那条线——HITL 的"恢复"能力**完全建立在 checkpointer 之上**,没有 checkpointer 就没有"暂停-恢复"。让我先确认下当前 `interrupt` API 的状态,这块 LangGraph 这一两年改过几版:核心一句话:**HITL 的"恢复"不是重放对话,而是 checkpointer 把暂停那一刻的完整状态快照恢复出来,再用 `Command(resume=...)` 把人的输入喂回去**。这正好接上前面那条 checkpointer 的线——`thread_id` 就是那个"游标/主键"。

## 暂停-恢复的机制

`interrupt()` 在节点里被调用时,会抛一个 `GraphInterrupt` 异常,运行时捕获后把当前 state 快照存进 checkpointer 并停下,同时把 `interrupt()` 的参数作为 payload 抛给调用方。resume 时必须用 `Command` 原语把值传回去;而且整个机制依赖 checkpointer 持久化 state,没有 checkpointer 就用不了。

一个完整周期:

```python
config = {"configurable": {"thread_id": "session-42"}}

# 1) 首次运行,跑到 interrupt 处暂停
for chunk in graph.stream({"messages": [...]}, config):
    if "__interrupt__" in chunk:
        payload = chunk["__interrupt__"][0].value   # 要给人看的内容(问题/待批准的动作)

# ... 这里时间可以过去几小时、几天,进程甚至可以重启 ...

# 2) 人回来了,恢复:同一个 thread_id + Command(resume=...)
for chunk in graph.stream(Command(resume="approve"), config):
    ...
```

关键在第 2 步:只要 `thread_id` 和第 1 步一致,checkpointer 就能定位到那条线的快照,从中断节点继续。`Command(resume=...)` 里的值,就是节点里 `interrupt()` 那行的返回值。

## 跨进程 / 隔很久才回来——生产里真正的场景

这是你问"如何恢复对话"最实际的那一面。因为 checkpointer 保存了中断前的完整状态(channel values、下一步要执行的节点、pending tasks),agent 可以被暂停几小时甚至几天,恢复时加载快照,继续执行就像只过了几毫秒一样。

所以一个**全新的进程**也能恢复——前提是 checkpointer 是**持久化**的。这就是为什么生产必须用 `PostgresSaver` 而不是 `InMemorySaver`:`InMemorySaver` 进程一重启快照就没了,人再回来就接不上。换句话说,前面那张 Postgres 表(checkpointer)正是让 HITL "隔天恢复" 成为可能的那一层。

## 怎么判断"该恢复"还是"全新输入"

人回来时,你的服务端需要先判断这条 `thread_id` 是不是处在中断态,否则不知道该传 `Command(resume=...)` 还是传新消息。用 `get_state`:

```python
snapshot = graph.get_state(config)

if snapshot.next:                      # next 非空 = 有 pending 节点 = 处于中断态
    pending = snapshot.tasks[0].interrupts   # 取出当初抛给人的 payload
    # → 走 Command(resume=人的回答) 路径
else:
    # → 走全新输入路径,graph.stream({"messages":[新消息]}, config)
```

`snapshot.next` 和 `snapshot.tasks[].interrupts` 是你恢复 UI 的依据:把待批准的动作重新渲染给人看,拿到回答再 resume。

## 三个必须注意的坑

**1. 恢复时整个节点从头重跑,不是从 `interrupt()` 那一行继续。** 运行时是从节点开头重新执行的,`interrupt()` 之前的代码会再跑一遍。所以**副作用(写库、扣费的 API 调用、发消息)必须放在 `interrupt()` 之后**,之前只放纯计算,否则人一批准就重复执行一次。

**2. 节点里多个 `interrupt()` 靠"顺序"匹配 resume 值,不能条件跳过。** LangGraph 按 interrupt 在节点里出现的顺序、严格按索引匹配 resume 值,所以调用顺序必须稳定。别用 `if` 有时跳过某个 `interrupt()`,也别用非确定性的 `while True` 校验循环——要做输入校验,用条件边绕回来,而不是在节点内循环 `interrupt()`。

**3. 设计"人永远不回来"的情况。** 生产里一定有线程挂着没人响应。建议查 checkpointer 里 `updated_at` 超过 TTL 的 thread,做自动拒绝或重新提醒——否则这些半中断的 thread 会一直占着。



# Agent 开发全栈五层

Agent 开发的全栈五层 + 一个模型底座(L0)+ 两条正交横切带——L0 模型/推理基座 → L1 底层契约(结构化输出/工具/action)→ L2 核心机制(规划/状态机)→ L3 上下文(RAG/记忆)→ L4 多 Agent 协作 → L5 部署/安全运行时; **协议** 与 **度量·观测(评测+tracing)** 是贯穿所有层的正交横切带,不占某一层。

> 组织逻辑:**水平层之间故障向上级联,每一层都假设它下面那层已经可靠**——所以自底向上稳固。
> 唯一例外是最底的 **L0(概率底座)**:它天生不可靠,L1 的职责恰恰是"假设 L0 不可靠并驯服它",而不是信任它。
> 结构化输出(L1)一抖,上面全部不可信;度量·观测横切带缺失,所有层的改动都是盲改。
> Demo 通常只需把 L0–L3 跑通;**生产的分水岭在 L4–L5 + 横切带**(多 Agent 协调 + 部署 + 评测/观测),这也是大多数团队真正翻车的地方。

```
        ┌─ 横切带 B:度量·观测(评测 + tracing)── 从 L0 起包裹整栈,搭建上应最先存在 ─┐
   L5   │  部署 / 安全运行时    部署形态 / 沙箱·审批 / 限流降级     ← 让它可运维、可控
   L4   │  多 Agent            拓扑 / 通信 / 任务分解              ← 单 Agent 不够时才上
   L3   │  上下文              RAG / 记忆 / 长上下文取舍           ← 把对的 token 喂进窗口
   L2   │  核心机制            规划 / 状态机                       ← Agent 怎么决策和移动
   L1   │  底层契约            结构化输出 / 工具 / action 范式      ← 概率输出 ↔ 确定性代码接口
   L0   │  模型/推理基座        选型分档 / 路由级联 / 微调 / 推理    ← 概率底座(贯穿选型轴)
        └─ 横切带 A:协议   MCP 锚 L1 · A2A 锚 L4 · AG-UI/ACP(Zed) 锚 L5 ────────────┘
```

---

## L0 · 模型/推理基座:选型 / 路由 / 微调 / 推理预算

**定位.** 整个栈的**概率底座**。它不是一个"会向上级联故障的水平层",而是一条**贯穿选型轴**:每个 LLM 节点都要在这一层做取舍。架构师最高频、最影响**成本-质量-延迟**的决策都在这里。

### 关键决策

- **分档选型**:旗舰 / 中端 / 小模型 / 专用模型,**按节点分档**——不是整个系统一个模型。
- **路由与级联**(降本不降质的头号杠杆):便宜模型先行,置信度低或失败再升级(LLM cascade / FrugalGPT 思路)。
- **自托管 vs API**:数据合规、成本曲线、可控性 vs 省事、随时用上最新模型。
- **微调 / 蒸馏 / 量化**:把旗舰能力蒸到小模型、量化压部署成本——与 L5 数据飞轮接续(生产数据回流 → 蒸馏)。
- **推理参数与 test-time compute**:temperature/top-p、思考预算/推理档位——"想多久"本身就是可调的成本旋钮。

### 核心张力

**能力 vs 成本/延迟**。最强模型每个节点都用最贵;架构功夫在于"哪个节点配得上旗舰,哪个节点小模型就够"。

> ⚠️ **L0 与 L1/L2 的边界**:CoT/ToT/ReAct/Reflexion/LATS 这些是 **agent 级编排,属 L2**,不是 L0;L0 只管"用哪个模型、怎么调它"。而且 L1 不"信任"L0——它**假设 L0 概率不可靠**,用契约/校验把不确定性吸收掉。

---

## L1 · 底层契约:结构化输出 / 工具

**定位.** 这一层解决一件事:让概率性的 LLM 输出,可靠到能被确定性代码消费。它是「模型」和「工程」之间的契约,枯燥但承重。

### 关键组件

**结构化输出**——按可靠性从低到高:

1. **Prompt 约束 JSON**:最不可靠,模型会漂、会带 markdown 围栏、会少字段。
2. **Function / Tool calling**:模型被训练过吐结构化 args,可靠性跃升。
3. **约束解码(constrained decoding)**:token 级强制,采样层 mask 掉非法 token。**注意分两档**:OpenAI Structured Outputs(strict + json_schema)/ GBNF / Outlines / XGrammar 把 schema 编译成语法、**保证符合你的 schema**;而 **JSON mode(response_format=json_object)只保证输出是合法 JSON、不保证符合 schema**,是更弱的一档。
4. **Schema 校验 + 重试**:Pydantic + instructor/trustcall,校验失败把错误回喂重试。

> **关键区分(两道坎)**:① **合法 JSON ≠ 符合你的 schema**(JSON mode 只跨第一道,schema 级约束解码才跨第二道);② **语法合法 ≠ 语义正确**(值本身合理)——后者只能靠校验逻辑 + 业务规则,约束解码管不了。
> trustcall 的 **JSON-patch** 增量更新,正是为了改已有结构时不让模型重吐整对象丢字段。

**工具 / Function calling**:

- 契约 = 工具 schema(name / description / params)→ 模型发起调用 → executor 执行 → 结果回喂。
- **工具 description 就是 prompt engineering**:模型只知道 schema 告诉它的东西,描述写不清就选错、传错参。
- **粒度**:工具太多→选择错误率上升(~10–20 个是经验上限);太粗→不灵活。超量时上分层 / RAG-over-tools(先检索相关工具子集)。
- **错误当数据,不当异常**:工具失败要返回模型能推理的错误信息,而不是抛异常中断。
- **副作用管理**:幂等性、并行调用——直接关联 HITL 恢复时「节点从头重跑」的坑。

**Action 范式谱**(动作怎么表示,本身是一阶架构轴,别默认只有 JSON 工具调用):

1. **JSON / Function calling**:离散、可校验、可审计——默认选择。
2. **CodeAct / code-as-action**:模型直接写并执行代码作为**一个动作**。工具多、需要组合或控制流(循环/条件/中间变量)时显著省 round-trip(smolagents 默认、Manus 核心);代价是**必须沙箱执行**。这也是上面"工具太多"问题除 RAG-over-tools 外的另一经典解。
3. **Computer-use / 浏览器自动化**:截图 + 点击/键入操作 GUI,兜底**无 API 的系统**并提供多模态观察(Anthropic computer use、OpenAI Operator)。blast radius 大、对 UI 变更脆弱、慢,需要强护栏。

> 选型轴:**目标系统有没有 API / 动作要不要组合控制流 / 要不要多模态观察**。

### 核心张力

**灵活性 vs 可靠性**。约束越强(grammar 强制)越可靠,但越死板;越自由(纯 prompt)越灵活,但越容易碎。生产默认偏可靠端,在确定性边界处用约束解码兜底。

### 生产教训

这层的失败是**静默**的——demo 里十次有九次对,上线后那 10% 的畸形输出让上层莫名其妙地崩。值得为它单独写校验 + 重试 + 降级,而不是假设「模型一般都对」。

---

## L2 · 核心机制:规划 / 状态机

**定位.** Agent 实际怎么**决策**和**移动**。(协议曾作为第三子部分放在这里,现已上移为正交横切带——它是接入标准、不决定决策与控制流,见文末。)

### 规划 / 推理范式

| 范式 | 一句话 | 何时用(触发条件) |
|------|-------|------|
| **CoT** | 线性推理,想一步说一步 | 单步线性推理,默认起点 |
| **ReAct** | thought→action→observation 交错循环 | 需要边做边看的工具型主循环 |
| **ToT** | 分支搜索 + 回溯 | 解空间大、易走死胡同,且容忍多倍调用成本 |
| **Reflexion** | 失败后自我批判,反思存进 episodic | 有可验证的失败信号、且允许重试 |
| **LATS** | MCTS 树搜索 + LM 价值函数 + ReAct 式 acting/环境反馈 + 自反思(比 ToT 多了外部观测与价值回传) | 高价值、可多次尝试、值得烧算力的任务 |

**Plan-and-execute vs ReAct** 是这层最核心的一个选择轴:

- **先规划再执行**:LLM 调用少、可控,但不适应中途变化。
- **逐步决策(ReAct)**:适应性强,但调用多、成本高、可能跑偏。
- **混合**:先出计划,偏离时 re-plan——生产里最常用。

> 张力本质:**深思熟虑的深度 vs 延迟/成本**。

### 状态机 / 控制流

为什么生产用图/状态机,而不是自由的 agent while 循环:**确定性、可调试、可恢复**。

- LangGraph 模型:node(工作单元)/ edge(控制流)/ conditional edge(路由)/ state(共享通道)。
- 关键演进:从「自主 Agent 循环到 done 为止」(无界 ReAct 循环)→「显式图 + 有界路径」。这是血泪换来的生产共识——无界循环会绕圈、会爆成本、没法 debug。
- **持久执行**:每个 super-step 落 checkpoint,崩溃/暂停后可恢复(直接接 HITL 那套 `interrupt` + `Command(resume)`)。

> 协议(MCP / A2A / ACP / AG-UI)曾被归在这里,但它**是跨层的接入标准、不决定决策与控制流**——已移到文末「正交横切带 A · 协议」。

### 生产教训

新手最容易把「自主性」当卖点,放任 Agent 无界循环;成熟做法是**用状态机把自主性关进有界的笼子**,在该自由的节点自由,在该确定的地方确定。

## L3 · 上下文层:RAG / 记忆

**定位.** 在对的时机,把对的信息塞进 context 窗口。L3 是**知识与记忆基础设施**(RAG + 记忆持久化 + 上下文组装),也是 **context 工程的主要落点**:system prompt、工具结果、RAG、记忆都在抢同一个 token 预算。(注意 context 工程本身是横切学科,装配主要发生在 L3 但不"等于"L3——见文末层间关系。)

### 上游闸门:要不要 RAG?(2026 第一分叉,也最影响成本)

旗舰普遍 1M+ context 且越来越便宜,"该不该 RAG"已经是 L3 最核心的架构分叉——L4 有"加 Agent 不是默认解",L3 同样要有"**RAG 不是默认**":

- 语料小而稳、要低延迟 → **长上下文直接塞 + prompt caching**,别上检索基建。
- 语料大 / 动态 / 要溯源 / 要控 token 成本 → **检索**。
- 生产多为 **hybrid**:RAG 先收窄到几十万高信号 token,再喂 1M 级模型 + prefix cache。

> ⚠️ **长上下文不能裸用**:有 **lost-in-the-middle**(中部 U 型衰减)和 **context rot**(干扰项越多越退化、非线性掉崖)。所以 RAG/压缩不是"长上下文时代的过渡品",而是对抗退化 + 控成本 + 保溯源的手段。"RAG 效果差是检索问题"也要补一句限定:**塞太多时模型自身也会退化,检索再完美也掉点**。

### RAG —— 超越 naive RAG

naive(embed→top-k→塞)只够 demo。生产栈:

- **Chunking**:固定 / 语义 / 分层 / late chunking。
- **混合检索**:向量 + BM25 全文,RRF 融合(纯向量漏专有名词、代码标识符、精确数值)。
- **Reranking**:一阶召回后用 cross-encoder 精排。**何时用**:召回够但精度/排序不够、且能吃额外延迟(本地 cross-encoder 数十 ms、API 可达数百 ms)。
- **Query 变换**:HyDE、multi-query、分解。
- **Contextual Retrieval**(Anthropic):embed 前给每个 chunk 拼上下文,大幅降召回失败率。**何时用**:chunk 短、或跨 chunk 指代多(代词/省略)导致单 chunk 语义不自足时。
- **Agentic RAG**:Agent 自己决定何时/检索什么、迭代检索——对比静态一次性 RAG。
- **GraphRAG**:在知识图上检索,解多跳。

### 记忆

- **短期(working)**:context 窗口管理;溢出时压缩/摘要。
- **长期**:semantic / episodic / procedural,持久化进 Store。
- **RAG vs 记忆的区别**:RAG 是检索**外部语料**(相对静态);记忆是检索 Agent **自己积累的经验**。但两者都是「context 组装」,共用检索基础设施。
- **窗口管理本身**:留什么、摘要什么、淘汰什么(Letta/MemGPT 的三层 OS 类比:**core** 窗口内、类 RAM / **recall** 窗口外、可检索的对话历史 / **archival** 长期知识、类磁盘;模型经工具调用在层间 page in/out)。

### 核心张力

**召回率 vs 信噪比**。塞得多怕漏,塞得少怕缺;塞太多反而稀释注意力、抬成本。检索质量 = 召回到的 + 没召回错的,两个都要管。

### 生产教训

大多数「RAG 效果差」不是模型问题,是**检索问题**:chunking 烂、缺 reranking、纯向量漏精确命中。优化顺序应该是 检索质量 → 上下文组装 → 才轮到换模型。

## L4 · 多 Agent 协作

**定位.** 单 Agent 不够时才上。**先警告**:多 Agent 经常被滥用,「单 Agent + 好工具」通常该是第一选择。

### 为什么 / 代价

- **为什么**:context 隔离(各 Agent 聚焦)、专业化、并行、关注点分离。
- **代价**:协调开销、错误传播、调试更难、延迟、成本翻倍。

> Anthropic 的多 Agent research 经验:orchestrator-worker 并行子 Agent 做广度优先研究有效,但 **token 成本约为单 Agent 聊天的 15 倍**——只在任务价值撑得起时才用。

### 拓扑

| 拓扑 | 形态 | 特点 |
|------|------|------|
| **Supervisor / orchestrator-worker** | 中心 Agent 路由给专家 | 最常用、可控;不知道选哪个就先用它 |
| **Hierarchical** | supervisor 的 supervisor | 子任务还能再往下分解时才上 |
| **Network / P2P** | Agent 自由互通 | 对等节点需自由互发、无中心协调时;灵活但难控 |
| **Sequential / pipeline** | 交接链 | 阶段固定、无需回头时最简单 |
| **Swarm** | 动态交接,Agent 自己决定下一棒 | 下一棒由内容动态决定;需清晰交接协议 |

### 通信模式

- **Handoff**:转移控制权 + context。
- **共享 state/scratchpad vs 消息传递**。
- **context 传递问题**(核心难点):多少状态跨边界?太多=噪声,太少=接手的 Agent 缺乏 grounding。

### 关键设计问题

工作怎么分解(orchestrator 决定 vs 预定义)、结果怎么聚合(map-reduce、`Send` 扇出扇入)、**谁拥有跟人的对话**。

### 生产教训

「加 Agent」不是默认解。先问:这是 context 隔离/并行的真实需求,还是用拓扑复杂度掩盖了 prompt/工具没做好?多数场景,把 L1–L3 做扎实比加 Agent 更值。

## L5 · 部署 / 安全运行时

**定位.** 栈顶**运行时层**:把跑通的 agent 真正、安全地放到生产里跑。(评测 / 可观测已上移为「横切带 B」——它们贯穿所有层、不只属于这里。)

### 部署

- **运行形态(第一道分流)**:同步请求-响应 / **流式(SSE,token 边出边回)** / **异步后台长时 agent**(分钟到小时,任务队列 + durable execution 驱动,如 coding agent、后台研究)。这是 demo → 产品最主要的形态转变。
- **延迟预算 / SLO 前置**:先给整个 agent 定延迟预算,再据此决定步数上限、是否流式、是否模型级联/降级——把延迟从事后观测指标变成事前设计约束。
- **有状态 vs 无状态**:checkpointer 让 Agent 变有状态,需要持久存储后端(LangGraph 叫 checkpointer,生产用 PostgresSaver,其他框架有等价物)。
- **持久执行 / 可恢复**;长时任务把状态当持久对象(复用 L2 的 checkpointer)。
- 后台 agent 额外的一等公民:**进度回传、用户发起的中断/取消通道**(区别于 HITL 那种等输入的暂停)、**完成通知(webhook/push)**。
- **并发、限流、多 provider 降级**;**prompt caching** 控成本。

### 安全 / 护栏

- **Prompt 注入**:观察到的内容(网页、文档、工具结果)是数据不是指令。
- **工具权限边界**:最小权限,危险操作走审批(HITL 闸门)。
- **输入/输出过滤**:PII、注入检测;沙箱隔离代码执行(直接关联 L1 的 CodeAct/computer-use)。

### 核心张力

**自主性 vs 可控性**。给 Agent 越多权限越能干,但 blast radius 越大。护栏、评测、HITL 都是在买「可控」。

## 正交横切带 A · 协议(MCP / A2A / AG-UI / ACP)

标准化接口,把 N×M 的定制集成降成 N+M。**它不属于任何单层,而是贯穿接入**——故单列为横切带。三条轴,各锚在不同层:

- **Agent ↔ 工具/数据(锚 L1)**:**MCP**(Anthropic 发起;2025 被 OpenAI/Google 原生采纳,2025-12 捐入 Linux Foundation/AAIF,跨厂商**事实标准**)。
- **Agent ↔ Agent(锚 L4)**:**A2A**(Google 发起,2025-06 起由 Linux Foundation 治理),负责 agent 间的发现与通信。
- **Agent ↔ UI / 客户端(锚 L5)**——两个同轴兄弟,都是 agent ↔ 某个"客户端表面":
  - **AG-UI**(CopilotKit 发起):agent ↔ 通用 web 前端,把状态流式推给 UI,承载 HITL/streaming。
  - **Agent Client Protocol(ACP,Zed 发起)**:**编辑器/IDE ↔ 编程 agent** 的标准接口,类比"LSP 之于编辑器",只是面向编辑器里的编程 agent。

> ⚠️ **"ACP" 是两个毫无关系的协议的同名缩写,务必分清**:
> - **Agent Communication Protocol**(IBM Research / BeeAI,2025-05 发布,晚 A2A 约一个月):管 **agent ↔ agent**——**已于 2025-08 并入 A2A**、停止独立演进(BeeAI 现通过 A2A 适配器对接)。即"被 A2A 吸收"的那个 ACP,属上面的 Agent↔Agent 轴。
> - **Agent Client Protocol**(Zed):管 **编辑器/IDE ↔ 编程 agent**——独立且活跃,属上面的 Agent↔UI/客户端 轴。
> 一个已被 A2A 吸收、一个还活着,且分属不同轴——**看到 "ACP" 先问是哪一个**。
> 架构师视角:协议**几乎总是加分项**——选定框架后用它暴露能力,换框架时不用重写。这与你「选型矩阵」里"协议正交、不单列选型"的定位一致。

## 正交横切带 B · 度量与观测(评测 + 可观测)

**为什么是横切带、不是 L5 的一部分**:它从 L0 起就该包裹整栈——**位置画在最上(故障观测面),但搭建顺序上应最先存在**(没有它,所有层的改动都是盲改)。这两条轴不冲突。

### 评测(Agent 最难的部分)

多步轨迹没有单一 ground truth。

- **分层**:组件级(检索质量、工具选择准确率)vs 端到端(任务成功率)。
- **轨迹评测**:路径走得好不好,不只是答案对不对。
- **方法**:LLM-as-judge(注意偏置,需校准)、人工、程序化检查;reference-based vs reference-free。
- **工具**:agent-first / 回归门控——**Braintrust**(实验 + CI 回归卡作 deploy gate)、Galileo;通用/RAG eval 与判官蒸馏小模型——RAGAS、DeepEval、Galileo Luna-2;观测 + eval——Phoenix、LangSmith、Langfuse。(TruLens 2026 已边缘化,可降权。)
- **Eval-driven development**:先建评测集,再对着它迭代;在线 vs 离线;回归套件防止改一处崩另一处。
- **配置即代码(可复现性)**:把 prompt、工具 schema、模型版本、推理参数(temperature/seed)版本化,每个 eval 结果绑定一份可复现配置快照——才能把指标变化归因到具体改动(LangSmith/Langfuse 自带 prompt 版本管理)。
- **数据飞轮(评测集是活的)**:把生产 trace 的失败/边缘案例持续回流成评测样本 + 标注,驱动 prompt/检索调优乃至**小模型蒸馏微调**(接回 L0),再用回归套件守住不退化。采集与回流管线**第一天就埋**,而非上线后补——这是 agent 产品的复利与护城河。

### 可观测

- **全链路 tracing**:每个 LLM 调用、工具调用、检索都打点(类比分布式追踪)。
- 工具:LangSmith、Langfuse、Phoenix、OpenLLMetry。
- **成本/延迟/token** 追踪;注意 **HITL 的 interrupt 会打断 naive tracing**(一次 interrupt-resume 容易被拆成两条断裂的 trace,工具被误标 ERROR)——治法见下「HITL 横切线」。

> 生产教训:团队普遍**低估评测、高估模型**。没有评测集就没有「改好了」的客观判据,所有优化都是凭感觉。**评测应该是第一个搭的,不是最后补的**——这正是把它画成横切带、而非顶层 L5 的原因。

---

## 层间关系(横向再看一遍)

1. **故障向上级联(L1→L5)**:L1 不稳→L2 路由错→L3 喂错 context→L4 错误跨 Agent 传播→L5 才发现却分不清哪层的锅。所以**自底向上稳固**。注意 **L0 是概率底座、不在级联链里**:L1 不是"信任 L0",而是"驯服 L0 的不可靠"。
2. **可恢复性是一条贯穿线**:L2 的 checkpointer → L3 的状态持久化 → L5 的部署/HITL,是同一个能力在不同层的体现。
3. **context 工程是横切学科,主要落点在 L3**:它在 system prompt / 工具 schema(L1)、RAG/记忆(L3)、跨 Agent 状态(L4)间分配同一 token 预算——装配主要发生在 L3,但不"等于"L3。
4. **度量·观测(横切带 B)是元层**:让 L0–L5 每次改动可度量的前提,搭建上应最先存在。

**还有几条贯穿全栈的横切关注点(不属于某一层,但每层都在为它买单):**

5. **成本/单位经济学**:以"每任务/每工单的美元成本"为统一指标——L0 选更便宜模型/级联、L2 用 plan-and-execute 压调用数、L3 控 token 预算 + prompt/语义/结果三级缓存、L4 量化"多 Agent 15x 是否值回票价"、L5 成本/延迟/token 追踪。**先量化单位经济学,再做任一层优化**。
6. **HITL 是横切设计模式,不只是 interrupt API**:按风险/置信度决定介入点——危险动作审批、低置信度升级、人审编辑中间态;UX 经横切带 A 的 AG-UI 推前端,恢复经 L2 的 `interrupt + Command`/checkpoint;介入结果须可审计并回流——**人既是安全闸,也是数据飞轮的标注来源**。⚠️ **HITL × 可观测的坑**:`interrupt()` 靠抛 `GraphInterrupt` + 两次 invoke 实现暂停,naive tracing 会把一次人审切成**两条断裂 trace**、把暂停**误标 ERROR**——治法:① 两次 invoke 带同一 `thread_id`/session,用 LangSmith/Langfuse 的 thread 分组缝成一条逻辑线;② 把 `GraphInterrupt` 特判为 `paused` 而非 ERROR;③ 用框架原生 tracing 集成,别手搓 OTel span。
7. **数据飞轮**:trace → 评测集 → 改进(prompt/检索/蒸馏)→ 回归(详见横切带 B),把"可持续改进"从口号变成管线。
8. **确定性优先**:能用规则/查表/确定性代码可靠解决的步骤就**别调 LLM**,把概率模型留给真正需要泛化判断的环节。(与 L1"约束解码兜底"是两件事:前者决定**某步要不要用 LLM**,后者管**已经用了 LLM 时怎么约束输出**。)

> 一句话总览:**模型基座定上限,底层契约保证可信,核心机制保证可控,上下文层保证知情,多 Agent 在必要时扩展,部署/安全让它落地,协议让能力可复用,度量·观测让全栈可度量。**

## 五层 ↔ 选型矩阵六层 crosswalk

两套分区是**两种切法,不是谁对谁错**:**本文(五层 + L0 + 横切带)= 能力/故障级联心智模型(怎么想)**;**`roadmap/agent-selection` 选型矩阵六层 = `/plan` 选型决策包(选什么)**。映射并非一一对应:

| 本文(心智轴) | 选型矩阵(决策轴) | 关系说明 |
|---|---|---|
| L0 模型/推理基座 | 🧠 模型层 | **一致**(矩阵也当底座);本文额外强调它横切每个 LLM 节点 |
| L1 底层契约(结构化输出/工具/action) | 🔧 工具层(只管 100+ 路由) | L1 ⊃ 工具层:L1 含调用契约 + action 范式,矩阵工具层只覆盖"路由选对" |
| L2 核心机制(规划/状态机) | 🏗️ 编排框架层 | 对应:CoT/ToT/Reflexion/LATS、图/状态机都归编排框架 |
| L3 上下文(RAG/记忆) | 📚 检索栈层 + 🧩 记忆层 | 本文按"共用检索基础设施"并归,矩阵按"独立选型"拆开——**不矛盾** |
| L5 部署/安全运行时 | (矩阵未单列,属落地) | — |
| 横切带 A · 协议 | (矩阵:协议正交、不单列) | **一致**:两边都把协议当正交加分项 |
| 横切带 B · 度量·观测 | 🔍 可观测·Eval 层(横切) | **一致**:两边都画成贯穿所有层的横切 |


# 如统计大模型的token使用量


先确认下 Anthropic API 的 token 统计细节,免得给你过时的字段名:统计 token 的方法取决于你要的**粒度**——是单次调用、整个 agent run、还是跨天的组织账单。从细到粗有这么几层,各有各的用途:

| 层 | 手段 | 用途 | 是否计费真值 |
|----|------|------|------------|
| 单次调用 | response 的 `usage` 对象 | 每次请求实际消耗 | ✅ 真值(按这个计费) |
| 发送前预估 | `count_tokens` 端点 | 控制 context 窗口、预算 | ❌ 估算 |
| Agent run 聚合 | 框架 callback / `usage_metadata` | 多步任务累计 | 基于真值聚合 |
| 可观测平台 | LangSmith / Langfuse / Phoenix | trace 级分解 + 看板 | 基于真值聚合 |
| 组织账单 | Usage & Cost API | 财务对账、团队分摊 | ✅ 权威 $ 来源 |
| Claude Code 本地 | ccusage | Claude Code 会话用量 | 读本地日志 |

## 1. 单次调用:`usage` 对象(真值,你被计费的就是它)

每个 response 都带 usage,这是一切统计的源头。关键是它有**四个字段**,不是两个:

```python
resp = client.messages.create(model="claude-opus-4-8", max_tokens=1024, messages=[...])
resp.usage
# input_tokens, output_tokens,
# cache_creation_input_tokens, cache_read_input_tokens
```

把 usage 对象当成所有优化的计分板——后面所有聚合都是把它累加起来。

## 2. 发送前预估:`count_tokens`

要在发送前判断会不会超窗口、估成本,用 `/v1/messages/count_tokens`,它接受和 create 一样的输入(messages / system / tools / images / PDF),不计费:

```python
count = client.messages.count_tokens(
    model="claude-opus-4-8",
    messages=[{"role": "user", "content": "..."}],
)
count.input_tokens
```

但**它只是估算**——实际创建消息时用的 input token 数可能有小幅差异,且可能包含 Anthropic 为系统优化自动加的 token(这部分不计费)。所以:预估用 count_tokens,对账用 response 的 usage。

## 3. Agent run 聚合(你 LangGraph 场景最相关的一层)

agent 一次任务里 LLM 被调多次,你要的是**整个 run 的累计**。LangChain 的 message 上有 `usage_metadata`,而跨多步聚合用 callback:

```python
from langchain_core.callbacks import get_usage_metadata_callback

with get_usage_metadata_callback() as cb:
    graph.invoke({"messages": [...]}, config)
    print(cb.usage_metadata)   # 按 model 聚合好的整个 run 用量
```

这是把 L5 可观测落到 token 维度的最小实现——不接平台也能先把每个 run 的成本打出来。

## 4–5. 平台 / 组织级

- **可观测平台**(LangSmith / Langfuse / Phoenix):自动随 trace 记录每一步 token,给你 per-node 分解和看板。接了 tracing 就免费拿到,不用自己埋。
- **Usage & Cost API**:用 `/v1/organizations/usage_report/messages` 端点跨组织追踪 token,可按 model、workspace、service tier 分解,时间桶 1m/1h/1d,区分未缓存输入、缓存输入、缓存创建、输出四类 token;`cost_report` 给出 USD 成本。需要 Admin API key(和普通 key 不同)。这是财务对账的权威来源——response 累加可能和账单有微小漂移,以这个为准。

## 三个最容易踩的坑

**坑 1:只统计总 token,不拆 cache。** cache_read 和正常 input、cache_creation 的**单价完全不同**——缓存把全价的 input_tokens 转成廉价的 cache_read_input_tokens。如果你只看 `input+output` 总数,会完全看不出缓存有没有生效、真实成本结构是什么。四个字段要分开记。

**坑 2:用 tiktoken 估 Claude 的 token。** tiktoken 这类工具会少算 Claude 的 token,基于它做的预算和限额检查全是错的——要用目标模型的 count_tokens。

**坑 3:换模型时沿用旧的 token 基线。** Claude Opus 4.7 引入的新 tokenizer,同样文本产生的 token 比 4.7 之前的模型多约 30%。迁移模型时要对新模型重新基线,绝不能用一个固定倍率去换算。



# 前后端 Stream 流的事件模型

> 核心认知:**「前后端 stream」是三段独立的流串起来的**,每段有自己的事件词汇表,工程上的活儿就是在它们之间做翻译。
> 大多数人把三段混成一团,debug 时就分不清丢的 token 是哪一段断的。

---

## 0. 先分清三方:provider / framework / app

「provider」= **大模型的供应商 / API 提供方**,真正跑模型、吐 token 的那一方。用这个词而不直接说「模型」,是因为这条链路上有三方容易混:

| 角色 | 是谁 | 干什么 |
|------|------|--------|
| **provider(供应商)** | Anthropic / OpenAI / Google,或本地 Ollama、vLLM | 提供 API 和**原始 SSE 流** |
| **framework(框架)** | LangGraph / LangChain | 在 provider 之上做**编排** |
| **app(你的应用)** | 你的后端 + 前端 | 调框架、对接 UI |

你代码里 `client.messages.create(...)` 打过去的那个 API,背后就是 provider。

---

## 1. 三段流总览

```
LLM ──provider SSE──> 后端 ──框架 stream──> 适配层 ──标准协议──> 前端
  chat.completion.chunk   values/updates       AG-UI events     React/Vue
  choices[].delta          messages             TEXT_MESSAGE_*   增量渲染
  usage(末chunk)/[DONE]    custom / events      TOOL_CALL_*
  ...                                          STATE_DELTA
                                               INTERRUPT
(每次 LLM 调用一条流)    (整个 run 一条流)      (标准事件 schema)
```

- **第一段**:provider 的「方言」(OpenAI 专属格式)
- **第二段**:框架把多方言 + 编排信息翻成的「普通话」(LangGraph 抽象)
- **第三段**:再翻成前端能直接渲染的「标准协议」(AG-UI)

---

## 2. 为什么框架不直接透传 provider 的原始 SSE

这是第一段和第二段之间为什么要做一次翻译的原因:

**① 各家 provider 格式不一样。**
Anthropic 是 `content_block_delta`,OpenAI 是 `choices[].delta`,Gemini 又是另一套。直接透传的话,换个模型前端就得重写。框架把它们**归一化**成统一事件,上层不用关心底下是哪家。

**② 框架要加自己的语义。**
provider 只知道「这次 LLM 调用吐了什么 token」;但 LangGraph 是个图,它还要告诉你「执行到哪个 node、state 怎么变、工具结果是什么」——这些 provider 的事件里**根本没有**,得框架自己合成。

**③ 一次 agent run 里有多次 provider 调用。**
你的 graph 跑一遍可能调 5 次 LLM、3 次工具。provider 的每条 SSE 流只对应**其中一次** LLM 调用;框架要把这许多次调用 + 工具执行,编织成「整个任务」这一条对外的流。

---

## 3. 第一段:LLM → 后端(provider 原始 SSE)

以 OpenAI 为例。注意 OpenAI 有**两套**流式 API,事件结构差别很大。

### Chat Completions(经典,用得最广)

流式响应是一串**结构统一**的 chunk,每个都是 `chat.completion.chunk`;内容类型靠 `choices[].delta` 里哪个字段有值来判断,而不是靠事件名:

| 字段 | 含义 |
|------|------|
| `choices[].delta.role` | 仅第一个 chunk,标记 `assistant` |
| `choices[].delta.content` | 正文 token |
| `choices[].delta.tool_calls[]` | **工具调用增量**(见下) |
| `choices[].finish_reason` | 结束原因(`stop` / `tool_calls` …),在最后一个内容 chunk 上 |
| `usage` | **仅当** `stream_options={"include_usage": true}`,且全部集中在最后一个 chunk |

三个关键点:

- **工具参数逐片流式**:`delta.tool_calls[].function.arguments` 是 JSON 片段,要自己累加拼成完整 JSON。第一个工具 chunk 会先声明用哪个工具,之后才流参数。
- **usage 集中在末尾**:OpenAI 把 input + output token 全放最后一个 chunk(且那个 chunk 的 `choices` 是空数组 `[]`)。**流被中断就拿不到 usage**。
- **终止靠 `data: [DONE]`**,而不是某个事件类型。

> 结构特点:OpenAI Chat Completions 是**统一 chunk**,内容类型靠 `delta` 字段 + `finish_reason` 推断出来,而不是靠命名事件标边界。

### Responses API(较新,事件驱动)

OpenAI 的新一代端点,更像状态机,流式格式换成了**带 `type` 的命名事件**:

- 文本:`response.created` → `response.output_text.delta`(重复)→ `response.completed`
- 工具:`response.function_call_arguments.delta` / `.done`
- `response.completed` 直接携带最终完整 response(含 usage),不用自己从 delta 重组
- `error` 事件

代价是**更啰嗦**——正文前后有一堆 metadata 事件,客户端得按 `event.type` 做 switch 分发。经验法则:简单 chat 用 Chat Completions 就够;要做 agent、要原生工具(如 web search),Responses API 更合适。

> 工具 args 流式到达(两套 API 都是),决定了上层能不能「边收边预填表单」。

---

## 4. 第二段:后端框架内部(LangGraph stream modes)

框架不透传原始 SSE,而是按自己的抽象重新分发。LangGraph 的 `stream_mode`:

| 模式 | 给什么 | 用途 |
|------|--------|------|
| `values` | 每步后的**完整 state** | 要全量快照时 |
| `updates` | 每个节点**只给状态变更** | 增量驱动 UI |
| `messages` | LLM token + metadata,逐 token | 打字机效果 |
| `custom` | 节点里 `get_stream_writer()` 主动 emit 的数据 | 自定义进度 |
| `events`(`astream_events`) | 最细粒度(`on_chat_model_stream` / `on_tool_start`…) | 需要精细控制 |

可组合:`stream_mode=["updates", "messages"]`——一边推 token 渲染,一边推 state 变更驱动 UI。这一段是 LangGraph 场景真正要选型的地方。

---

## 5. 第三段:后端 → 前端(AG-UI 标准协议)

狭义的「前后端事件」就是这段。AG-UI 把它标准化成约 16 个事件类型,分五类:

**文本——三段式 triad**
`TEXT_MESSAGE_START` → `TEXT_MESSAGE_CONTENT`(重复)→ `TEXT_MESSAGE_END`,合起来就是打字机效果。

**工具调用——流式 args**
`TOOL_CALL_START`(带 toolCallId)→ `TOOL_CALL_ARGS`(逐片流式吐 JSON 参数)→ `TOOL_CALL_END`(参数传完、开始执行)→ `TOOL_CALL_RESULT`(结构化结果)。因为 args 流式,UI 能在 agent 还没「说完」时就预填表单。

**状态——snapshot + delta(关键设计)**
`STATE_SNAPSHOT` 给完整状态用于初始同步;`STATE_DELTA` 用 **JSON Patch(RFC 6902)** 发增量 diff。不是每次重发整个文档,而是发一个 tiny diff(如「在 index 5 加 'hello'」)——这就是协作类 agent(实时改文档/表格)不卡的原因。

**生命周期**
`RUN_STARTED` → … → `RUN_FINISHED` / `RUN_ERROR`;`STEP_STARTED` / `STEP_FINISHED` 标记内部节点(对应 LangGraph 的 node)。

**特殊**
`RAW`(透传外部事件)、`CUSTOM`(应用自定义),以及 HITL 相关的 `INTERRUPT`。

**两类较新的**
`REASONING_*`(取代已废弃的 `THINKING_*`,流式推理过程);`ACTIVITY_*`(前端专用进度/搜索状态,**不回传给 LLM**,适合做「正在搜索…」这种纯 UI 提示)。

---

## 6. 传输层:SSE vs WebSocket

| | SSE | WebSocket |
|---|-----|-----------|
| 方向 | 单向 server→client | 双向 |
| 重连 | 自带 | 手动 |
| 数据 | 文本 | 文本 + 二进制 |
| 适合 | 大多数展示型 agent | 低延迟、双向 steering |

经验法则:纯展示型 agent 用 SSE 够了;真正交互式协作(频繁人类介入、双向 steering)上 WebSocket。

---

## 7. 工程要点

**① HITL 的 interrupt 是完整环路,不只是下行事件。**
后端 `interrupt()` 暂停 → 发 `INTERRUPT`(或一条 text 提问)→ 前端渲染审批卡 → 人批准 → 上行 approval 事件 → 后端 `Command(resume=...)` 继续。
**现实的坑**:AG-UI 其实没有专门的「暂停等批准」原语,很多实现里 HITL 退化成 agent 文本问一句、用户回一句,和普通 chatbot 同 pattern。事件只是传输,状态机还得自己写。

**② 断流重连要接得回去。**
SSE 自带重连,但「从哪接」是你的问题——用 checkpointer:thread_id 定位快照,前端用 last-event-id 或重新拉一次 `STATE_SNAPSHOT` 对齐。AG-UI 有 threadId/runId,但跨消息维护会话历史是你的责任,每个请求默认无状态,除非传完整历史。

**③ 顺序与去重。**
三段逐层翻译时事件顺序必须稳。客户端 SDK 会去重(如 `TEXT_MESSAGE_START` 若 ID 撞上已有 tool call 父消息会被忽略),但自定义事件时要自己保证 toolCallId / messageId 一致,否则 UI 重复渲染或丢块。

**④ 安全边界在适配层。**
观察过的内容(工具返回、外部 RAW 事件)是数据不是指令;用 JSON Patch 同步 state 时防 prototype pollution,禁止改 `__proto__` 这类受保护属性。

---

## 落到你的栈

- 已在用 LangGraph → AG-UI 有官方集成,第二段(stream_mode)到第三段(AG-UI events)的翻译基本现成,主要写前端 reducer 和 `INTERRUPT` 审批 UI。
- 不想引 AG-UI、自己用 SSE 推 → 照这五类事件的形状定义自己的 schema。**至少别只推一个 `text` delta**,把 tool call、state、interrupt 也分出来,否则做不出「看得见 agent 在干什么」的效果。
