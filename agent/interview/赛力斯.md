## 如何监控和治理运行中的 Agent？

> 主场题——可观测栈、LiteLLM 网关、Guardrails、EDD 全是简历里的弹药。先用总纲句把"监控/治理"拆开，再分层展开，每层落到自己真用过的工具。

**总纲句（先说这个）：**

"我把这个问题拆成两半：**监控解决'看得见'**——Agent 在生产里每一步做了什么、质量如何、花了多少钱；**治理解决'管得住'**——出问题之前有护栏，出问题之后能定位、能回归。我在两段经历里都完整建过这套体系。"

**一、监控：三层指标 + 一条数据链路**

数据链路（地基）：OpenTelemetry 埋点，一次 Agent 任务组织成 session → trace → span 层级，span 区分 LLM 调用 / 工具调用 / 检索三类，导出到 Phoenix（自托管）或 LangSmith。任何坏 case 都能下钻到具体哪一步、哪个 prompt、哪个工具参数。

> 2026 水位更新：埋点语义跟 **OTel GenAI 语义约定（`gen_ai.*`）**走——2026.6 已拆成独立 conventions 仓库（v1.42.0），覆盖 agent 生命周期操作（`invoke_agent` / `execute_tool` / memory 操作），Claude Code、Copilot、Codex 已原生发 OTel GenAI trace；但注意它**至今仍是 Development（实验）状态、没有 1.0**，正确姿势是"跟着走 + 钉住约定版本容忍 churn"，OpenInference 作为 Phoenix 侧兼容层并存。这句说出来是"持续跟进"的信号。

三层指标（从下往上）：

1. **系统层**：P99 延迟、错误率、token 消耗与成本归因（按 trace 归因到 Agent / Skill / 用户）。实现：OTel Collector → Prometheus / Tempo / Loki，Grafana 统一面板，Blackbox 可用性探测——LGTM 栈自己搭过
2. **质量层**（Agent 特有）：工具选择命中率、参数抽取正确率、轨迹收敛度（有没有绕路 / 死循环）。实现：线上流量**采样**跑 LLM-as-a-Judge 在线评估，结果写回 trace 标注——全量跑太贵，采样 + 规则预筛是取舍点
3. **业务层**：任务完成率、用户显式反馈（点踩）、人工抽检。这层决定前两层的阈值

关键闭环：线上 trace 不只是看板——坏 case 通过 SpanQuery 导出、标注后**回写进评测数据集**，生产事故变成回归用例。这是监控和治理的连接点。

**二、治理：四个控制面**

1. **入口治理（网关层）**：所有 LLM 调用收口到 LiteLLM 统一网关——API key 管理、按团队/应用限流、预算控制与成本核算、模型准入、fallback / 负载均衡。没有网关就谈不上治理
2. **运行时护栏**：输入侧防 prompt injection / 越权指令，输出侧格式校验、PII 过滤、事实性校验（Guardrails AI validator 机制）；上线前用 Giskard 红队评测（jailbreak / injection 套件）验证护栏有效性
3. **权限与行为边界**：工具权限最小化（Agent 只挂它需要的工具）、高危操作（写操作 / 交易类）强制 Human-in-the-Loop 审批中断、执行环境沙箱化
4. **变更治理（EDD）**：prompt / 模型 / 架构任何变更先在版本化评测数据集上跑实验对比，CI 设评测门禁（规则评估 + 模型评分双轨），不达标不合入。运行中 Agent 最大的风险是"改坏了没发现"

**三、现成框架选型口径（追问时上）**

| 用途 | 框架 | 一句话定位 |
|---|---|---|
| Tracing / 可观测 | Phoenix（开源自托管）、LangSmith（SaaS）、Langfuse（开源） | 数据敏感选 Phoenix 自托管；LangGraph 系且接受 SaaS 选 LangSmith |
| 埋点标准 | OTel GenAI 语义约定（`gen_ai.*`）+ OpenInference | 跟 OTel GenAI 约定走（仍实验态，钉版本容忍 churn）；OpenInference 作 Phoenix 兼容层 |
| 网关治理 | LiteLLM | 开源最成熟；企业也可选 Kong AI Gateway / Higress |
| 运行时护栏 | Guardrails AI、NeMo Guardrails | validator 生态 vs 对话流规则；结构化输出校验选前者 |
| 离线评测 | RAGAS / DeepEval / Phoenix evals | RAG 指标 / pytest 风格断言 / 与 trace 一体 |
| 红队测试 | Giskard | 上线前扫 injection / jailbreak |
| 基础设施监控 | Grafana LGTM 栈 | LLM 指标要和传统 SRE 指标放同一块屏 |

选型原则一句话："**埋点选标准（OTel），平台选可自托管的（Phoenix / LiteLLM / LGTM），护栏选可组合的（validator 生态）**——企业级场景数据不出域和不被锁定是硬约束。"

**展开顺序：** 总纲句 → tracing 地基 → 三层指标 → 四个控制面 → 追问再上框架对比表。全程强调"这套是真搭过的"，能给踩坑细节（如 macOS 系统代理截胡 localhost 导致 Phoenix client 503）反而最显真实。

## 除了 LangGraph，你接触过哪些主流的 Agent 架构或框架？

> 陷阱是当成报菜名题。面试官真正验证的是：你是不是"只会 LangGraph 的人"、有没有架构师级的框架观。答法：给分类框架 + 诚实标注深度 + 落到选型原则，不要罗列。

**开场句：**

"我接触框架的方式是按编排范式横评的，因为做选型时'它属于哪类'比'它叫什么'更重要。主流框架我分四类。"

**四类范式（把框架放进格子）：**

1. **图 / 状态机编排**——LangGraph（生产主力，两段经历都在用）。确定性路由 + 可恢复状态，适合可控性要求高的企业场景
2. **角色协作 / 对话式多 Agent**——CrewAI 实跑过，AutoGen 了解架构。按角色分工、Agent 间对话推进任务，原型快但执行路径不确定，生产可控性弱于图编排——实际对比后没选它做主栈的原因。**注意 2026 格局更新：AutoGen 已并入 Microsoft Agent Framework（2026.4 发布 1.0 GA，与 Semantic Kernel 合并为微软统一 agent SDK）**——面试说 AutoGen 还是独立框架会露怯
3. **产品级 Agent 运行时（harness 类）**——Claude Agent SDK / Claude Code，生产用它做了 8 个仓库的 GitLab / Jenkins MR 自动评审。架构哲学和 LangGraph 相反：**不做显式图，单循环 + 工具 + 子 Agent 委派**，可靠性押在模型能力和工具设计上。Letta 也归这类——agent 即持久化运行时、记忆原生，0.6→0.16 大版本迁移跑过
4. **轻量 / 类型安全派**——Pydantic AI（类型契约为中心）、裸 SDK + Agentic 设计模式（Reflection / Planning / Tool Use 自己组装）。能说出"什么时候不用框架"本身就是架构判断

补一句检索侧：LlamaIndex 的 agent 能力在红队测试项目实跑过（0.14 最新版），定位偏"数据框架带 agent"而非编排框架。

**收尾（拉回选型原则）：**

"强流程可控选 LangGraph，快速原型多角色协作选 CrewAI，长生命周期带记忆的 Agent 看 Letta，编码/运维类任务直接上 Claude Agent SDK，简单场景裸 SDK 不引框架。我把这套判断沉淀成了分层选型矩阵，每个框架的结论都是自己跑出来的。"

**注意点：**

- 诚实分层深度：生产用过（LangGraph、Claude Agent SDK）/ 实跑对比过（CrewAI、Letta、LlamaIndex）/ 了解架构（Microsoft Agent Framework、Google ADK、OpenAI Agents SDK）。主动区分深度不减分，被追问"了解"层答不上才减分
- 2026 格局三个大动作要能顺口说出：**Microsoft Agent Framework 1.0 GA**（AutoGen + Semantic Kernel 合并，微软栈首选）、**Google ADK**（已扩展 Java/Go，绑 A2A 生态）、**OpenAI Agents SDK**（轻量 handoff 链路）；LangGraph 版本口径：**1.0 GA 2025.10.22**（与 LangChain 1.0 同天，主基调 API 稳定/无破坏性变更），**当前已到 1.2**（2026.5，加节点级超时、节点级错误处理器、优雅停机 RunControl——都是生产可靠性特性，正好呼应"图编排适合企业场景"论点）。另外 LangChain 1.0 的 `create_agent` 就跑在 LangGraph 运行时上——两者是同一运行时的高低两层 API，不再是竞争关系
- 第三类是差异化：能讲清 harness 类（Claude Code 单循环哲学）和 memory-native 类（Letta）的候选人很少，且直接为第⑥题铺路，两题打通
- 别踩 LangChain：被问关系就答"LangChain 是组件库、LangGraph 是编排层，新项目编排直接用 LangGraph"，不展开吐槽

## Claude Code/Claude Agent SDK 背后的 Agent 架构是怎样组成的？

> 天然优势题——生产里真用 Claude Agent SDK 做过 8 仓库 MR 自动评审，且接着第⑤题"harness 类"的话头。按"一个循环 + 四个支撑系统"讲，落到架构哲学对比。

**开场定调：**

"它的架构哲学和 LangGraph 是两个极端：**LangGraph 把控制流写在图里，Claude Code 把控制流交给模型**。整个系统就是一个极简主循环加四个支撑系统，可靠性不靠预定义路由，靠模型能力 + 工具设计 + 反馈闭环。"

**核心：单一主循环（agent loop）**

没有显式状态机。一轮循环：模型收到 system prompt + 工具定义 + 上下文 → 决定调哪些工具 → harness 执行并把结果喂回 → 模型继续决策，直到不再调工具、输出最终回答。所有"编排"都是模型每一轮的即时决策——计划、重试、换路子都是涌现行为，不是图上的边。

**四个支撑系统：**

1. **工具层 + 权限层**：工具集少而正交（文件读写编辑、Bash、Grep/Glob 搜索、WebFetch/WebSearch、子 Agent 派发）。两个设计要点：**Bash 是万能兜底**——给了 shell 等于给了无限工具，框架不需要几百个预定义工具；**每次工具调用都过权限系统**（允许/询问/拒绝规则 + 沙箱），HITL 内建在工具调用粒度上
2. **子 Agent 机制（orchestrator-worker）**：主 Agent 通过 Task 工具派生子 Agent，核心目的是**上下文隔离**——搜索/调研这类高 token 探索工作让子 Agent 烧自己的上下文，只把结论带回主线程；可并行派多个。是层级委派，不是 CrewAI 那种同侪协商
3. **上下文管理**：CLAUDE.md 项目级持久记忆随会话注入；上下文接近上限**自动压缩**（历史摘要后继续，不硬截断）；关键取舍是**检索靠 agentic search 而不是预建 RAG**——模型自己用 grep/read 按需拉取（just-in-time），不做向量库预灌
4. **扩展机制（三条正交轴）**：**MCP** 接外部工具/数据源（协议层）；**Skills** 把领域工作流打包成按需加载的指令包（知识层，渐进披露——不用时只占一行描述）；**Hooks** 在工具调用前后插确定性拦截（策略层，如强制 lint、阻断危险命令）。治理不改核心循环，全挂在这三条轴上

**Claude Agent SDK 的关系（带亲身实践）：**

"SDK 就是把 Claude Code 的 harness——主循环、工具、权限、MCP、子 Agent、Hooks——抽成可编程库，去掉终端交互，嵌进自己的系统。我在生产里用它做 CI 的 MR 自动评审：CI 触发、SDK 起 agent、挂上 diff 读取和评论工具、权限收敛到只读 + 评论，跑完写回 GitLab。"——这段是和背题候选人的区别。

**收尾（架构师落点）：**

"选型分水岭：**流程刚性、每步要审计的业务场景，图编排（LangGraph）仍然是对的；任务开放、以工具探索为主的场景（编码、运维、研究），harness 式架构上限更高**——模型每一轮都在重新规划，鲁棒性来自模型而不是图的完备性。两种范式并存，按场景选。"

**追问防御：**

- "没有图怎么保证可靠性？" → 工具结果就是反馈信号（测试跑失败模型自己修）+ 权限/Hooks 硬约束 + 外层评测门禁兜底（EDD）
- "上下文压缩丢信息怎么办？" → 关键状态外置到文件系统（todo 文件、笔记、CLAUDE.md），文件系统就是长期记忆——为第⑦题铺路
- "为什么不让子 Agent 互相通信？" → 层级委派保证结果可归集、成本可控；同侪对话式协商难收敛，这是与 AutoGen 路线的本质分歧

## 如何解决 Memory 注入导致的 Context 膨胀问题？

> 主场题——五个记忆框架实跑过，xBubble 双层记忆和宜信摘要注入都是第一手实践。按"记忆生命周期"组织答案，比零散报技巧高一个层次。

**开场定调（先纠正问题的隐含假设）：**

"Context 膨胀的代价不只是 token 成本——更大的伤害是**无关记忆会降低准确率**，长上下文有 lost-in-the-middle 和 context rot 问题，注入 20 条记忆里 15 条无关，模型反而更容易答错。所以这不是'压缩'一个动作能解决的，我的做法是在记忆生命周期四个环节分别控制：写入、检索、注入、遗忘。"

**四个环节的手段：**

1. **写入侧：存蒸馏结果，不存原文。** 对话原文先做事实抽取 + 消解（新旧记忆 ADD / UPDATE / DELETE 合并，冲突更新、重复去掉）——Mem0 核心机制，实跑时专门收集过它消解失败的样本。源头压缩做好，膨胀先砍一半
2. **检索侧：按需取回，不全量注入。** 记忆主体放外部存储，每轮只做相关性检索：向量 top-k + reranking + 相关性阈值（低于阈值宁可不注入）。Zep/Graphiti 更进一步——时序知识图谱只取与当前查询相关的**子图**，不拉整个用户历史
3. **注入侧：分层 + 预算。**
   - 分层注入：少量高价值信息常驻（用户画像、硬性偏好等 core memory，几百 token 封顶），其余走按需检索（recall memory）——Letta/MemGPT 分页架构，main context 放不下的放 external context，agent 自己用工具"翻页"
   - 上下文预算：memory 区固定 token 配额（如上下文 10%），超了按相关性分数裁剪。宜信"上下文摘要主动提取注入"即此思路——提取结构化摘要注入，不带原始历史轮次
   - 索引外置（更彻底）：context 里只放一行式索引，命中再读全文——渐进披露，Claude Code 文件式记忆即此模式
4. **遗忘侧：记忆要有生命周期。** 时间衰减、访问频率降权、低价值记忆归档/删除。没有遗忘机制的记忆系统膨胀只是时间问题

**2026 新维度：平台原生方案 + 缓存互动（加分段）**

- API 层已有原生解法：Anthropic 的 **context editing**（服务端自动清理旧 tool result / thinking 块，且在 prompt cache 查找之后执行——**不打破缓存前缀**）+ **memory tool**（文件式记忆，模型在内容被清理前主动把关键信息落盘）。官方数据：100 轮任务 token ↓84%、性能反升 39%。趋势是"上下文管理正在从应用层下沉到平台层"
- 高分点——**记忆注入与 KV cache 的互动**：膨胀不只吃 token，还**杀 prompt cache**。每轮把易变的 memory 注入进稳定前缀，等于每轮打穿缓存、成本翻倍。正确做法：稳定内容（system prompt、core memory）放前缀，易变注入放前缀之外或走服务端 context editing。能主动说出这层的候选人极少

**收尾（评估闭环验证，架构师落点）：**

"这套要用数据验证：评估**注入精确率**（注入的记忆里真正被回答用上的比例）和记忆开关 A/B（带记忆 vs 不带对任务成功率的影响）。目标是'更少但更准的注入'——实际观察注入量降下来后准确率是升的，反证膨胀问题的本质是相关性问题。"

**追问防御：**

- "摘要压缩丢细节怎么办？" → 摘要只是索引层，原文在外部存储保留，命中后可回捞（两级检索）；关键事实走结构化抽取而非自由摘要
- "这几个框架实际选哪个？" → 接第⑤题：简单个性化 Mem0（写入消解好）、强时序关系 Zep/Graphiti（注意 reranker 依赖）、agent 长生命周期自治 Letta（分页 + self-editing）；xBubble 自建双层（episodic + durable，Compound Memory 统一编排），因 Web3 时效性要求当时现成框架都不满足
- "core memory 放什么、谁决定？" → 放跨任务稳定且高频的（身份、偏好、硬约束）；可让 agent 自己晋升/降级（Letta self-editing），但设预算上限防止什么都往 core 塞

## 你在 Agent 权限、安全和边界管理方面做过哪些实践？

> 实证题——Guardrails、红队测试、HITL、SDK 权限收敛、LiteLLM 网关、合约审计背景全能用上。按"三层纵深"组织，每层带一个真实实践，收尾点破安全出身。

**开场框架句：**

"我把 Agent 安全当纵深防御做，分三层：**身份与访问层管'谁能调什么'，运行时防护层管'进出的内容干不干净'，行为边界层管'Agent 自己不能干什么'**。单独任何一层都挡不住，三层叠起来才可靠。这三层可以映射到 **OWASP Top 10 for Agentic Applications 2026**（ASI01–ASI10，2025.12 发布）——企业安全对话现在用它做通用语言。"

**第一层：身份与访问（最小权限）**

- 工具权限最小化：Agent 只挂它需要的工具，不给全量工具集——权限是架构时决定的，不是运行时求模型别乱来
- 生产实例：Claude Agent SDK 做 MR 自动评审时，权限收敛到**只读 diff + 写评论**两个动作，agent 拿不到合并、推送、删除权限，最坏情况也只是评论写错
- 入口收口：LiteLLM 网关统一管 API key、按团队/应用限流、预算硬上限；身份侧 Keycloak（SSO / OIDC）管人和服务的准入
- **Agent 作为第三类身份进 IAM（2026 共识）**：每个 agent 独立 OIDC client + 短时效 token，不共享 service account——出事能定位到具体 agent、单点吊销。业界产品化方向：Microsoft Entra Agent ID（2026.5 GA）、AWS AgentCore Identity、Okta/Auth0 for AI Agents（含 Auth for MCP）。三个"零"原则：**无常驻凭证、无全量 scope 令牌、agent 间不共享密钥**

**第二层：运行时防护（输入/输出 + 红队验证）**

- 输入侧：prompt injection / 越权指令检测（Guardrails validator 前置）
- 输出侧：格式校验、PII 过滤、事实性校验——Guardrails AI 的 validator 机制，本地跑通过 L1-L8 全套 + hub validator 变体
- 护栏有效性要**用攻击验证，不能自我感觉良好**：上线前用 Giskard 跑红队评测（injection / jailbreak 套件），把攻击样本沉淀成回归集，护栏每次变更都重新扫

**第三层：行为边界（高危操作与执行环境）**

- 高危操作强制 HITL：xBubble 支持聊天触发交易——这是资产安全级别的边界问题。做法是执行前过 **strategy-validator 风险校验** + LangGraph HITL 中断人工确认，Agent 可以提案，不能独自动钱
- 执行环境沙箱化：代码执行类工具放隔离沙箱，文件系统 / 网络访问白名单
- 双模式路由本身也是边界设计：Fast 模式只读查询放开跑，涉及深度分析/写路径的走 Deep 模式带更重的校验

**收尾（点破复合背景）：**

"我对'边界'的敏感其实来自智能合约审计出身——审计的本能是假设每个入口都会被恶意利用。Agent 安全和合约安全同构：**不能依赖'模型大概率不会乱来'，要在架构上保证它乱来也造不成损失**。这也是我认为 Agent 权限设计的第一原则：安全边界必须是确定性机制（权限、沙箱、HITL），prompt 里写'请不要'不算安全措施。"

**权限的具体实现（被问"到底怎么实现"时按四个执法点讲）：**

1. **工具可见性**：权限的第一实现是 tools 列表构造——按角色/场景组装工具子集，不给的工具模型根本看不见（MR 评审只挂 diff 读取 + 评论两个工具）
2. **调用拦截**：每次 tool call 执行前过策略判定。Claude Agent SDK 用 `permissions.allow/deny/ask` 规则（可到参数粒度）+ `canUseTool` 回调 + PreToolUse hook；LangGraph 给工具包 wrapper，deny 返回拒绝、高危 `interrupt()` 转 HITL。关键是**参数级校验**（SQL 只许 SELECT、转账限额），工具名粒度太粗
3. **凭证边界（唯一不依赖 agent 自身正确性的层）**：agent 进程持有的凭证本身就没有多余权限——GitLab token 只有 read + comment scope，注入成功也是服务端 403；每 agent 独立身份 + 短时效 token
4. **身份透传（防混淆代理人）**：多用户场景 agent 代用户行动时透传**用户的**身份，下游按用户 RBAC 判定——A 用户不能借 agent 查 B 的数据

**业界参考口径（Databricks 模式，被问"业界怎么做"时用）：**

"数据访问这块我认同 **Databricks 的 OBO（on-behalf-of）模式**：agent 权限**不另建体系，权限跟数据走**——agent 部署时有自己的 service principal 管运行时身份，但访问数据用 token exchange（RFC 8693）把发起用户的身份透传下去，Unity Catalog 里用户没权限的表 agent 替他干活时也查不到，行级列级权限对 agent 实时生效、零重复配置；审计**双身份落账**（真实用户 + agent 各记一笔）。我的自托管栈里这套是可落地的——Keycloak 原生支持 token exchange，LiteLLM 网关收口后换降权短时效 token 调下游。"

**追问防御：**

- "prompt injection 具体怎么防？" → 分层：输入检测只是第一道（会漏）；工具返回的外部内容标记为不可信数据、不当指令执行；架构级方向是 plan-then-execute / 双模型隔离不可信内容（CaMeL 一系思路）；**最后一道防线永远是权限而不是 prompt**——就算注入成功，agent 也没有能造成损失的权限
- "护栏误杀正常请求怎么办？" → 护栏也要评测：维护正常流量样本集，每次收紧规则跑误杀率回归；高风险动作宁可误杀转人工，低风险宽松
- "沙箱具体怎么做？" → 按风险分级：代码执行容器隔离 + 资源限额 + 网络白名单；文件操作限定工作目录；生产数据只读副本

# 概念补充（追问弹药，备查）

## MR 自动评审里的 MR 是指什么？

MR = **Merge Request（合并请求）**，GitLab 术语，等同于 GitHub 的 PR（Pull Request）。简历那条的含义：有人在 GitLab 提交 MR → CI 触发 Claude Agent SDK 起 agent → 读取 diff 自动评审 → 评论写回 MR 页面，覆盖 8 个仓库。口径注意：对 GitLab 公司说 MR、GitHub 公司说 PR，同义词直接接住。

## Token exchange 里的 token 是什么？降权链路怎么走？

token = **OAuth/OIDC 的访问令牌（access token，通常是 JWT）**——加密签名的"数字工牌"，写着"持有者是谁、能干什么、何时过期"，下游验签后决定放行。

链路里有两张牌：

1. **用户 token**（登录 Keycloak 拿到）：scope 宽（用户全部权限）、有效期长（小时级）、aud 是前端应用。**不能原样透传给 agent**——等于把用户全权工牌交给可能被注入的 agent
2. **降权 token**（token exchange 换出，RFC 8693）：agent 拿用户 token 找 Keycloak 换新牌——`sub` 还是用户（身份没变）、`act` 标注代办 agent（审计双身份）、`scope` 缩到本次任务（如只剩 market:read）、`aud` 限定单个下游 API、`exp` 分钟级

agent 全程只拿降权牌干活：就算被注入骗了想调下单接口，下游验签直接 403。**四个变化记牢：身份没变、权限缩了、受众限了、时间短了**——说出这四个才是真懂。这就是"凭证边界是最后一道硬防线"的具体机制。

## NFR 标准是什么？起什么作用、达到什么效果？

NFR = 非功能需求（性能/可用性/安全/成本等"做得多好"的维度），特点是**横切**：每个功能都沾边，做任何单个功能时都容易跳过，事后补十倍贵。传统靠资深架构师评审时"想起来问一句"——他不在场就漏、离职就失传。

我的 nfr-standard 仓（github.com/Colonel86/nfr-standard）把它编码成可执行标准，建在 spec-kit 上：

- **7 个门禁 G1–G7**：性能（延迟 SLO 定了吗）/ 可用性（模型挂了有 fallback 吗）/ 可观测（tracing+告警配了吗）/ 安全（注入防御+工具边界）/ 成本（单请求 token 预算）/ 评估（golden set + CI 回归，含金融场景"禁止前视偏差"）/ 可维护（新能力配置驱动还是改核心）
- **分级 T0/T2**：原型只查密钥安全，生产全过 7 门——**防橡皮图章 N/A**（不分级的标准会被敷衍杀死）
- **三个执法时点**：plan 时强制过门（Addressed+证据 或 N/A+理由，显式留痕）、CI 时评审 agent 按 Verification 清单查 diff、新项目 `install.sh` 一键继承

效果一句话：**把质量保障从"依赖某个人"变成"依赖流程"，把架构经验从"脑子里"变成"可安装的资产"——相当于给团队装了一个不会离职的架构评审员**。对上行业术语：7 门禁 = architectural characteristics（架构特征），Verification 章节 = fitness functions（架构适应度函数）。

## Prometheus / Loki / Tempo 各自做什么？

Grafana LGTM 栈的三种存储后端，对应可观测三大支柱，各答一个问题：

| 组件 | 支柱 | 回答的问题 | 数据形态 |
|---|---|---|---|
| Prometheus | 指标 Metrics | 系统现在健不健康？ | 时序数字：QPS、P99、错误率、token 消耗；定期 scrape，可设告警 |
| Loki | 日志 Logs | 出错时具体发生了什么？ | 文本日志；只索引标签不做全文索引（比 ES 便宜），Promtail 收集 |
| Tempo | 链路 Traces | 请求经过哪些环节、慢在哪步？ | trace → spans 调用树，收 OTel 上报 |

排查动线（加分点）：**指标发现问题（Prometheus 告警）→ 链路定位环节（Tempo 查 trace）→ 日志看清细节（Loki 按 trace ID 关联）**，Grafana 一块屏内跳转。LGTM = Loki + Grafana + Tempo + Metrics(Prometheus/Mimir)。

易混点防御："Tempo 和 Phoenix 都存 trace 什么关系？" → **Tempo 管基础设施视角（请求链路、延迟，给 SRE 看），Phoenix 管 AI 质量视角（prompt 内容、评估标注，给算法工程师看）**——数据同源（OTel 埋点），消费场景不同。

## SRE 是什么？

SRE = **Site Reliability Engineering（站点可靠性工程）**，Google 提出：用软件工程方式做运维——让系统"不挂、够快、出事快速恢复"。核心做法：SLO + 错误预算（挂太多就停新功能还稳定性债）、四大黄金信号监控（延迟/流量/错误率/饱和度）、自动化（扩容/切换/回滚写成代码）、故障后写 postmortem 改流程不怪人。国内常叫"运维开发/稳定性工程师"。面试可用句："我把传统 SRE 的成熟实践搬到了 AI 系统上——LGTM 栈、P99、告警面板就是给 Agent 系统配 SRE 级基础设施监控。"

## Blackbox 可用性探测是做什么的？

**从外部模拟用户定期"敲门"**，只看能否得到正常响应，不看系统内部（黑盒之意）。实现是 Prometheus 生态的 Blackbox Exporter：HTTP 探测（返回 200 吗、多快、证书几天过期）、TCP（端口通吗）、ICMP（ping 通吗）、DNS（解析正常吗），结果进 Prometheus 触发告警。

为什么必须有：**白盒监控会说谎**——进程活着、CPU 正常，但服务实际已不可用（死锁、上游断、证书过期），内部指标全绿用户全红。一句话分工：**白盒告诉你"为什么坏了"，黑盒告诉你"用户看到坏了没有"**；告警通常黑盒先响，再用白盒定位。

我的栈里探测目标：LiteLLM 网关健康端点（最高优先级，网关挂全断）、下游 LLM API 连通性（供应商故障要第一时间知道触发 fallback）、Phoenix/Grafana 自身（观测系统也要被观测）、HTTPS 证书有效期。

## Caddy 和 Keycloak 在自托管栈里各起什么作用？

**Caddy = 统一大门，Keycloak = 保安。**

- **Caddy（反向代理）**：按域名把请求分发给 LiteLLM / Grafana / Phoenix，内部服务不直接暴露；**自动 HTTPS** 是选它而非 Nginx 的核心理由——自动申请 Let's Encrypt 证书、自动续期，零证书运维；入口统一后限流、访问日志、认证跳转都有地方挂
- **Keycloak（IAM 身份中心）**：SSO 单点登录（登录一次全栈通行，离职禁用一个账号全栈生效）；OIDC/OAuth2 发牌方（发 token、执行 token exchange）；服务间身份（每个 agent/服务独立 OIDC client）；可联邦企业 AD/LDAP——赛力斯语境即"接入企业已有 AD，不另建账号体系"

一句话分工：**Caddy 管"流量从哪进、走 HTTPS"，Keycloak 管"进来的是谁、能干什么"**。加分句："企业内网标准三件套——入口（反向代理）+ 身份（IdP）+ 网关（LiteLLM）；我自托管跑通过，到企业换成 Nginx + AD + 商业网关，架构不变只换实现。"

## OIDC client 是什么？

**在身份中心（Keycloak）注册的"应用账号"**——用户有账号，应用也要有。OIDC = OpenID Connect（OAuth2 之上补"你是谁"的认证层）。注册得到 `client_id`（应用用户名，公开）+ `client_secret`（应用密码，保密）+ 配置（回调地址、可申请 scope、token 有效期）。

两种用法：**代表用户登录**（authorization code 流程：Grafana 作为 client 把用户引到 Keycloak 登录换 token）；**程序自己作为身份**（client credentials 流程：agent 用自己的 id+secret 直接换自己的工牌）。

"每个 agent 独立 OIDC client"的落地含义：审计能定位到具体 agent、scope 按 agent 收敛、出事单点吊销、token exchange 权限挂在 client 上。类比：**用户账号是"人的身份证"，OIDC client 是"应用的营业执照"**——"agent 作为第三类身份进 IAM"的落地动作就是给每个 agent 发营业执照。

## 延迟 SLO 是什么？

SLO = **Service Level Objective（服务等级目标）**，对服务质量的量化承诺线，如"95% 请求 3 秒内返回首 token，P99 不超 10 秒"。作用：把"要快一点"变成**可判定、可告警的数字**——告警阈值和优化优先级都从它推导（"我觉得慢" vs "离承诺线差 400ms"）。

- 三兄弟：**SLI**（实测指标）对比 **SLO**（内部目标）；**SLA** 是写进合同违约赔钱的对外承诺，SLO 定得比 SLA 严留缓冲
- 为什么用 **P99** 不用平均：平均会骗人（99 个 1 秒 + 1 个 60 秒平均才 1.6 秒），P99 盯最差 1% 用户的体验
- LLM 场景拆两个数：**TTFT**（首 token 时间，流式下决定体感）+ 端到端总延迟——NFR 标准 G1 门禁写的 "Latency SLO (TTFT, p99)" 即此意

面试句："SLO 是把性能从'感觉问题'变成'工程问题'的那道闸。"

## LangGraph 生态五组件（库 / Server / SDK / CLI / Studio）？

| 组件 | 包名 | 角色 |
|---|---|---|
| LangGraph 库 | `langgraph` | 开源核心：StateGraph、节点/边、checkpointing——**写图跑图**（生产主力） |
| LangGraph Server / Platform | — | 把图**部署成 API 服务**（assistants / threads / runs 端点 + 持久化 + 队列 + 扩容），现归入 LangSmith 产品体系，可托管可自托管 |
| LangGraph SDK | `langgraph-sdk` | **调用已部署 Server 的客户端**（Python/JS 薄封装），给前端 BFF / 其他后端用 |
| LangGraph CLI | `langgraph-cli` | 本地开发：`langgraph dev` 起本地 Server、打 Docker 镜像 |
| LangGraph Studio | — | 图形化调试台：可视化图、单步执行、改状态重放 |

核心区分：**`langgraph` 是"写图"的，`langgraph-sdk` 是"调用别人部署好的图"的**。SDK 三概念：assistant（图的一套配置）、thread（带 checkpoint 的持久会话）、run（一次执行，支持流式/后台/HITL 中断恢复）。

被问"LangGraph 怎么部署到生产"：图用库写，部署三条路——自己包 FastAPI（我们自托管栈的做法）/ 自托管 LangGraph Server / LangSmith 托管 Platform（按 run + uptime 计费）；调用方统一走 SDK，threads/runs/HITL 恢复不用自己造。2026 官方分工话术：**LangChain 出积木、LangGraph 管编排、LangSmith 管观测+部署**。

## OpenTelemetry 和 OpenInference 分别是什么？

一句话定位：**OTel 管"怎么记录和传输遥测数据"（通用管道），OpenInference 管"LLM 领域的数据该叫什么名字"（领域词汇表）**。类比：OTel 是邮政系统（信封格式、投递协议），OpenInference 是行业公文格式（信里字段怎么写）。

**OpenTelemetry（CNCF 开源可观测标准）**——解决"每家观测厂商私有 SDK、埋点一次锁死一家"的问题，四件套：

1. **API/SDK**：创建 trace/span、记 metric 的统一接口（各语言都有）
2. **OTLP 协议**：遥测传输格式——Phoenix/Tempo/LangSmith/Datadog 全都收
3. **Collector**：中间收集器，统一接收、加工、分发
4. **语义约定**：属性命名规范（HTTP 耗时叫 `http.request.duration`，不许各自发明）

裸 OTel 埋点：

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(
    OTLPSpanExporter(endpoint="http://localhost:6006/v1/traces")))  # 发往 Phoenix
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("quant-agent")

with tracer.start_as_current_span("fetch_funding_rate") as span:
    span.set_attribute("symbol", "BTCUSDT")   # 属性名随便起——问题就在这
```

关键缺口：OTel 只规定"怎么记"，没规定 LLM 调用的属性"叫什么"——你叫 prompt 我叫 input_text，后端没法统一渲染聚合。这就是 OpenInference 的位置。

**OpenInference（Arize/Phoenix 定的 AI 专用语义约定）**——两部分：

1. **规范**：span 类型（`openinference.span.kind`: LLM/CHAIN/TOOL/RETRIEVER/EMBEDDING/AGENT/RERANKER）+ 属性名（`llm.model_name`、`llm.token_count.prompt`、`input.value`、`tool.name`…）
2. **自动埋点库**：`openinference-instrumentation-openai` / `-langchain` / `-llama-index`——打补丁后每次 LLM/工具/检索调用自动产出规范 span

课 21 实跑的写法（业务代码零改动）：

```python
from phoenix.otel import register
from openinference.instrumentation.openai import OpenAIInstrumentor

tracer_provider = register(project_name="quant-agent",
                           endpoint="http://localhost:6006/v1/traces")
OpenAIInstrumentor().instrument(tracer_provider=tracer_provider)

from openai import OpenAI   # 之后正常调用即可，span 自动生成
```

产出的 span 属性（语义约定的实体）：

```
openinference.span.kind = "LLM"
llm.model_name          = "deepseek-chat"
llm.token_count.prompt  = 18
llm.token_count.completion = 236
```

因为属性名约定死了，Phoenix 才能自动渲染对话视图、算 token 成本、按模型聚合——**简历里"token 成本归因、P99 延迟分析"能做的前提就是属性名有约定**。

追问防御："OpenInference 和 OTel GenAI 约定什么关系？" → OTel 官方后来也出了 LLM 语义约定（`gen_ai.*`，如 `gen_ai.request.model`、`gen_ai.usage.input_tokens`），与 OpenInference 竞合：gen_ai.* 是官方标准但仍实验态，OpenInference 起步早、Phoenix 生态成熟。务实姿态：跟 gen_ai.* 走、钉版本容忍 churn，OpenInference 作 Phoenix 兼容层并存——两套约定描述同一件事，Phoenix 两种都收。

## AI Agent 的 metric 都有哪些？用什么框架统计？

核心认知先立住：**Agent 的 metric 大部分不是独立埋出来的，是从 trace 里算出来的**（一次 trace 携带延迟、token、工具调用、路径全部原始数据）。框架分两类：采集传输类（OTel/Prometheus）+ 质量评估类（Phoenix/RAGAS）。按三层指标展开：

**第一层 系统指标（SRE 视角按 LLM 语义切）：**

| 指标 | 说明 | 统计框架 |
| --- | --- | --- |
| QPS / 请求量 | 按 agent/skill/用户维度 | Prometheus counter |
| TTFT + E2E 延迟 P99 | 分解到 LLM/工具/检索各段 | trace span 时长聚合（Tempo/Phoenix） |
| 错误率 | 分类：LLM API 错 / 工具失败 / 超时 / 429 | Prometheus counter + 标签 |
| Token 消耗 | input/output 分开，按模型/agent/用户归因 | OTel GenAI 约定 `gen_ai.client.token.usage` |
| 成本 | token × 单价；预算余量 | LiteLLM 网关原生统计（知道每模型单价） |
| 缓存命中率 | prompt cache / 语义缓存 | 网关 / 自埋 counter |
| 模型可用性 | 下游探测成功率、fallback 触发次数 | Blackbox Exporter + LiteLLM 计数 |

**第二层 质量指标（Agent 特有，统计方式本质不同）：**

| 指标 | 统计框架 |
| --- | --- |
| 工具选择命中率 / 参数抽取正确率 | LLM-as-a-Judge 评 trace（Phoenix evals / LangSmith）+ 规则 |
| 轨迹收敛度（绕路/死循环/步数分布） | 轨迹评估（实际步数 vs 最优步数） |
| 任务成功率 | golden set 回归（离线）+ 在线采样 Judge |
| 幻觉率 / RAG 检索质量 | RAGAS（faithfulness / context precision·recall）、DeepEval |
| 格式合规率 | 规则校验（零成本可全量） |
| 护栏触发率 / 误杀率、HITL 介入率 | Guardrails 埋点 / 自埋 counter → Prometheus |

关键区分：**第一层是"记账"（counter/histogram 直接累加），第二层是"评判"（要跑规则或 Judge 才有结果）**——评判做不起全量，线上采样 + 规则预筛，结果写回 trace 标注再聚合。

**第三层 业务指标**：任务完成率（用户视角）、点赞点踩率、会话留存、单任务成本 ROI（替代人时价值 vs LLM 成本）。这层决定前两层阈值。

自埋 metric 代码示意：

```python
from opentelemetry import metrics
meter = metrics.get_meter("quant-agent")
tool_hit = meter.create_counter("agent.tool_selection.total")
task_steps = meter.create_histogram("agent.trajectory.steps")

tool_hit.add(1, {"skill": "funding_rate", "correct": str(is_correct)})
task_steps.record(len(trace_steps), {"mode": "deep"})
```

面试一句话总结："**系统层记账用 OTel metrics + Prometheus，质量层评判用 Phoenix/Judge 从 trace 算，成本类收口在 LiteLLM 网关，三路汇进 Grafana 一块屏——指标名跟 OTel GenAI 约定走。**"覆盖"有哪些 + 用什么统计"两问，且每个组件都真用过。
