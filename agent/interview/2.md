如何测试回答精准度？怎么做的

> **答法（详细机制见 jd-senior-agent-engineer/09-eval-driven-development.md）**
>
> **① 开场先拆"精准度"**——不同任务定义不同，定义不清没法测：
>
> - 有 ground truth（分类/抽取/路由）→ 直接算 accuracy/F1
> - RAG 问答 → 拆三个正交维度：**忠实度**（答案只基于检索材料，不编造）、**答案相关性**（答到问题点上）、**检索质量**（材料找对没）。答案错可能是检索的锅，不拆开定位不了
> - 多步 agent → 终点对不代表过程对，还要评**轨迹**（工具选择、有无绕路打转）
>
> **② 分层测**（测试金字塔）：组件级（检索 recall@k/MRR、工具选择准确率、schema 校验通过率）→ 端到端（任务成功率，按任务类型分桶）→ 轨迹级（agent 特有）。
>
> **③ 方法按确定性排序**：确定性断言（exact/contains/regex/JSON schema/跑测试）**>** 统计指标 **>** LLM-as-judge **>** 人工。judge 兜底语义判断但必须：给 rubric 逐条打分（不裸问好不好）；防三偏置（位置→交换顺序测两次、长度、自我偏好→换模型当 judge）；先拿几十条人工标注**校准 judge 与人的一致率**，不过关的 judge 不可信。
>
> **④ 数据与节奏**（"怎么做的"核心）：
>
> - eval 集：20–50 条人工黄金集起步 → **线上失败案例回流**（最值钱来源）→ LLM 合成扩边缘 case；数据集版本化当代码资产管
> - 开发期：eval 进 CI 当回归——改 prompt/换模型/调检索参数跑一遍看退步（DeepEval=pytest 风格进 CI；Promptfoo=YAML 矩阵对比）
> - 线上:抽样送 judge + 隐式信号（用户重述/追问"不对"）监控漂移
>
> **⑤ 实战弹药**：Guardrails 课跑过幻觉检测两条路线——NLI 判"答案能否被检索文档蕴含"（忠实度的确定性化实现）+ provenance 校验，即"精准度靠机制保证、不靠 judge"的落地案例；12a pgvector RAG（69 chunks 知识库）是检索单测现成场景。
>
> **收尾金句**：精准度不是测出来的，是"**测 → 失败案例回流 → 修 → 再测**"循环滚出来的——eval 是驱动开发的方向盘，不是上线前的一道关卡。

管理记忆？

> **答法（详细机制见 jd-senior-agent-engineer/04-multi-layer-memory.md；实跑过课程 12/12a/12b/12c/12d/12e 六套记忆方案）**
>
> **① 先给记忆类型学**（30 秒骨架）：
>
> - **短期/工作记忆** = 会话状态（messages、checkpointer 按 thread_id 快照），进程内、单线程
> - **长期记忆**按 CoALA 分三类：**semantic**（事实与知识："用户是 PG 重度用户"）、**episodic**（带场景的经历：历史邮件+处理标签，当 few-shot 用）、**procedural**（做事规则：prompt/工具定义本身也是记忆）
>
> **② 管理 = 四个生命周期环节**，每个环节都有取舍：
>
> - **写入**：agent 主动写（hot-path，挂 manage_memory 工具自主决定）vs 后台提取（对话结束后异步蒸馏，不占推理延迟）；写入时要做**冲突消解**（新旧事实矛盾时 update 而非重复 append——mem0 实测有消解失败样本，不能全信框架）
> - **存储**：数据模型跟着检索需求走——会话/时序走 **SQL 表按 thread_id 精确取（不是相似度！）**，知识走**向量库语义检索**，人物关系/时间演化走**知识图谱**（Zep/Graphiti 的时序图）；同库 SQL+向量并存是甜点位（pgvector）
> - **检索**：按记忆影响什么定检索方：影响**生成内容** → agent 自主调 search_memory（可能忘调）；影响**决策/路由** → 系统代码强制检索拼进 prompt（few-shot 翻转分类，100% 生效）；这是"工具型 vs 强制型"的关键架构决策
> - **遗忘与维护**：context 超限时 **Summarization 丢信息 vs Compaction 搬信息**（摘要作索引、原文归档、summary_id 可逆展开）；按用户 namespace 隔离（换 user_id 记忆互不可见）
>
> **③ 框架选型一句话**：LangGraph store+langmem（编排内轻量）→ mem0（开箱即用的提取+消解，但消解要抽检）→ Zep/Graphiti（要时序关系推理才上图谱）→ Letta/MemGPT（agent 自编辑记忆、OS 分页心智，重但自主性最强）。多数场景从"向量库 + 强制检索 + 后台提取"起步就够。
>
> **④ 实战弹药**：12a 亲手实现 MemoryManager（PG 里 7 类记忆表、SQL+HNSW 双路径、压实 2007→141 tokens）；课程 12 跑通 semantic/episodic/procedural 三类各自的读写机制（含 prompt optimizer 反馈改写）；Letta 跨 agent 信箱、mem0 消解失败样本、Graphiti 时序图谱都实测过——被追问任何一个都接得住。
>
> **收尾金句**：记忆管理的本质不是"存下来"，而是**在对的时机、以对的代价、把对的信息放回 context**——存储只是手段，context 装配才是目的。

知识库的分片处理

> **答法（检索选型详见 agent/skills/agent-selection/3-retrieval.md）**
>
> **① 为什么要分片、为什么它是地基**：三个约束逼出来的——embedding 模型有输入上限（bge-small 512 token，超了静默截断）；检索粒度（整篇文档做一个向量 → 语义被稀释，什么 query 都命中一点又都不准）；context 预算（命中后要塞回窗口，块太大塞不了几个）。**分片错了后面全歪**：再好的 embedding 和 rerank 都救不了切碎的语义单元。
>
> **② 策略谱系**（从机械到语义，成本递增）：
>
> - **固定大小 + 递归回退**：RecursiveCharacterTextSplitter——优先按段落切、切不动降级句子、再降级字符，`chunk_size` + `chunk_overlap` 两参数。80% 场景的起点
> - **结构感知**：按 Markdown 标题层级/代码函数边界/HTML 标签切，保住"天然语义单元"；不同文档类型分策略（代码按函数、表格整块不切、PDF 先版面解析再切）
> - **语义分片**：相邻句 embedding 相似度骤降处下刀，边界最自然但要先算全文 embedding，贵，收益在长篇连贯文档
> - **contextual retrieval**（Anthropic 路线）：每个 chunk 前置一段 LLM 生成的"这块在讲什么/来自哪"上下文描述再 embed——用一次性索引成本换检索命中率
>
> **③ 关键取舍**（资深分在这里）：
>
> - **chunk_size 没有普适值**：问答类小块准（定位精）、综述类大块全（上下文足）；跟 embedding 模型窗口匹配，overlap 取 10–20% 防边界切断关键句
> - **检索粒度 ≠ 生成粒度**（最重要的进阶点）：small-to-big / parent document retriever——用小块做**命中**（向量语义集中），命中后返回父块/邻域窗口给 LLM 做**生成**（上下文完整）。把"准"和"全"解耦，不再二选一
> - **chunk 必须带元数据**（标题路径、来源、页码）：过滤、引用溯源、以及 rerank 都靠它
>
> **④ 怎么验证分片好坏**：不是拍参数——拿标注的 query→chunk 对测 recall@k/MRR，A/B 不同策略；分片参数是**调出来的**，接 eval 那题的黄金集方法。
>
> **⑤ 实战弹药**：12a 的 `fetch_and_save_paper_to_kb_db`——arXiv PDF 全文 → RecursiveCharacterTextSplitter（chunk_size=1500 / overlap=200）→ 69 chunks 带元数据入 PG(pgvector, HNSW)，fastembed bge-small 384 维；agent 后续答题即基于这些 chunk 的语义检索。
>
> **收尾金句**：分片的目标不是"把文档切开"，是**制造检索单元**——每个 chunk 独立可理解、独立可命中；做不到就该换切法。
