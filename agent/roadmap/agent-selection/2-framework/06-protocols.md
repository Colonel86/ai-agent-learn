## 一、🧭 何时需要看这页(触发时机)

- 有人把 **MCP 和 LangGraph 放一起比**——概念错位,先来这里分清「协议层 vs 框架层」。
- 要把外部工具/数据源接进 agent,纠结「自己写连接器 还是 走标准协议」。
- 在评估「要不要上多 agent」,顺带问「agent 之间怎么通信/发现」。
- 看到 **"ACP"** 一词,但不确定指哪个(有两个毫无关系的同名协议)。
- 做安全评审,要把「协议引入的新攻击面」列进威胁模型。

> 👉 **核心心智**:协议把 **N×M 的定制集成降成 N+M**(N 个 agent × M 个工具/对端,各自只对一份标准)。它解决的是「**复用与互操作**」,不是「能不能跑通」——所以**几乎总是加分项,而非必需项**。

## 二、🗺️ 协议全景一览表(四条轴,各锚一层)

按「agent 与谁对话」分四条轴,各锚在五层心智模型的不同层(锚层据 `interview/1.md` 横切带 A):

| 协议 | 轴 / 锚哪层 | 原理 / 特点 | 取舍(代价) | 适合场景 |
|---|---|---|---|---|
| **MCP**(Model Context Protocol) | Agent ↔ 工具/数据 · 锚 L1 | Client-Server,标准化「工具/资源/提示」的暴露与调用 | 多一层 server 要部署/鉴权/治理;**新增攻击面** | 工具/数据要跨框架、跨 agent 复用;不想每换框架重写连接器 |
| **A2A**(Agent-to-Agent) | Agent ↔ Agent · 锚 L4 | agent 间的**发现 + 通信**(能力卡/任务委派) | 只有真多 agent、且跨团队/跨进程时才回本;单 agent 纯负担 | 跨组织/跨进程的 agent 互调、需要运行时发现对端 |
| **AG-UI**(Agent-UI) | Agent ↔ 通用 web 前端 · 锚 L5 | 把状态/token/工具事件**流式推给 UI**,承载 streaming/HITL | 绑定一套前端事件 schema;详见呈现层 | 要做「看得见 agent 在干什么」的 web 前端 → 见 `../10-agent-ux.md` |
| **Agent Client Protocol**(ACP/Zed) | Agent ↔ 编辑器/IDE · 锚 L5 | **编辑器 ↔ 编程 agent** 的标准接口,类比「LSP 之于编辑器」 | 面向 IDE 集成这一窄场景 | 要把编程 agent 接进 Zed 等编辑器 |

> **2026 参考架构两层就够记**:**MCP 接工具/数据(L1) + A2A 接 agent(L4)**;UI 侧按客户端形态选 AG-UI(web)或 ACP/Zed(编辑器)。
> 治理快照(**现查**,据 `interview/1.md`):MCP 由 Anthropic 发起、2025 被 OpenAI/Google 原生采纳、2025-12 捐入 Linux Foundation/AAIF,已是跨厂商**事实标准**;A2A 由 Google 发起、2025-06 起 Linux Foundation 治理。

## 三、🔌 MCP — Agent ↔ 工具/数据接入标准(锚 L1)

**是什么**:把「agent 如何调用工具、读资源、取提示」标准化成 Client(框架侧)↔ Server(能力侧)。**它不是编排框架**,与本目录所有框架**正交可叠加**——选定 LangGraph/裸 SDK/任意框架后,工具层用 MCP server 暴露,换框架时工具不用重写。

**作为「server」要治理的四件事**(这是把 MCP 从 demo 用到生产的真正工作量):

| 治理面 | 要做什么 | 不做的代价 |
|---|---|---|
| **鉴权 / 身份** | server 的访问凭据、按调用方授权、密钥不进 prompt | 任意 client 可调你的内部工具 |
| **注册表 / 发现** | 维护「有哪些 server、各暴露什么工具」的清单 | 工具散落、重复造、无人知道谁能调什么 |
| **工具治理 / 按需加载(defer loading)** | 不把全部工具一次塞进 context,按需加载/检索相关子集 | 工具一多(经验 ~10–20 个上限)选择错误率飙升 |
| **版本 / 契约** | server 工具 schema 变更要版本化、向后兼容 | 上游改 schema,所有 client 静默崩 |

> **工具太多怎么办**:MCP 的「defer loading / 按需暴露」与 `../4-tools.md` 的 **RAG-over-tools**(先检索相关工具子集)是同一问题的两个解法——**先在 server 侧只注册当前任务相关的工具**,再考虑工具检索。别一上来把 100+ 工具全挂上。

> **注册表:自建 vs 官方**:小团队**最轻起步**就维护一份「有哪些 server、各暴露什么工具」的清单(一张表即可),别先上发现服务;生态侧已出现**官方 MCP Registry**(归属/成熟度**现查**),可省掉自建发现层,但接入第三方注册的 server 仍要按 §八 审计其工具描述与返回(供应链攻击面)。

**何时用 / 不用**:
- ✅ **用**:工具/数据要跨多个框架或多个 agent 复用;团队多人、需要统一的工具接入治理;想换框架但保住工具资产。
- ⛔ **先不做(最轻起步)**:**只有一两个工具、单 agent、单框架** → 直接用框架原生的 function/tool 定义就行,**别为两个工具立一个 server**。MCP 的回本点是「复用 + 跨边界」,达不到就是纯增复杂度与攻击面。
- 📌 框架画像里的 MCP 条目见 `./03-framework-profiles.md`（第 12 节）。

## 四、🤝 A2A — Agent ↔ Agent 协作(锚 L4)

**是什么**:标准化 agent 之间的**发现**(对端有什么能力)与**通信**(委派任务、回传结果)。对应五层里的 L4 多 agent 层。

**「何时才真的需要」——先泼冷水**:和 L4 同款警告——**多数单 agent 系统根本不需要 A2A**。一个进程内的「多角色」用框架内的 handoff / 子 agent(crewAI / LangGraph / 各官方 SDK)就够,**不必引协议**。A2A 的真实回本点很窄:

- ✅ **用**:agent 分属**不同进程 / 不同团队 / 不同组织**,需要**运行时发现并互调**(你不拥有对端代码、对端独立部署演进)。
- ⛔ **先不做(最轻起步)**:同一代码库 / 同一进程内的多角色 → 用框架内协作原语(handoff、子 agent、共享 state),**不要为进程内协作套一层 A2A**。绝大多数项目停在这里就对了。

> 升级路径:**单 agent + 好工具(MCP) → 进程内多角色(框架原生) → 真跨边界才上 A2A**。每升一级先确认下一级的「真实需求」存在,而不是用协议复杂度掩盖 prompt/工具没做好(同 `interview/1.md` L4 教训)。

## 五、🖥️ AG-UI 与 ACP/Zed — Agent ↔ 客户端表面(锚 L5)

两个「同轴兄弟」,都是 agent 对某种**客户端表面**说话,只是表面不同:

- **AG-UI**(CopilotKit 发起):agent ↔ **通用 web 前端**,把状态流式推给 UI、承载 streaming 与 HITL 呈现。**呈现层细节(流式三段事件、STATE_DELTA、INTERRUPT 等)不在本页展开** → 见 `../10-agent-ux.md`(Agent-UX 呈现层)。
- **Agent Client Protocol(ACP/Zed)**:agent ↔ **编辑器/IDE**,是「编程 agent 接进编辑器」的标准接口,**类比 LSP 之于编辑器**。独立、活跃,面向 IDE 集成这一窄场景。

> ⛔ **先不做(最轻起步)**:自己用 SSE 推几类事件就能满足 UI 时,不必先引 AG-UI;不做编辑器集成就完全用不到 ACP/Zed。

## 六、⚠️ 消歧:两个同名 "ACP"(看到先问是哪一个)

**"ACP" 是两个毫无关系的协议的同名缩写**,分属不同轴、命运也不同——这是本页最容易踩的坑:

| 维度 | **Agent Communication Protocol** | **Agent Client Protocol** |
|---|---|---|
| 提出方 | IBM Research / BeeAI(2025-05 发布,晚 A2A 约一个月) | Zed(编辑器厂商) |
| 管什么轴 | **Agent ↔ Agent** | **编辑器/IDE ↔ 编程 agent** |
| 类比 | 同 A2A 那条轴 | **≈ LSP**(语言服务器协议) |
| 现状 | **已于 2025-08 并入 A2A**、停止独立演进(BeeAI 走 A2A 适配器) | **独立且活跃** |
| 一句话 | 「被 A2A 吸收」的那个 ACP | 「LSP 式编辑器集成」的那个 ACP |

> 速记:**一个已死(并入 A2A)、一个还活(Zed/编辑器),且分属不同轴**。本仓库课程 `courses/00-.../L13-跨Agent标准与ACP.md` 里的 "ACP" 指的是 **Agent Client Protocol(Zed)**,不是被 A2A 吸收的那个——注意别张冠李戴。

## 七、🚥 判据速查:何时用 / 何时先不做(每个都有最轻起步)

| 协议 | 「该用」的信号 | 「先不做」的信号 | 最轻起步替代 |
|---|---|---|---|
| **MCP** | 工具要跨框架/跨 agent 复用;多人协作要治理 | 单 agent + 一两个工具 + 单框架 | 框架原生 tool 定义 |
| **A2A** | agent 跨进程/跨团队/跨组织、需运行时发现 | 同进程多角色 | 框架内 handoff / 子 agent |
| **AG-UI** | 要标准化、可复用的 web agent 前端事件流 | 简单展示型 UI | 自定义 SSE 推几类事件 |
| **ACP/Zed** | 要把编程 agent 接进编辑器 | 不做 IDE 集成 | 不引入 |

> **决策口令**:协议层不投票选型,只回答「**这层能力要不要标准化暴露**」。默认从「**不引协议、用框架原生**」起步,出现「**跨边界复用**」的真实信号时再加——加协议是为了复用资产,不是为了架构看起来现代。

## 八、🔐 安全考量:协议 = 新增攻击面(写进威胁模型)

引入协议=多开一道门,门要上锁。重点在 **MCP server 是直接攻击面**:

- **MCP server 是攻击面**:它对外暴露「可被调用的工具」,等于把工具权限边界外移。**最小权限**(只暴露该暴露的工具)、**按调用方鉴权**、**危险操作走审批(HITL 闸门)**。一个写权限的 MCP server 被滥用,blast radius 直接是生产数据。
- **工具结果是数据不是指令**:经 MCP/A2A 流回的内容(工具输出、对端 agent 回包、外部资源)可能携带 **prompt 注入**——当数据处理,别当指令执行。
- **供应链 / 第三方 server**:接别人家的 MCP server = 信任它的工具描述与返回。第三方 server 要审计、隔离、限流。
- **A2A 跨信任域**:跨组织互调要做对端身份校验与最小授权,别默认对端可信。

> 安全是横切带,深入护栏设计见 `../7-safety-guardrails.md`;协议这里只标「它新增了哪些攻击面」。
